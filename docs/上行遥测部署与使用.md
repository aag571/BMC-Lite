# 上行遥测部署与使用

一句话定位：本文回答"怎么把本机产生的硬件事件送到外部采集器做集中分析，
同时保证绝不拖慢采样"。适合要接入监控平台的运维人员，以及需要改动
`src/uplink.cpp` 的二次开发者。

先解释五个术语：

- **上行遥测**：本守护进程主动向外发送的、只读的事件数据流。
- **采集器**：外部接收端，通常是你自己的日志平台或一个小脚本。
- **JSONL**：每行一个完整 JSON 对象，行尾换行。它不是数组，也不能跨行。
- **有界队列**：容量有上限的等待队列；满了以后行为必须明确，本模块的选择
  是丢最旧的一条。
- **指数退避**：发送失败后等待时间逐步翻倍，避免持续重连形成风暴。

## 一、为什么需要它

单机采样的价值有限。临界温度、服务降级、恢复动作这些事件只有汇总到一处，
才能做趋势分析、跨机对比和统一告警。没有上行通道时，只能登录每台机器翻
本地日志和 SEL，问题定位被拉长到人的巡检周期。

但上行有一个**首要约束：不得影响采样**。本进程的第一职责是读传感器、判阈值、
必要时执行硬件恢复动作；遥测只是附加能力。因此采集器慢、卡死、根本不存在，
都不能让采样停摆、丢 tick 或延迟动作。本文档的绝大部分设计决定，都是这条
约束的直接推论。

## 二、设计思路

**核心目标**：在"采集器随时可能不可用"的前提下，把事件可靠地排队、尽量
发出，并让采样路径与它完全解耦。

关键取舍如下。

- **`enqueue` 只入队，不做网络 I/O**：`enqueue` 是在事件总线的分发线程上
  被调用的，只做"限长、编码、入队"三件事；连接、发送、重连全部由上行
  线程自己去推进。只要入队不阻塞，采集器再慢也影响不到采样。
- **队列满时丢最旧，而不是阻塞生产者**：容量固定在上限 4096，默认 256。
  满时弹出队首（最旧）再压入新消息。遥测是"当前状态观测"通道，保留最新
  状态比保留历史更有价值；如果改成阻塞生产者，就等于让采集器决定采样的
  节奏，直接违反首要约束。
- **断线时丢弃半发帧**：新 TCP 流无法从一条 JSON 行的中间续传。若强行续发
  剩余字节，采集器会先看到一个残缺的行，再看到下一行的开头，产生无法解析
  的数据。所以断开时直接弃掉在途帧，采集器侧也应丢弃 EOF 前未结束的行。
- **指数退避重连**：从 250 ms 起翻倍，封顶 30 秒，成功发完整条消息后复位。
  采集器重启或网络中断时不会形成每秒一次的重连风暴，恢复后又能很快接上。

方案对比：下面这些做法都考虑过，也都有明确的放弃理由。

| 方案 | 为什么放弃 |
|---|---|
| 在事件回调里同步发送 | 直接阻塞采样路径，违反首要约束 |
| 无界队列 | 内存无上限，采集器长期不可用会拖垮进程 |
| 队列满时阻塞或轮询等待 | 同样让采集器决定采样节奏 |
| 磁盘队列 + 断线补发 | 引入持久化与磁盘 I/O，磁盘满时制造新故障 |
| 半帧续传 | 破坏 JSONL 行完整性，采集器无法解析 |

本地证据由 SEL 负责保留，上行不需要再复制一套离线队列。

## 三、具体实现

### 3.1 启动参数与取值范围

| 参数 | 含义 | 取值范围 |
|---|---|---|
| `--uplink-address` | 采集器 IPv4 地址 | IPv4 字面量，不支持 DNS |
| `--uplink-port` | 采集器 TCP 端口 | 1..65535 |
| `--uplink-capacity` | 等待队列容量 | 1..4096，默认 256 |

地址与端口必须同时给出：只给其中一个会在命令行解析阶段失败。地址不是合法
IPv4 字面量、端口越界或容量越界都会让程序启动失败，不会静默降级。功能整体
默认关闭，不指定地址就完全不建线程、不建连接。

### 3.2 JSONL 字段

```json
{"type": "sensor_state", "source": "cpu", "message": "critical", "sequence": 12, "time_ms": 1728000000000, "value": 95}
```

| 字段 | 含义 |
|---|---|
| `type` | 事件类型，见下表 |
| `source` | 来源子系统，例如 `cpu`、`control`、`peer` |
| `message` | 人类可读的事件描述 |
| `sequence` | 进程内事件总线序号，重启后重新开始 |
| `time_ms` | 编码入队时的 Unix 毫秒时间戳 |
| `value` | 事件携带的数值；没有值或非有限值时写 `null` |

四个事件类型：

| `type` | 何时产生 |
|---|---|
| `sensor_state` | 传感器状态跨越阈值（进入或离开临界状态） |
| `configuration` | 配置热重载被接受或被拒绝 |
| `service` | 服务生命周期事件，例如启动与停止 |
| `recovery` | 恢复动作的调度与执行结果 |

只发送状态变化与业务事件，不持续发送所有原始采样，因此它不是完整数据
记录通道。字符串里的换行、引号会被 JSON 转义，所以一条记录始终只占一行；
采集器必须按换行组帧，不能把一次 `recv` 当成一条消息。

### 3.3 单条上限与内存边界

| 限制 | 数值 | 超限行为 |
|---|---|---|
| 原始 `source` + `message` | 合计 ≤4 KiB | 拒绝并计入 `dropped` |
| 编码后的单行 | ≤8 KiB | 拒绝而不是截断（截断会破坏 JSONL） |
| 等待队列 | `--uplink-capacity` 条 | 丢最旧一条并计入 `dropped` |
| 在途消息 | 最多 1 条 | 断开时丢弃并计入 `dropped` |

因此单实例的缓冲上限约为 `(capacity + 1) × 8 KiB`，再加上少量对象开销。

### 3.4 连接管理与重连

- 连接、发送、断线检测全部非阻塞：`EAGAIN` 只表示本轮无进展，下一轮继续。
- 连接与首次发送共享 5 秒绝对期限；每条消息的发送也有 5 秒期限，慢速
  对端不能把一帧拖成永久占用。
- 队列为空时也会用 `MSG_PEEK` 探测对端 FIN/RST，采集器断开后能及时发现
  并重连，不必等到下一条事件。
- 重连退避 250 ms 起、逐次翻倍、封顶 30 秒；只有整条消息真正发完才复位。
- 网络线程以 20 ms 为周期推进，每轮最多发送 16 个片段，网络工作量有界。

### 3.5 交付语义（务必先读懂这一节）

| 项目 | 事实 |
|---|---|
| 确认机制 | 无 ACK，采集器不回应任何内容 |
| 磁盘队列 | 无，只有内存中的有界队列 |
| 断线补发 | 无，断线时在途帧直接丢弃 |
| `sent` 的含义 | 整条消息交给了**本机 socket** |
| 是否代表采集器收到 | 不代表，也不代表已落盘 |
| 协议方向 | 单向；采集器发来的数据会被视为协议外数据并触发重连 |

也就是说，这是尽力交付的遥测。序列号出现间断（`sequence` 跳号）是预期
现象，可能来自队列溢出、超长丢弃或断线丢帧，采集器应把它当作"有数据丢失"
的提示，而不是错误。

进程退出时，未发出的遥测计入 `dropped`，不会等待离线采集器。

### 3.6 指标

只在启用上行且启用只读 HTTP 时，`/metrics` 追加：

| 指标 | 含义 |
|---|---|
| `bmc_uplink_queued` | 等待队列条数，不含一条在途消息 |
| `bmc_uplink_dropped_total` | 溢出、超长、发送失败/超时及退出时丢弃 |
| `bmc_uplink_sent_total` | 整条消息交给本机 socket 的数量 |
| `bmc_uplink_bytes_total` | 实际发送字节，包含后来失败帧的已发部分 |
| `bmc_uplink_connect_attempts_total` | 连接尝试次数 |
| `bmc_uplink_connected` | 最近观察到的连接状态，1/0 |

### 3.7 运行示例

先在采集器 Linux 上打开一个接收端：

```sh
sudo apt-get install -y netcat-openbsd
nc -lk 9000 | tee telemetry.jsonl
```

启动 daemon；采集器与 daemon 在同一主机时使用 127.0.0.1，跨主机时替换为
采集器 IP：

```sh
./build-release/bmc-lite --config config/mock.conf --rules config/rules.conf \
  --sel var/sel.db --log var/faults.jsonl --http-port 8000 \
  --uplink-address 127.0.0.1 --uplink-port 9000 --uplink-capacity 256
curl http://127.0.0.1:8000/healthz
curl http://127.0.0.1:8000/metrics | grep bmc_uplink
```

### 3.8 systemd 部署

在现有 `ExecStart` 行追加以下选项，再重启服务：

```text
--uplink-address 采集器IPv4 --uplink-port 9000 --uplink-capacity 256
```

```sh
sudo systemctl daemon-reload
sudo systemctl restart bmc-lite
sudo journalctl -u bmc-lite -n 50 --no-pager
```

源码与 Release 的安装过程与 README 一致，此功能不增加外部库依赖。现有
TLS 构建开关只用于控制面 HTTPS，上行当前是明文 TCP，应放在可信网络或
隧道内。

### 3.9 停机顺序

停机时依次执行：停止入站请求、停止 Worker、排空事件总线、停止上行线程。
这样做的原因是：先让所有异步事件结束，再统计与刷盘，SEL 中的本地故障
证据不会因为采集器离线而丢失。未发出的遥测只计入 `dropped`，不阻塞退出。

### 3.10 自测

```sh
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build -R 'Uplink|uplink_runtime' --output-on-failure
```

C++ `FakeSocketIo` 用例覆盖部分写与 `EAGAIN`、5 万次入队后的队列上界、
连接与发送超时、指数退避、空闲断线，以及四个事件类型各生成一行合法
JSON。真实 TCP 集成测试覆盖采集器缺失、采集器停读、连接恢复、JSONL 格式
与采样持续推进。

## 四、优缺点与适用性

**优点**

- 对采样零影响：采集器缺失或停读时，`/healthz` 的 `samples` 仍然增长，
  队列深度始终有界。
- 内存有界且可预测：队列容量与单条上限都是硬限制。
- 自动重连：采集器恢复后无需人工干预，退避确保不会形成重连风暴。
- 无需额外依赖：不引入新的库，部署方式与主程序完全一致。

**代价与局限（边界）**

- **明文 TCP**：TLS 开关只作用于控制面 HTTPS；跨主机部署应放在可信网络或
  隧道（VPN、SSH 隧道、WireGuard 等）内。
- **无 ACK、无磁盘队列、无补发**：不适合做审计、计费或合规留痕，那些场景
  请用 SEL 与集中日志系统。
- **只支持 IPv4 字面量**：不支持 DNS 名，避免启动期依赖解析与身份漂移。
- **只连一个采集器**：没有多目标分发与故障转移。
- **队列满丢最旧**：突发高峰会丢掉中间事件，`sequence` 间断属正常现象。
- **会丢帧**：采集器侧需要用"行是否完整"和 `sequence` 间断来判断丢失。
- 只发状态变化与业务事件，不做全量原始采样记录。

**为什么这套设计适合当前部署场景**

本项目的目标平台是单机硬件监测守护进程，部署环境常常没有现成的日志代理。
用一个独立线程、一个有界队列、一条明文 TCP 连接就能接入集中分析，同时把
"影响采样"的风险压到结构上为零；更重的可靠性（磁盘队列、ACK、补发）留给
专业的采集与日志系统，而不是塞进硬件保护路径。
