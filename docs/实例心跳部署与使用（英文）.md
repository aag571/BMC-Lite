# Peer heartbeat installation and use

One-line summary: this document answers "with several instances deployed, how do
I know the remote instance is still alive and whether both machines loaded the
same configuration?". It is written for operators deploying peer heartbeat for
the first time and for developers changing `src/peer.cpp`.

Four terms first:

- **Heartbeat**: two instances periodically send each other a very small HTTP
  request and read the response, proving the other side is alive. It is a
  liveness signal, not a data channel.
- **Generation**: a configuration version number. It starts at 1 and increases
  by one on every successful hot reload. Equal generations mean both machines
  see the same configuration revision.
- **Stale**: no valid heartbeat arrived for `stale_ms`, so the remote side is
  declared stale.
- **Peer channel**: the heartbeat channel described here. It uses its own port
  and its own token, and it is disabled by default.

## 1. Why it is needed

A hardware monitoring daemon normally sees the world from one machine only: it
knows which sensors it read and which fans it changed. As soon as the same
service is deployed as two instances, two new questions appear:

1. Is the remote instance still alive? A killed process, an unplugged cable or
   a powered-off host is invisible locally.
2. Did both machines load the same configuration? If only one host hot-reloads,
   the two instances act on different thresholds and their fault evidence no
   longer matches.

Without heartbeat, both questions require a human to log into every machine, so
failure detection is as slow as the inspection cycle. Worse, the failure stays
silent: local metrics look perfect while half of the deployment is gone.

The usual multi-instance answer is leader election plus fencing, where fencing
means forcibly cutting a failed node's power or network so it cannot keep
writing shared resources. This project **only exchanges heartbeats and
generations; it does not elect a leader and does not fence**. The reason is that
this logic fails more dangerously than doing nothing: one wrong verdict can
remove a healthy node from service. This daemon protects hardware on one
machine, so keeping two running instances is preferable to an arbiter that can
kill the wrong one.

## 2. Design

**Core goal**: answer exactly two questions, "is the peer alive" and "what
generation does the peer report", while making it structurally impossible for
this channel to touch hardware.

The key trade-offs:

- **Separate port and separate token**: heartbeat listens on its own
  `--peer-listen-port` and loads its own `--peer-token-file`. The control plane
  is the only entry point that can trigger hardware actions, so sharing a port
  or a token would copy "change fan speed" authority into a liveness probe.
- **No Worker, Action or device reference in the type**:
  `PeerHeartbeat` stores only address, token, generations and timestamps. With
  no `Action` member there is no code path from a heartbeat to a hardware
  action; this excludes the possibility by type instead of by convention.
- **Outgoing traffic always verifies certificate chain and host name**:
  constructing `PeerHeartbeat` for a non-loopback peer requires a CA and a
  server name together. There is no "skip verification" switch in the code: if
  verification were optional, an attacker could fake heartbeats and make this
  host believe a compromised peer is healthy.
- **One connection per exchange**: the outgoing request carries
  `Connection: close`, and the daemon disconnects as soon as a valid response
  arrives. Liveness therefore means "a real round trip just completed", not
  "an old connection has not reported an error yet".

Alternatives that were considered and rejected:

| Alternative | Why it was rejected |
|---|---|
| Share the control port and token | The heartbeat credential would equal hardware authority |
| Carry configuration and apply it | One instance could rewrite the other's policy |
| Do election and fencing inside heartbeat | A wrong verdict evicts a healthy node |
| Long-lived connection with pings | Half-open connections look alive; extra timeouts needed |

## 3. Implementation

### 3.1 Options and constraints

| Option | Meaning | Constraint and default |
|---|---|---|
| `--peer-address` | Remote IPv4 address | Required; IPv4 literal only |
| `--peer-port` | Remote port | Required, 1..65535 |
| `--peer-listen-port` | Local listening port | Required, 1..65535 |
| `--peer-bind` | Local listening address | Default `127.0.0.1`, IPv4 literal only |
| `--peer-token-file` | Shared heartbeat token | Required |
| `--peer-interval-ms` | Heartbeat interval | >=10, default 1000 |
| `--peer-stale-ms` | Stale timeout | Must exceed interval, default 5000 |
| `--peer-ca` | CA used to verify the peer | Paired with server-name; required off loopback |
| `--peer-server-name` | Host name in the peer certificate | Same as above |
| `--peer-tls-cert` | Listener certificate | Paired with `--peer-tls-key`; off loopback |
| `--peer-tls-key` | Listener private key | Same as above |

If any `--peer-*` option appears, `--peer-address`, `--peer-port`,
`--peer-listen-port` and `--peer-token-file` must all be present, otherwise
option parsing fails and the process exits with code 2.

The token file is validated by `load_control_token()`: it must be a regular
file owned by the effective user, mode exactly 0640, opened with `O_NOFOLLOW`
(symlinks are refused), and contain 32..512 printable non-space characters
with one optional trailing newline. A 64-character random hexadecimal token is
recommended.

### 3.2 Protocol

| Item | Value |
|---|---|
| Method | `GET` |
| Target | `/v1/heartbeat` |
| Request header | `Authorization: Bearer <token>` |
| Request header | `X-BMC-Generation: <decimal non-zero integer>` |
| Request body | Must be empty |
| Success response | `200 OK`, `text/plain`, body is the local generation plus newline |

A generation must parse as a fully consumed decimal: empty strings, a minus
sign, trailing characters and `0` are all invalid.

### 3.3 Status code order: token first, target second

**The token is checked before the route**: a missing `Authorization` header or a
token mismatch always returns `401 Unauthorized`; repeated failures from the
same source IP are rate limited and then return `429 Too Many Requests`; only a
valid token combined with an invalid method, target, body or
`X-BMC-Generation` returns `400 Bad Request`.

The order exists because the two classes of error have different owners:
401/429 means "you are not a trusted peer", while 400 means "you are a trusted
peer but the request is malformed". If the route were checked first, an
unauthenticated scanner could map the supported paths from status code
differences.

Rate limiting is a token bucket with capacity 5 and a refill of 0.2 tokens per
second, so after a burst of five failures roughly one request per five seconds
is admitted. The bucket key is the source IP without the port, so changing the
source port does not bypass it. A valid token with an invalid request consumes
no authentication tokens.

### 3.4 State machine, deadlines and bounds

- The outgoing thread drives the state machine every 10 ms; one exchange is:
  connect, TLS handshake, send request, read response, disconnect.
- The whole exchange shares one **absolute deadline** of
  `min(5 seconds, stale_ms)`; partial writability cannot extend it. The next
  attempt starts after `interval_ms`.
- Send and receive are nonblocking: `EAGAIN` only means no progress this round.
- Each instance has at most one outbound exchange in flight; no work is queued.
- At most eight inbound connections are served; further connections are closed
  immediately and counted in the network metrics.
- An outgoing response growing beyond 8 KiB is treated as malformed, which
  disconnects and counts one failure.
- `stop()` waits at most one 10 ms cycle, so shutdown cannot hang on the
  heartbeat thread.

### 3.5 Stale and recovery are each reported once

`stale` is a **latched** flag: `now - last_seen >= stale_ms` reports
`peer stale generation=N` only on the crossing, so repeated checks do not spam
logs or events. Recovery behaves the same way and reports
`peer recovered generation=N` only on the transition back to fresh.

`last_seen` is initialised at construction, so **the timer starts at startup**:
even if no valid heartbeat was ever received, the peer becomes stale after
`stale_ms`. Valid incoming requests and verified outgoing responses both
refresh liveness.

Reports are published on the EventBus as type `service`, source `peer`, so they
also appear in SEL, the action log and uplink telemetry.

### 3.6 Metrics

With read-only HTTP enabled, `/metrics` adds:

| Metric | Meaning |
|---|---|
| `bmc_peer_stale` | Whether the peer is stale, 1/0 |
| `bmc_peer_generation` | Last observed peer generation, 0 if none |
| `bmc_peer_heartbeats_total` | Valid heartbeats: inbound requests + verified responses |
| `bmc_peer_failures_total` | Failed outbound exchanges |
| `bmc_requests_total{role="peer",...}` | Requests on the heartbeat listener by method/status |
| `bmc_request_bytes_total{role="peer",...}` | Bytes in and out on the heartbeat listener |

`bmc_peer_generation` is an observation only: the peer generation is **never**
copied into the local configuration automatically.

### 3.7 Two local instances

From the repository root; both processes must use the same token. The token
must belong to the runtime user, be exactly mode 0640, be a regular file and
not a symlink.

```sh
mkdir -p var/peer-demo
openssl rand -hex 32 > var/peer-demo/token
chmod 0640 var/peer-demo/token
# Terminal A:
./build/bmc-lite --config config/mock.conf --rules config/rules.conf \
  --log var/peer-demo/a.log --sel var/peer-demo/a.sel --http-port 8001 \
  --peer-address 127.0.0.1 --peer-port 9002 --peer-listen-port 9001 \
  --peer-token-file var/peer-demo/token --peer-interval-ms 1000 --peer-stale-ms 5000
# Terminal B:
./build/bmc-lite --config config/mock.conf --rules config/rules.conf \
  --log var/peer-demo/b.log --sel var/peer-demo/b.sel --http-port 8002 \
  --peer-address 127.0.0.1 --peer-port 9001 --peer-listen-port 9002 \
  --peer-token-file var/peer-demo/token --peer-interval-ms 1000 --peer-stale-ms 5000
# Terminal C:
curl -s http://127.0.0.1:8001/metrics | grep bmc_peer
```

Stop B: after five seconds A reports `peer stale` in SEL/log/EventBus and sets
`bmc_peer_stale=1`. Restart B: A reports recovery. Send B SIGHUP to observe its
new generation on A. The timer starts at startup even if no heartbeat has ever
arrived, and repeated stale checks do not spam logs.

### 3.8 Remote TLS deployment

Install both daemons using README.en.md, then create certificates containing
each server's actual IP/DNS SAN as described in
[控制面部署与使用（英文）](控制面部署与使用（英文）.md). Install a separate shared
peer token under `/opt/bmc-lite/control` on each machine, owned by the service
account, mode 0640. Do not reuse the control token.

Copy A's public certificate to B as `peer-ca.pem` and B's certificate to A;
private keys remain on their servers. With an internal CA, use the CA
certificate instead. All files live in the systemd-readable
`/opt/bmc-lite/control`; private keys 0600, tokens 0640. Both builds need
`BMC_TLS=ON`.

Append to A's systemd `ExecStart`, when B is 192.168.124.128:

```text
--peer-bind 0.0.0.0 --peer-listen-port 9443 --peer-address 192.168.124.128 \
  --peer-port 9443 --peer-token-file /opt/bmc-lite/control/peer-token \
  --peer-ca /opt/bmc-lite/control/peer-ca.pem \
  --peer-server-name 192.168.124.128 \
  --peer-tls-cert /opt/bmc-lite/control/cert.pem \
  --peer-tls-key /opt/bmc-lite/control/key.pem
```

On B, reverse the remote address and server name to A's actual identity. Keep
the config/rules/sel/log arguments and add `--http-port 8000` for metrics.
Include `ReadOnlyPaths=/opt/bmc-lite/control` in the override, run
daemon-reload/restart, and allow TCP 9443 between the two management hosts.
Rotate credentials by restarting.

Non-loopback outgoing traffic requires a CA and a verified server name;
non-loopback listeners require a certificate and key. A wrong CA, host name or
token cannot refresh liveness, and there is no insecure verification switch.

### 3.9 Startup failure and self-test

If the heartbeat object or the listener fails to start, the daemon stops the
peer listener, logs `listener unavailable` and throws, so the process finally
exits with code 1 (which makes systemd `Restart=on-failure` effective).
Sampling is unaffected because the failure happens at startup, before the main
loop runs.

```sh
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build -R 'PeerHeartbeat|peer_runtime' --output-on-failure
```

The C++ tests cover authentication and generation, stale and recovery being
reported once each, partial writes with `EAGAIN`, the absolute deadline and
retry interval of a pending connect, and rejection of plaintext remote peers
and incomplete TLS. `peer_runtime` uses two real processes to verify
bidirectional heartbeats, generation propagation after a hot reload, stale and
recovery, and that peer traffic never writes the configured PWM.

## 4. Strengths, costs and applicability

**Strengths**

- Peer liveness and configuration generation are observable and recorded in
  SEL, the log and uplink telemetry.
- Hardware actions are structurally impossible: using the peer port as a
  control port only yields 400.
- Separate port and token, so a leaked credential or a fault stays inside the
  peer channel.
- Disabled by default: without options nothing listens and no thread starts.

**Costs and limits**

- **No leader election, no fencing, no failover**: both instances keep acting
  on their own rules and conflicts are resolved by a human.
- **Generation is observed, never applied**: a mismatch must be fixed by
  reloading or aligning configuration manually.
- IPv4 literals only; DNS names are not supported.
- One new TCP connection per interval (once per second by default), so
  connection and TLS handshake cost is higher than a long-lived connection.
- Real network jitter can produce false stale alarms; `stale_ms` must be tuned
  to the actual network.
- The heartbeat proves the peer's heartbeat thread is alive, not that the peer
  keeps sampling.
- It uses the monotonic `steady_clock`, so wall-clock jumps do not matter, but
  it carries no relation to real date and time.

**Why this fits the project**

Multi-instance deployment here is redundant observation, not a high-availability
cluster: hardware protection decisions are made by the local rule engine and
need no cross-host arbitration. Narrowing the scope to "liveness plus
generation" buys deployment visibility at almost zero risk; automatic failover
belongs to an external orchestrator, not to a daemon that would have to guess.
