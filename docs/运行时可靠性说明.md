# 运行时可靠性说明

**一句话定位**：这份文档回答"当日志、SEL 或内部状态表**自己**开始出问题时，
守护进程靠什么继续采样、靠什么让人看见故障"。适合值班与运维人员，以及要修改
`monitor.cpp`、`logger.cpp`、`sel.cpp`、`rules.cpp`、`recovery.cpp` 的开发者。

## 一、为什么需要它

监测程序最讽刺的失效方式是：**故障刚发生，记录故障的那条路先坏了。** 现实中有三类具体表现：

1. **日志写不进去**（磁盘写满、目标是 `/dev/full`、只读挂载、配额耗尽）。
   此后每一条采样记录都会失败一次。如果"写失败"被当成致命错误，守护进程会在最需要它的时候退出——
   温度还在升高，而已经没人值班了。
2. **内部状态表随着硬件变化无限增长**。设备热插拔、重新枚举，或者每次启动拿到的传感器 ID 都不同，
   都会在规则引擎与恢复引擎里留下再也不会被使用的条目。进程连续运行几个月后内存被慢慢吃光。
3. **"写失败"与"同步失败"被混为一谈**。数据写进了内核页缓存但 `fdatasync` 失败，
   和写入本身失败是两回事；混在一起计数会让人分不清"记录真的丢了"还是"记录只是还没落盘"。

先解释后面反复出现的四个词：

- **降级（功能受损但继续运行）**：不退出、也不重试到卡死，而是带着受损的功能继续工作，
  并把"我正在降级"报出来。
- **节流（限制上报频率，避免刷屏）**：同一个故障按固定时间间隔重复上报，
  否则每个采样周期都会新增一条记录，真正的新故障会被淹没。
- **fsync / fdatasync（把数据真正写入磁盘）**：`write` 通常只把数据交给内核页缓存，掉电即丢；
  `fdatasync` 是请内核把数据真正落到持久介质上。它代价高，所以只用在"这条记录是故障证据"时。
- **反馈循环（feedback loop）**：告警本身也走同一条失败路径，
  于是告警产生新的失败、新的失败又产生新告警。

没有这套机制会怎样：最坏的情况不是崩溃，而是**日志在丢、状态表在涨、而没有人知道**。

## 二、设计思路

核心目标只有一句话：**把"能继续工作"和"必须停下来"分开。**

判据也只有一条：这个问题会不会让**已确认的故障证据**永久丢失，或让**判定条件本身失效**？

| 情形 | 处置 | 为什么这样判定 |
|---|---|---|
| 日志写入失败 | 继续采样，计数并上报 | 日志是审计轨迹，不是恢复依据 |
| SEL 写入失败 | 继续采样，单独计数并上报 | 不能因为"记不了笔记"就不值班 |
| `fdatasync` 失败 | 单独计数（`sync_failures`） | 数据可能已在页缓存，不等于丢失 |
| 日志/SEL 缓冲区超限 | 丢弃最旧字节并计数 | 保证内存有界，且丢了多少可被观测 |
| 配置或规则非法 | 启动失败，或热加载整体拒绝 | 判定条件错误会给出错误的硬件动作 |
| 控制面动作审计持久化失败 | 停止监听，进程以非零码退出 | 硬件动作必须有不可否认的审计 |

**为什么日志写失败不退出**：退出等于"因为记不了笔记，所以不值班"。
日志在这里的角色是审计轨迹；它损坏时正确的做法是让监测继续，并把"日志已不可信"本身
变成一条可观测的告警。（唯一的例外是轮转后**重新打开文件**失败——此时新分片根本不存在，
会抛 `std::system_error`；普通写入失败从不抛出。）

**为什么降级告警不能写回失败的日志**：告警自己也是一次日志写入。如果日志失败触发告警、
告警又写进同一份失败日志，失败计数会自我推高，形成反馈循环，把一条真实故障放大成无穷多条。
所以日志降级告警**只写 SEL 与事件总线**，不碰那个已经失败的日志。
同理，SEL 降级上报自己以**非关键**方式追加，不会强制 `fdatasync` 而再次失败。

**考虑过但放弃的做法**：

- **写失败立刻退出、交给 systemd 重启**：会丢掉正在进行的采样上下文，故障时最不该做的事。
- **失败就无限重试直到成功**：磁盘满时会把采样线程钉死在写系统调用上。
- **为降级上报单开线程或监听端口**：本项目刻意不新增线程与端口，降级必须复用
  已有的采样循环和事件总线，否则"可靠性机制"自己又成了新的故障面。
- **状态表满了就淘汰最旧条目**：会把仍在冷却或正在执行的状态误删，导致恢复动作重复触发
  或丢失去重。正确做法是只回收"确实可回收"的条目。
- **给降级状态加一套新的持久化格式**：复用既有 SEL 与日志格式，
  这样 `grep` 和 [控制面部署与使用](控制面部署与使用.md) 里的查询方式都不必改。

## 三、具体实现

相关代码集中在 `src/monitor.cpp`（上报）、`src/logger.cpp`、`src/sel.cpp`（落盘）、
`src/rules.cpp`、`src/recovery.cpp`（状态表）。

### 1. 日志降级上报

`Monitor::report_log_degradation` 读取 `EventLogger::write_failures()` 与 `dropped_bytes()`：

| 规则 | 具体行为 |
|---|---|
| 触发条件 | 失败次数**或**丢弃字节数与上次上报值不同 |
| 首次上报 | 立即，不受节流限制（保证降级立刻可见） |
| 后续上报 | 距上次上报不足 5 秒则跳过本轮 |
| 相同计数 | 不重复上报 |
| 窗口内的变化 | 合并到下一次允许上报时的最新累计值 |
| 去向 | SEL 一条 `source=log state=degraded` + 总线 `service` 事件 |
| 不写回 | 不向正在失败的 `Logger` 写任何告警 |

检查点有两处：`Monitor::poll` 末尾，以及主循环 `logger.flush()` 之后（`src/main.cpp`）。
计数器**只在真正上报成功之后**才推进基线，所以被节流丢掉的那次观测会在下一轮补报。

以文件日志为例，SEL 里的一条记录形如：

```text
source=log state=degraded message="log-write-failures=10 dropped-bytes=0"
```

实际 SEL 文件使用带引号的字段格式（`std::quoted`），可以这样查询：

```sh
sudo grep '"log" "degraded"' /var/log/bmc-lite/sel.db | tail -10
```

`Logger` 把三类情况都计入 `write_failures()`：
真实写入失败、`fdatasync` 失败（`sync=true` 时）、以及因超过缓冲区上限而丢弃未落盘内容。
丢弃的字节数另外记入 `dropped_bytes()`。

采样期间日志持续失败**不会**终止采样；只有退出时的最终刷盘失败会让进程返回状态 1
并在 stderr 打印 `log flush failed`（`tests/degradation_runtime_test.py` 固化了这一行为）。

### 2. SEL 写入降级上报

`Monitor::report_sel_degradation` 的规则更简单：**只在 `sel.write_failures()` 增长时上报一次**
（相同值不重复上报），上报内容包含四个互相独立的计数：

| 字段 | 含义 |
|---|---|
| `sel-write-failures` | 写入（或压缩重写）失败次数 |
| `sync-failures` | `fdatasync` 失败次数，单独计数 |
| `pending` | 尚未成功落盘的字节数 |
| `dropped` | 因缓冲区超限被丢弃的字节数 |

这条上报同时写一份日志动作行（`logger.action`）、一条 SEL 记录（`state=degraded`，**非关键**）
和一条总线 `service` 事件。之所以不设为关键记录：否则"上报降级"自身就会强制落盘，
可能再次失败并把计数推得更高。有了这套计数，"故障证据正在丢失"从一个猜测
变成了一个可查询的数字。

### 3. 规则状态的生命周期

规则引擎的运行时状态键是 `<规则 id>\n<触发状态>\n<传感器 id>`（把触发状态放进键里，
改 `trigger` 的规则就不会命中旧状态的计数与 `active` 标志）。

| 时机 | 行为 |
|---|---|
| 每轮 `Monitor::poll` 结束 | 用当前传感器集合做 `retain_sensors`，删除已消失设备的状态 |
| 仍存在的传感器 | `bad`/`good` 确认计数与 `active` 标志**保持不变** |
| 为什么每轮都做 | 只在热重载时做不够：ID 相同的新设备会继承旧计数，映射也会持续增长 |
| SIGHUP 热重载 | `merge` 先整体校验新规则集，再决定哪些状态可以沿用 |

`merge` 保留的条件是"规则身份（`id` + 触发状态）仍在"**且**"传感器仍存在"。
被删除的规则、消失的传感器、以及 `trigger` 被改写的规则，其状态一律丢弃——
保留下来的 `active` 会对应到不同的判定条件，那比丢失状态更危险。
`confirmations`/`action` 的改动不重置状态，因为判定身份没有变。

**给直接调用者的提醒**：`retain_sensors` 必须在一次完整设备采样之后调用，
并传入当前**全部**传感器；如果在每个单独 `evaluate` 之后只传当前一个设备，
会错误地清掉其他设备的确认计数。这些接口属于采样线程，不是网络线程共享对象。

### 4. 恢复状态表的上限与回收

`RecoveryPolicyEngine` 的状态键是 `传感器 + '\n' + 动作`，所以同一传感器的不同动作各有独立冷却。

| 规则 | 具体行为 |
|---|---|
| 上限 | 4096 条 |
| 何时检查 | 只在需要**新建**键时做一次容量检查 |
| 可回收条目 | `!running` 且 `now - last >= cooldown`（从未执行完的条目同样可回收） |
| 绝不淘汰 | 正在运行（`running`）或仍在冷却窗口内的状态 |
| 回收后仍满 | 拒绝本次恢复，`detail = "state capacity"` |

"宁可少做一次动作，也不让状态表无界增长"是有意的选择：拒绝是可见的（结果里带原因），
而状态表溢出会让进程在几周后无声地死掉。

### 5. 日志与 SEL 的落盘策略

两者都用**常驻描述符 + 批量合并写入**，把"每条记录一次系统调用"降为"每批一次"。

| 对象 | 批量阈值 | 同步策略 | 未落盘缓冲区上限 |
|---|---|---|---|
| `Logger` | 4096 字节 | 默认**不** `fsync` | 1 MiB，超出丢弃最旧字节 |
| `SelStore` | 4096 字节 | 关键记录立即 `write+fdatasync` | 1 MiB，超出丢弃最旧字节 |

**为什么日志默认不 `fsync`**：它是审计轨迹而非恢复依据，允许崩溃时丢掉最后一小批。
把 `Logger` 构造参数 `sync` 设为 `true` 即可恢复"每条记录立即落盘并 `fsync`"的强持久行为。
**为什么 SEL 要区分关键记录**：状态迁移、规则激活/清除、恢复结果、控制面审计都是故障证据，
每一条都 `important=true`，立即 `write+fdatasync`；普通记录累积到阈值再落盘。

另外四条与"不丢行"直接相关的实现细节：

- **轮转前先落盘**：日志只在"当前文件 + 未落盘缓冲区 + 新记录"确实超过上限时才轮转，
  且轮转前先把缓冲区写进即将改名的分片；如果这一步写失败，就保持文件与缓冲区原样并立刻重试。
  仅仅为了判断是否轮转而无条件落盘，会让缓冲区永远是空的，批量合并也就完全失效了。
- **无法查询大小的目标**（管道、设备节点）跳过轮转判断，但仍然尝试写入，
  这样这些目标上的写入失败依然可被观测到。
- **短写只重试后缀**：`write` 只写出一部分时，缓冲区只保留尚未写出的后缀，
  重试不会把已经写出的半条记录再写一遍。
- **SEL 启动重放**：尾部没有换行符的残缺记录由 `Truncate` 策略处理（见下表），
  并在内存里按 `max_records`（默认 4096）裁剪；超过上限时用唯一临时文件重写压缩，
  `fsync` 后 `rename`，目录项也 `fsync`，最后由 `SelStore` 接管新的描述符
  （`rename` 不会更新已经打开的 fd，不接管就会继续写入已被删除的旧 inode）。

| `Truncate` 策略 | 启动时的行为 |
|---|---|
| `tail`（默认） | 从残缺记录起点截断文件，丢弃字节数记入 `truncated_bytes()` |
| `refuse` | 只追加、不修改文件：绝不丢数据，但残缺行会留在文件中间 |
| `prepare` | 内存模式：记录只进内存，不写文件也不压缩（测试与只读检查用） |

### 6. 开发验证

```sh
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build -R 'RuntimeManagement|degradation_runtime' --output-on-failure
```

覆盖内容包括：`/dev/full` 上的写入失败、运行期持久告警、5 秒报告窗口、
"告警不反写日志"、丢弃字节独立变化、1 万个设备出现又消失、
保留传感器的确认计数，以及 `Monitor` 的真实裁剪接线
（见 `tests/runtime_management_test.cpp` 与 `tests/degradation_runtime_test.py`）。

## 四、优缺点与适用性

**优点**

- **故障时仍然值班**：日志坏了不退出、SEL 坏了不退出，监测本身从不因为"记录失败"而停摆。
- **故障可观测**：降级不是沉默的，它变成 SEL 记录、总线事件与可查询的计数器。
- **内存有界**：规则状态随当前设备集合收敛，恢复状态表与两个写缓冲区都有硬上限。
- **证据优先**：真正需要持久化的记录（状态迁移、规则决策、恢复、控制面审计）单独走同步路径。
- **不加新的故障面**：没有新增线程、监听端口或存储格式，降级复用已有通道。

**代价与局限**

- **降级期间会丢日志**：缓冲区超过 1 MiB 时丢弃最旧字节，只保留计数，内容确实丢了。
- **节流窗口内的事件被合并**：5 秒内的多次计数变化只会报出最新累计值，
  期间"失败增长的速度"这种细节观察不到。
- **SEL 也不可写时无法保证告警持久化**：这时只剩日志与事件总线，
  若两者都不可用，降级就是不可见的（这一点无法用本机制解决）。
- **恢复状态表满时会拒绝动作**：极端情况下宁可少做一次恢复，也不扩容。
- **关键记录的同步有代价**：每条故障证据一次 `fdatasync`，
  量化的开销见 [写入路径性能基准](写入路径性能基准.md)。
- **退出码语义有限**：日志刷盘失败只反映为退出码 1 与一行 stderr，
  不区分"丢了几条"；具体数量要去计数里看。

**为什么这是本项目最适配的选择**：BMC-Lite 的定位是"长期驻留、低资源、尽量不误动作"的监测守护进程。
它没有冗余存储，也没有外部事务协调者，所以不可能做到"记录绝不丢失"；
能做的就是**把损坏变成可观测、可计数的状态，同时绝不因为记录问题而放弃监测**。
把降级逻辑放在无状态的 `Monitor` 与注入式的 `EventLogger` / `SelStore` 之上，
既不需要新线程，也让每条降级分支都能在单测里用替身驱动。
