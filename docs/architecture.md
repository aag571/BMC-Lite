## 1. 这个项目是干什么的

**BMC**（Baseboard Management Controller，基板管理控制器）是服务器主板上的一颗独立芯片。
它的职责很单纯但很关键：**在操作系统不管事的时候，盯着机器的物理状态**——温度、电压、
风扇转速——出问题就记录下来，能救就救。

`BMC-Lite` 不是真的 BMC 固件，而是把 **BMC 的核心逻辑**用 Linux 上的一个普通用户态
程序实现出来。它做四件事：

> **概要**：在 Linux 用户态使用 C++ 实现温度、电压、风扇转速采集、故障判断、结构化日志
> 和受控恢复。无真实 BMC 硬件（如使用 QEMU 虚拟机）时，模拟输入覆盖同一条处理链。
> 真实设备的路径、比例、阈值和恢复目标全部由配置定义。

| 做的事 | 说人话 |
|---|---|
| 采集 | 定时去读温度、电压、风扇转速 |
| 判断 | 判断这个数值算正常还是危险 |
| 记录 | 把发生的事写成日志；重要的事件单独存一份"事故档案" |
| 恢复 | 危险时尝试救一下（本项目中就是调大风扇） |

### 为什么要这么复杂

如果只读一次就动手，温度探头抖一下、或者某一瞬间读到垃圾数据，风扇就会乱转。
**这个项目绝大部分复杂度，都在解决"如何不被假信号骗到"。**

### 设计目标与边界

| 目标 | 说明 |
|---|---|
| 单一实现 | 模拟输入和真实硬件**走完全同一条处理链**，不存在"测试用一套、生产用一套" |
| 无硬件可运行 | 没有真实传感器（如使用 QEMU 虚拟机或纯软件环境）时用模拟序列，整条链路照样跑通 |
| 受控恢复 | 只允许写配置里明确指定的 PWM 文件，不执行任意 shell |
| 有界资源 | 队列、缓冲区、连接数都有上限，且上限满时有明确行为（丢弃并计数，而不是崩溃或无限增长） |
| 默认不可达 | 全部网络能力默认关闭，不显式开启就不监听任何端口 |
| 只读管理面优先 | 先保证"能看见发生了什么"，再考虑"能远程控制"；**不要求远程 TCP 也能完整运行** |

## 2. 核心难题：如何不被假信号骗到

这是全项目最重要的设计，也是理解其他一切的前提。三个机制配合使用。

### 2.1 去抖（debounce）：连续确认才认账

配置里的 `debounce 3` 意思是：**连续 3 次读到异常，才算真的异常。**

```text
读到 95°C → 可疑，先记下，对外状态仍是 normal
读到 95°C → 第 2 次
读到 95°C → 第 3 次，达到门槛 → 正式判为 critical
```

如果中间夹了一次正常值，计数**清零重来**。所以一个偶发尖峰骗不到它。

> 这就是代码里 `pending_count_` 的作用：记录"当前候选状态已经连续出现几次"。

### 2.2 迟滞（hysteresis）：留一段缓冲带，防止边界横跳

假设 `critical = 90`。如果只按"低于 90 就恢复"判断，温度在 89.9 ↔ 90.1 之间抖动时，
状态会疯狂来回切换，风扇跟着一顿一顿启停。

**迟滞就是留一段缓冲区间**：`hysteresis 3` 表示**必须降到 87 以下才算真的恢复**。

```text
升上去：90 才算 critical
降下来：87 才算恢复正常      ← 中间的 87~90 保持原状态不动
```

> 代码里体现为 `normalized >= critical - hysteresis`。注意迟滞只影响**恢复**，
> 不影响**升级**——恶化要敏感，恢复要谨慎。

### 2.3 读取失败与"垃圾值"必须单独处理

这三点看似琐碎，但都是真实踩过的坑：

1. **读取失败单独计数**，达到 `failure_limit` 才进入 `unavailable`。探头偶发一次读不到，
   不应该立刻报"设备失联"。
2. **NaN 与无穷大被当作"读取失败"，而不是"一个数值"。** 原因是 NaN 参与任何比较都返回
   `false`——如果不管它，它会一路穿过所有阈值判断，最后被静默地当成"正常"。这是最危险的
   一类 bug：**监控系统悄悄失效，但看起来一切正常。**
3. **方向可配。** 温度是"越高越危险"，风扇转速是"越低越危险"。代码用乘一个方向系数
   （`high ? 1 : -1`）把两种方向统一成"越大越糟"，因此判断逻辑只写一份，
   而不是复制两套。这是典型的架构取舍：**把差异压缩到参数里，而不是复制代码。**

## 3. 故障状态机

每个传感器独立维护一个状态，只有四个取值：

| 状态 | 含义 | 类比 |
|---|---|---|
| `normal` | 正常 | 病人平稳 |
| `warning` | 警告，需留意 | 需要观察 |
| `critical` | 危险，要处理 | 要叫医生 |
| `unavailable` | **读不到数** | **探头掉了 / 人不在病房** |

### 关键点：`unavailable` ≠ `critical`

这两个是**不同性质**的问题：

- `critical` = "数值很危险"
- `unavailable` = "**我根本不知道现在什么情况**"

后者往往更可怕：探头坏了，你就**失去了监控能力**，而所有危险都可能在无监控状态下发生。
所以它必须是独立状态、能独立上报，绝不能被糊弄成"正常"。

### 只有状态真的变了才产出事件

```text
每次采样 → Engine::update(读数)
             ├── 状态没变 → 返回"无事件"（什么都记）
             └── 状态变了 → 返回一个 Event（旧状态、新状态、当前值、原因、序号）
```

**为什么这样设计？** 如果每次采样都记一笔，正常运行一天会产生 86400 条相同记录，
真正的故障会被淹没。只有"变化"才是有信息量的。

> 时间戳不放在事件里，而是由写档案（SEL）时补上。事件本身只描述"发生了什么变化"。

## 4. 完整走一遍：一次温度事件的生命周期

用项目自带的 `config/mock.conf` 真实配置推演。`cpu_temp` 的配置是：

```text
cpu_temp mock 45,75,76,77,95,96,97,88,87,86,60,59,58,err,err,err,45,45,45 1 high 70 90 3 3 3 -
```

含义：模拟后端、按逗号循环读数、`high`（越大越危险）、warning=70、critical=90、
迟滞=3、连续确认=3 次、失败上限=3 次、`-` 表示不写 PWM。

| 巡房次数 | 读数 | 累计失败 | 判定过程 | 状态 | 写档案 | 触发规则 |
|---:|---:|---:|---|---|:---:|---|
| 1 | 45 | 0 | 正常 | normal | — | 否 |
| 2–4 | 75,76,77 | 0 | ≥70 连续 3 次 | → **warning** | ✅ | 否（规则只针对 critical） |
| … | 95,96,97 | 0 | ≥90 连续 3 次 | → **critical** | ✅ | ✅ 激活 `cpu-critical` |
| … | 88,87,86 | 0 | 在 87~90 迟滞带内 | **仍 critical**（不掉） | — | 已激活，不重复触发 |
| … | 60,59,58 | 0 | < 87，连续 2 次 | → **normal** | ✅ | ✅ 清除 `cpu-critical` |
| … | err×3 | 3 | 失败达上限 | → **unavailable** | ✅ | ✅ 激活 `any-unavailable` |
| … | 45×3 | 0 | 恢复正常 | → **normal** | ✅ | ✅ 清除 |

几个值得注意的细节：

- **warning 不触发动作。** `rules.conf` 里的规则只针对 `critical` 和 `unavailable`。
  警告级别的意义是"让人知道"，不是"自动动手"。
- **规则有独立的确认次数。** 注意上表第 4 行：`Engine` 已经进入 critical，但规则
  `cpu-critical` 要求 `confirmations 1`、而 `unavailable` 那条要求 1 次——
  规则层的确认是**独立的第二道闸门**，目的是允许"设备已经很危险了，但要更谨慎才动手"。
- **通配规则 `*` 按传感器各自计数。** `any-unavailable` 的 sensor 是 `*`，
  意味着任何一个传感器不可用都会触发，但每个传感器有独立的计数与激活标志。

### 一次恢复动作的完整路径

```text
规则激活
  └─ Worker::submit 提交任务（异步！不阻塞采样）
       └─ RecoveryPolicyEngine::submit
            ├─ 同一(传感器,动作)正在执行？ → 拒绝 "already running"
            ├─ 并发额度满？               → 拒绝 "concurrency limit"
            ├─ 还在 30 秒冷却期内？        → 拒绝 "cooldown"
            ├─ 状态表已满且无可回收？      → 拒绝 "state capacity"
            └─ 通过 → 释放锁 → 执行 Action（最多 3 次尝试，总退避 ≤30ms）
                 ├─ LogOnlyAction：只记日志（默认，dry-run）
                 └─ PwmAction：真的往配置指定的文件写 PWM 值 255
```

**四个拒绝原因分开报，不是啰嗦，而是必要的：** 调用方需要区分"这是重复提交"和
"系统忙不过来"，前者应该忽略、后者可能需要扩容。混在一起就无法判断。

## 5. 分层结构

四层，依赖方向**严格单向**：上层知道下层，下层完全不知道上层。

| 层 | 职责 | 代表文件 | 关键约束 |
|---|---|---|---|
| **domain**（领域） | 纯逻辑判断：读数该算几级、规则要不要触发 | `engine.cpp`、`rules.cpp`、`calibration.cpp` | **不碰文件、不碰设备、不碰网络** |
| **hardware**（硬件） | 真的去读设备 | `readers.cpp`、`chips.cpp` | 所有系统调用经统一接口转发 |
| **infrastructure**（基础设施） | 拧螺丝的活：文件描述符、定时器、信号、日志、线程池 | `fd.cpp`、`logger.cpp`、`sel.cpp`、`worker.cpp`、`event_bus.cpp` | 通用、与业务无关 |
| **application**（应用） | 把上面三层拼起来，管进程生命周期 | `main.cpp`、`monitor.cpp`、`config.cpp`、`cli.cpp` | 只有它知道"整个程序怎么启动和停止" |

**为什么这个方向很重要？** 因为 `domain` 层不依赖任何外部东西，所以它可以在没有硬件、
没有文件、没有网络的机器上完整测试。项目里测试覆盖最密集的就是这一层。

### 一个刻意的例外：`core.hpp`

`include/bmc/core.hpp` 一个头文件里塞了 20 多个类型（约 350 行）。按教科书标准这是
"上帝头文件"、应该按类型拆开成十几个小文件。**但这里是故意不拆的**，理由记录在
`docs/code-guide.md`：

> 保留 core.hpp 作为兼容的公共声明入口，避免一次引入大量互相包含的头文件。

这是一个**有意识的取舍**：牺牲"单文件整洁"，换取"不用处理一堆头文件互相 include 的
麻烦"。代价是 `core.hpp` 偏长，读的时候建议配合目录结构定位。

## 6. 并发模型：一个主线程加三个"外人"

这是全项目并发设计的核心，也是理解"为什么这个程序不会卡住"的关键。

### 6.1 主循环：一个人守着一台交换机

程序主体是一个单线程事件循环。它把所有需要等待的东西**登记**给 Linux 的事件通知器
`epoll`，然后等 `epoll` 告诉它"哪个有动静了"。

```text
        ┌───────────── epoll（统一事件分发）─────────────┐
        │                                               │
   timerfd              signalfd                  GPIO（可选）
  （定时器响）        （收到信号）              （线电平跳变）
        │                    │                        │
   采样一次             SIGHUP → 重载配置          立刻额外采样一次
                       SIGTERM → 准备退出
```

三个登记项，每个都有"为什么这样选"：

| 登记项 | 作用 | 为什么不直接用更简单的方式 |
|---|---|---|
| `timerfd` | 定时触发采样 | **不能用 `sleep()`**：睡眠期间收不到信号，退出会变慢，而且采样周期会被信号处理打乱 |
| `signalfd` | 把信号变成"可读的数据" | **信号处理函数里能干的事极少**（不能加锁、不能分配内存、不能调用大多数库函数）。把信号转成普通事件，就能在主循环里安全地处理 |
| GPIO | 线电平变化的中断 | **默认不用**：绝大多数硬件（hwmon）不支持可靠的中断通知，只能老实轮询。只有 GPIO 这类能独立注册中断的才值得用事件驱动 |

**主循环只做采样和状态判断，绝不干重活。** 这是硬约束：调风扇这种慢操作
（可能要几十毫秒）如果放在主循环里，整条采样节奏就被拖住了——一个坏掉的风扇
能让监控停摆。

### 6.2 三个"外人"：只读 HTTP、控制面、实例心跳

这三项网络能力各自开**独立线程 + 自己的 `epoll`**，和主循环并行运行。但它们受三条铁律约束：

**铁律一：绝不直接碰传感器对象，只能读"加锁的快照"。**

为什么这么严？因为**热加载会整个换掉传感器对象**。如果网络线程抓着一个旧对象的引用，
那就是野指针——程序会随机崩溃，而且极难复现。所以网络线程能看到的只有两样东西：
SEL 的快照、以及配置的快照，两样都是加锁拷贝出来的。

**铁律二：网络线程里绝不能直接写硬件。**

控制面收到"调大风扇"的请求时，必须把它扔进 `Worker` 任务队列，走和自动恢复
**完全同一条**恢复引擎。这样冷却、去重、并发限制、审计这些保护**自动全部生效**。
如果图省事绕过它直接写 PWM，那所有保护就都失效了——这是架构上最不能妥协的一条。

**铁律三：默认全部关闭。** 不给出对应开关，**连监听端口都不创建**。

### 6.3 为什么不用"一个端口搞定所有事"

四种网络需求（只读管理、控制面、上行遥测、实例心跳）的信任级别完全不同：

| 通道 | 方向 | 信任前提 | 要认证吗 | 出问题的后果 |
|---|---|---|---|---|
| 只读管理 | 入站 | 低 | 不需要 | 只影响可观测性 |
| **控制面** | 入站 | **高** | **必须** | **可造成物理动作** |
| 上行遥测 | 出站 | 中 | 采集器侧 | 不得影响采样 |
| 实例心跳 | 双向 | 高（对等） | 双向 | 可导致脑裂 |

合并成一个端口的代价是具体的：**一个端口无法按角色分别限流和审计**。
只读端点会继承写通道的凭证与暴露面；慢采集器会波及控制面重试；
实例间协议会变成"任何对等体都能改风扇"的后门。所以宁可多几个端口。

## 7. 安全设计：默认什么都不能干

### 7.1 默认全关，且 fail-closed

| 能力 | 默认 | 怎么开启 |
|---|---|---|
| 写 PWM（真的调风扇） | **不写**，只记日志（dry-run） | `--enable-actions` |
| HTTP 只读接口 | 不监听 | `--http-port` |
| 控制面（能触发动作） | 不监听 | 端口 **和** 令牌文件，两个都必须给 |
| 实例心跳 | 不监听 | 四个参数必须齐全 |

**"fail-closed" 的意思是：配置不全就拒绝启动，而不是降级成"裸奔但绑本地"。**
比如控制面只给了端口没给令牌文件——程序直接报错退出，
**不会开一个"不用密码的控制端口"**。这种习惯在安全领域叫"失败时选择关闭而非打开"。

默认全关还有一个实际好处：**不开启这些功能时，程序的攻击面和完全不做网络功能时一模一样。**

### 7.2 只允许写"配置里指定的那一个文件"

「不执行任意 shell」和「不允许控制请求指定文件路径」是配套的两条。

控制请求只能传**传感器名字**和**动作名**，真正的文件路径来自服务器自己的配置。
否则只要能构造一个请求让它写 `/etc/passwd`，整个系统就完蛋了。
代码里额外加 `O_NOFOLLOW`（拒绝跟随符号链接）只是**最后一道防线**，
防止有人用软链接把路径偷偷拐到别处。

### 7.3 令牌（密码）的处理细节

控制面用一个文件里的长随机字符串做认证。为什么不用命令行参数传？
**因为命令行参数会出现在 `ps` 输出和系统日志里**，等于公开密码。

文件本身也有硬性要求：

| 要求 | 原因 |
|---|---|
| 必须是普通文件、不能是符号链接 | 防止被指向别处 |
| 权限必须**严格**是 `0640` | 太宽（别人能读）不行；`0644`/`0666` 直接拒绝启动 |
| 属主必须是运行这个服务的账户 | 防止别人替换 |
| 长度 32~512 字符 | 太短不安全；太长放不进 HTTP 头部 |
| 比对时用**常数时间**算法 | 见下 |

**"常数时间比较"是什么、为什么要它？** 普通字符串比较是"发现第一个不同字符就返回"，
所以比较耗时**隐含地泄漏了正确密码的前缀信息**——攻击者可以通过测量响应时间
一个字符一个字符地猜出密码。常数时间比较从头扫到尾、不看内容差异提前返回，
从而不泄漏这类信息。

### 7.4 恢复动作的自我保护

| 机制 | 取值 | 为什么 |
|---|---|---|
| 冷却窗口 | 30 秒 | 风扇转速不会瞬间响应，每秒发一次会把硬件写爆，还掩盖真实情况 |
| 同一传感器去重 | 是 | 同一个动作不该重复提交 |
| 重试上限 | 3 次 | 避免一个坏设备把线程池占死 |
| 总退避预算 | ≤30 毫秒 | 即使失败要重试，也不能长期占用工作线程 |
| 队列满 | **记录拒绝事件** | 不静默丢弃——"没能处理"本身是需要知道的信息 |
| 状态表上限 | 4096 条 | 防止传感器频繁出现消失导致内存无限增长；但**正在执行或仍在冷却中的状态绝不淘汰** |

### 7.5 明确不做危险操作

**远程重启、关机、硬件 reset** 是 BMC 的标准功能，但也是**最危险的**——一条错误指令
就能让服务器下线。本项目主动不做这类动作，把风险从设计上排除，而不是靠"小心使用"。

## 8. 可靠性：宁可降级，不可消失

这一节体现的是工程成熟度。核心原则：**区分"能继续工作"和"必须停下来"。**

| 场景 | 行为 | 为什么 |
|---|---|---|
| 某次采样读失败 | **不退出**，累计失败次数 | 探头偶发故障不该让整个监控死掉 |
| 读失败达上限 | 进入 `unavailable` 并报告 | 单独的状态，不伪装成正常 |
| 配置文件写错 | **阻止启动** | 带着错配置跑，比不跑更危险——你会以为它在监控，其实没有 |
| 日志写入失败 | **只计数 + 上报降级，不退出** | 见下 |
| 档案（SEL）写入失败 | 同上，另把失败计数写进档案 | 见下 |
| 收到 SIGTERM | 有序停止：先排空已接受的任务，再退出 | 不能丢掉已经开始处理的活 |
| 退出时缓冲区仍未落盘 | 返回非零码 + 在错误输出说明原因 | 让 systemd 知道这次不正常 |

### 8.1 为什么日志写失败不退出

日志是**证据**，但监控本身更重要。如果因为磁盘满就退出，等于"因为记不了笔记所以
不值班了"——这显然更糟。所以设计成：继续监控，但把"我的日志正在丢"这件事
**上报成一条降级记录**。

这里有个很容易做错的细节：**降级告警不能写回那个已经失败的日志**。
否则会形成反馈循环：写失败 → 产生一条告警 → 告警也写失败 → 又产生一条告警……
所以降级信息走的是 SEL 和事件总线，不走日志本身。

### 8.2 两份记录，用途不同

| | 日志（Logger） | 档案（SEL） |
|---|---|---|
| 内容 | 所有事件的流水账 | 只记状态变化与恢复动作 |
| 用途 | 排查问题 | **故障证据** |
| 落盘策略 | 批量合并写（默认每 4096 字节一次），**默认不强制同步** | 关键记录**立即 `write` + `fdatasync`** |
| 崩溃时可能丢 | 最后一批（可接受） | 不丢（必须留存） |
| 满了怎么办 | 按大小轮转，保留若干份 | 只保留最近 4096 条，超出时重写文件压缩 |

**为什么要分开？** 因为两者的"证据价值"不同。日志是过程记录，丢几条无所谓；
档案是"故障发生过"的凭据，可能用于追责或分析根因，必须落盘。

### 8.3 崩溃后的自我修复

档案文件如果因为断电在**最后一条记录写到一半**时中断，重启后会发现"尾部有残缺"。
默认行为是**从残缺记录的起点截断**，然后继续追加，并记录"丢弃了多少字节"。

为什么默认截断而不是保留？因为残缺的行留在文件中间会让后续所有读取解析失败——
**一行半截会毒化整个文件**。当然这个行为是可选策略（`Truncate::refuse` 可以改成
"只追加不回退"，宁可无法解析也不丢字节）。

## 9. 配置与热加载

### 9.1 配置分成两类文件

| 文件 | 内容 | 改动频率 |
|---|---|---|
| `hardware.conf` | 有哪些传感器、后端、阈值、动作目标 | 换硬件才改 |
| `rules.conf` | 什么状态触发什么动作 | 调策略时改 |

分开的理由：调整告警策略不该冒着写错传感器路径的风险。

### 9.2 热加载：不重启就换配置

运维现实是"不能为了改一个阈值就重启监控"。所以支持发一个信号（`SIGHUP`）让程序
重新读配置。但这件事有几个必须做对的地方：

**第一，先全部校验完，再动任何状态。**

```text
收到 SIGHUP
  ├─ 解析新传感器配置 + 解析新规则
  ├─ 两者全部校验通过？
  │    ├─ 否 → 记一条 "reload rejected; keeping generation N"，保持旧配置不动
  │    └─ 是 → 发布 "validated generation N+1" → 替换 → 刷新缓存 → 完成
```

如果边解析边替换，中途失败就会留下"传感器换了一半、规则还是旧的"这种四不像状态，
比拒绝重载糟糕得多。

**第二，规则状态要"合并"而不是"清空"。**

这是最容易忽略、但用户最能感知的细节。假设某规则已经激活（风扇正在高速运转），
此时你只改了一个**无关**的阈值并重载——如果规则状态被清空，程序会认为
"这条规则还没激活"，然后**再触发一次恢复动作**。

所以重载时按"规则 id + 触发状态"判断哪些状态可以保留：

| 情况 | 保留状态？ |
|---|---|
| 规则 id 和触发状态都没变 | ✅ 保留确认计数与激活标志 |
| 规则的触发状态被改了（比如 critical 改成 warning） | ❌ 丢弃（旧的激活标志对应的是不同条件） |
| 规则被删除 | ❌ 丢弃 |
| 传感器消失了 | ❌ 丢弃 |

**第三，配置代次（generation）。** 每次成功重载，代次加一。
这个数字会通过网络接口暴露，让自动化工具能确认"我改的配置真的生效了"。
实例心跳之间也交换这个数字，用来互相判断对方是不是还活着、配置是否一致。

## 10. 如何做到可以在没有硬件的情况下验证

这是本项目在工程上最有价值的部分，也是它区别于"玩具项目"的地方。

### 10.1 把所有"外部世界"抽成可替换的接口

程序里所有与外部打交道的动作——打开文件、读设备、发网络包——**都不直接调用系统调用**，
而是通过两个薄接口：

| 接口 | 覆盖什么 | 生产实现 | 测试实现 |
|---|---|---|---|
| `LinuxIo` | 文件/设备的 `open`/`ioctl`/`read`/`write` | 真的调系统调用 | 脚本化返回值 |
| `SocketIo` | 网络的 `socket`/`accept`/`recv`/`send` | 真的调系统调用 | 脚本化返回值 |

**为什么这个抽象值得做？** 因为 I2C 芯片的寄存器解码、GPIO 的线值读取、TCP 的分包重组
这些逻辑**很容易写错，但很难测**——总不能为了写单测去插一块真的温度传感器。

有了这层抽象，测试可以构造"芯片返回了 0xFFF8"这样的场景，然后断言
"解析出来是 −0.125°C"。**芯片寄存器解码、地址校验、能力位拒绝、PWM 写入失败路径
这些以往最难测的逻辑，因此都能在普通机器上完整测试**，不需要插一块真的传感器。

代价是每次调用都多一层间接，但相比"无法测试"，这个代价微不足道。

### 10.2 用 Python 写一份参考实现，逐字对拍

只读 HTTP 接口的输出（Redfish 形状的资源文档、Prometheus 指标文本）有一个特殊要求：
**格式必须严格固定**，因为监控系统会按固定格式解析。

项目的做法是：用 Python 写一份独立的参考实现（`tools/bmc_manage.py`），
让生成器把它的输出固化成 C++ 测试里的"标准答案"（`tests/service_vectors.hpp`），
然后断言 C++ 实现**逐字节相同**。

**为什么要这么麻烦？** 因为如果只写 C++ 测试并自己填期望值，那测试只是
"重复了一遍我的假设"，无法发现"我以为对但其实和真实约定不符"。
有一份独立实现做对照，才真的能发现差异。

> 这个机制也确实发挥作用了：它曾暴露出 C++ 侧把 `1e16` 写成
> `10000000000000000`，而 Python 输出 `1e+16`。

### 10.3 三层测试，覆盖不同层次

| 层次 | 手段 | 能验证什么 | 不能验证什么 |
|---|---|---|---|
| 单元测试 | C++ + 假接口 | 判断逻辑、寄存器解码、状态机、持久化加固 | 真实进程行为 |
| 进程测试 | Python 启动真实程序 | epoll 循环、信号、热加载、真实 socket/TLS | 真实硬件电气行为 |
| 动态检查 | ASan/UBSan/TSan/Valgrind | 内存错误、未定义行为、数据竞争 | 逻辑正确性 |

**这三层不可互相替代。** 单元测试再全，也测不出"收到 SIGTERM 时线程没排空"；
进程测试再真实，也跑不出真实温度传感器的电气特性。

### 10.4 诚实的边界声明

测试全部通过**不等于**可以在真实硬件上直接使用：

- 真实 I2C/GPIO 的**电气行为**必须在目标板子上验证——虚拟机测不出来。
- 部分芯片寄存器常量标注为"**未核实**"（未拿到对应数据手册的确定章节），
  这些在文档和代码注释里都明确标注，**不以确定语气呈现**。
- 高可用相关的选主/fencing 没有实现，因为自己实现失败模式比不做更危险。

**把边界写清楚，比假装没有边界更专业。**

## 11. 边界与明确不做的事

| 不做 | 原因 |
|---|---|
| 完整 Redfish / RMCP+ / IPMI | 只实现了 Redfish 形状的只读子集 |
| 选主、fencing、故障切换 | 脑裂防护需要法定人数、外部仲裁与状态对账；自己实现失败模式是"两个实例同时控风扇"，比不做更危险 |
| 固件 A/B 升级 | 不在范围内 |
| SSE / WebSocket 推送 | 只做请求-响应 |
| 远程重启 / 关机 / reset | 最危险的功能，主动排除 |
| 强制取消已提交的任务 | 会破坏审计与一致性；改为"有界队列 + 明确拒绝" |
| SEL 的 CRC 与断电事务 | 只做尾部残缺修复，中间位翻转无法检测 |
| 多写者协调 | 日志与档案都假定单一写者（本进程） |
| 任意 shell 命令执行 | 恢复动作是白名单枚举，不是通用执行器 |

## 12. 术语表

| 术语 | 通俗解释 |
|---|---|
| **BMC** | 服务器上独立管理硬件的芯片；本项目是它的核心逻辑的软件实现 |
| **采样 / tick** | 一次"巡房"：读一遍所有传感器 |
| **去抖 debounce** | 连续 N 次异常才算异常，防偶发误报 |
| **迟滞 hysteresis** | 恢复时要求比触发时更"远离"阈值，防边界抖动 |
| **阈值 threshold** | 判断正常/警告/危险的警戒线 |
| **SEL** | System Event Log，系统事件档案；只记状态变化与恢复动作 |
| **PWM** | 控制风扇转速的信号；写入 0~255 的数值 |
| **dry-run** | 演练模式：只记录"本来会做什么"，不真的动手 |
| **fail-closed** | 配置不完整就拒绝启动，绝不降级成"不安全但能用" |
| **epoll** | Linux 的事件通知机制；一个线程可以同时等很多东西 |
| **fd / 文件描述符** | Linux 里"打开的东西"的编号（文件、socket、设备都算） |
| **RAII** | C++ 惯用法：资源在对象析构时自动释放，不靠手写清理 |
| **注入 / 可注入接口** | 把"怎么访问外部世界"做成参数，测试时换成假的 |
| **对拍** | 两份独立实现比输出，用来发现单方无法发现的错误 |
| **令牌 token** | 相当于密码的长随机字符串 |
| **常数时间比较** | 比较耗时不随内容变化，避免通过时间差猜密码 |
| **工作队列 / Worker** | 后台线程池；耗时的活扔进去，不阻塞主循环 |
| **有界队列** | 有容量上限的队列；满了有明确行为（丢弃并计数） |
| **代次 generation** | 配置版本号，每次成功热加载加一 |
| **冷却窗口 cooldown** | 同一动作在这段时间内不重复执行 |
