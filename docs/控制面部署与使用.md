# 控制面部署与使用

本文回答一个问题：**怎么安全地把 BMC-Lite 的控制接口打开并正确使用**。
它面向系统管理员和运维人员——你不需要读 C++ 代码，但需要一台 Linux 主机、
root 权限，以及理解"谁能改这块板子的风扇转速"这件事的分量。
只想了解网络层的设计依据，请看文末延伸阅读里的网络设计说明。

## 一、为什么需要它

BMC-Lite 会按规则自动做恢复动作（例如温度进入 warning 时提升风扇）。
但自动规则覆盖不了所有情况：现场排查时，运维常常需要
**主动触发一次检查或一次风扇提升**，来确认设备还听不听话。

没有控制面时，唯一的办法是登录到那台机器上手工执行：
目标机器需要 SSH、需要有人记住正确的 PWM 节点路径、
需要自己确保"不要连续写太多次"，而且这次操作**不会留下结构化的审计记录**。
更糟的是，一旦为了省事在别处再写一段"直接写 PWM"的脚本，
自动恢复引擎的冷却、去重与并发限制就全部失效了。

控制面要解决的问题因此不是"加一个 HTTP 接口"，而是：
**让远程写动作和本地自动恢复走同一条受控路径，并且留下可追溯的证据**。

没有它的具体后果：

- 远程干预不可行，故障响应时间受限于人能多快到机房；
- 手工写节点没有冷却保护，短时间内重复写可能掩盖真实的过热趋势；
- 操作记录只存在于人的记忆和 shell history 里。

### 为什么默认关闭，而且 fail-closed

控制面是本进程**唯一**能触发硬件动作的网络入口，所以它的默认状态必须是"关"：

- 端口选项默认值是 0。只要你不给 `--control-port`，就不会创建任何监听套接字。
- 端口与令牌文件必须成对给出。只给一个，进程**直接以非零状态退出**，
  错误信息是 "control requires port and token file together"。
- 非回环绑定必须配 TLS，否则在创建套接字之前就失败。
- 运行期审计持久化失败也会让进程退出。

这就是 **fail-closed（配置不全就拒绝启动，而不是降级成不安全但能用）**：
一个"以为开了但其实是裸奔"的控制面，比一个明确拒绝启动的控制面危险得多。
非零退出码同时让 systemd 的 `Restart=on-failure` 能按预期工作。

只读 HTTP 用独立端口，它的绑定失败**不影响**继续采样：
可观测性缺失可以接受，控制面边界模糊不可以。

## 二、设计思路

### 令牌放文件，不放命令行

`ps`、`/proc/<pid>/cmdline` 和 systemd journal 都会记录完整的命令行。
把令牌写进 `ExecStart` 等于把它长期公开：任何能执行 `ps` 的用户都能读到。

因此令牌只从文件读（`--control-token-file`），并且这个文件要满足四个条件，
任何一条不满足都直接抛异常——**绝不降级成"无令牌"或宽松模式**：

| 条件 | 原因 |
|---|---|
| 由当前有效用户（`geteuid()`）拥有 | 别人拥有的文件，别人也能改成别的内容 |
| 权限恰为 `0640` | 组可读是为了服务账户组；更宽意味着同机其他用户可以读到令牌 |
| 是普通文件，不是符号链接 | `O_NOFOLLOW` 拒绝末端符号链接，避免令牌被悄悄指向别处 |
| 内容 32~512 个可打印非空格字符 | 太短易被暴力枚举，太长会超出 HTTP 头部上限 |

### 为什么用常数时间比较

普通字符串比较（例如 `==` 或 `memcmp`）在第一个不同的字节处就返回。
攻击者虽然看不到内容，却能测量响应时间：先试 `a...`，再试 `b...`，
耗时更长的那个前缀更可能是对的。逐步逼近就能一次一个字节地猜出令牌。
这叫**计时侧信道**。

**常数时间比较（比较耗时不随内容变化，避免靠时间差猜密码）**的做法是：
不管内容是否相同，都完整扫过服务端令牌的全部字节，
把差异累积到一个变量里，最后一次性判断。长度不同只置位标志、不提前返回，
因此耗时只与服务端令牌长度相关，而长度本身不是秘密。

### 为什么控制请求不能指定文件路径

控制请求体只接受两个字符串字段：`sensor` 和 `action`。
**不接受路径**，也不接受额外字段、重复键、字符串转义。

如果允许客户端传路径，这个接口就等价于"任意文件写入"：
攻击者只要能出示令牌（或令牌被泄漏一次），就能改写系统里任何可写文件。
所以路径必须来自服务端的配置快照——`sensor` 必须存在于当前配置，
风扇动作还要求该传感器配了非空的 `action_path`。
底层写入使用 `O_NOFOLLOW` 拒绝末端符号链接，但那是**最后一道防线**，
不是用来替代"不接受客户端路径"这条规则的。

### 审计闸门：先落盘审计，再执行硬件动作

"闸门"（gate）指一串动作里那个必须先后有序的关卡。控制请求的处理顺序是：

1. 校验令牌（失败先按来源 IP 计数限流）；
2. 匹配路由与动作（`/v1/actions/fan` + `increase_fan`，或
   `/v1/actions/inspect` + `inspect_device`）；
3. 解析请求体并校验 `sensor` 在配置快照里存在；
4. 写一条 `outcome=requested` 的审计记录；
5. 把任务提交给 `Worker`，但任务在真正执行前必须等一个"gate"信号；
6. 主线程根据提交结果写 `outcome=accepted` 或 `outcome=rejected`，
   并把审计刷盘；
7. **刷盘成功之后**才放行任务；任务完成后追加一条带 `detail` 的执行结果审计。

因此硬件动作不可能先于它的审计记录发生。
反过来，如果 `accepted` 这条审计写不出去，任务不会被放行，客户端得到 503，
SEL 里留下 `requested` 但不留 `accepted`——"想动硬件但没动成"这件事本身也有证据。

如果审计在**运行期**持续失败（写日志失败、`fdatasync` 失败），
网络线程会停止监听，主进程以非零状态退出。理由很直接：
一个无法留下审计记录的控制面，比没有控制面更危险。

### 只做三个端点，不做通用 API

| 端点 | 为什么存在 |
|---|---|
| `POST /v1/actions/fan` | 唯一真正改变硬件的动作 |
| `POST /v1/actions/inspect` | 只记录一次检查请求，便于把"人看过了"写进证据历史 |
| `GET /v1/config/generation` | 只读；让自动化能确认 SIGHUP 热重载是否已生效 |

不做通用资源 CRUD、不做配置写入、不做批量动作。
每多一个能写东西的端点，就多一条需要在部署时重新评估的边界。

## 三、部署步骤

### 1. 从源码构建

Ubuntu 24.04：

```sh
git clone git@github.com:aag571/BMC-Lite.git
cd BMC-Lite
sudo apt-get update
sudo apt-get install -y build-essential cmake libssl-dev openssl curl python3
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF -DBMC_TLS=ON
cmake --build build-release --parallel 2
sudo bash deploy/install.sh
```

`BMC_TLS` 默认是 OFF。不启用 TLS 时不需要 OpenSSL，回环明文控制仍然可用；
**远程控制必须启用 TLS**。已有 Release 压缩包只有在打包时启用了 `BMC_TLS`
才能使用 HTTPS：

```sh
sha256sum -c bmc-lite-release.tar.gz.sha256
tar -xzf bmc-lite-release.tar.gz
cd bmc-lite-release
sudo apt-get install -y libssl3t64 openssl curl
sudo bash deploy/install.sh
```

安装脚本会检查动态库是否缺失，并创建 `/opt/bmc-lite/control` 目录，
但**不生成也不覆盖**任何凭证。

### 2. 生成令牌并设置权限

```sh
sudo install -d -o bmc-lite -g bmc-lite -m 0750 /opt/bmc-lite/control
openssl rand -hex 32 > /tmp/bmc-control-token
sudo install -o bmc-lite -g bmc-lite -m 0640 /tmp/bmc-control-token /opt/bmc-lite/control/token
rm /tmp/bmc-control-token
```

要点：

- 令牌文件必须由**实际运行进程的用户**拥有。以 systemd 单元运行时是 `bmc-lite`；
  手动以当前用户运行时，属主就要设成当前用户，否则启动会失败。
- 权限必须**恰好**是 `0640`。测试覆盖了 `0644` 会被拒绝这一条。
- 必须是普通文件，不能是符号链接。
- 内容是至少 32 字节的可打印非空白字符（允许一个结尾换行）。
- 不能用命令行传入令牌。

### 3. 生成 TLS 证书

测试虚拟机 `192.168.124.128` 可以用下面这套自签名证书起步；
把证书作为客户端信任锚，私钥只留在服务器上。正式管理网络应使用内部 CA 签发的证书。

```sh
openssl req -x509 -newkey rsa:2048 -nodes -days 30 \
  -keyout /tmp/bmc-key.pem -out /tmp/bmc-cert.pem \
  -subj /CN=bmc-lite -addext 'subjectAltName=IP:192.168.124.128,DNS:localhost'
sudo install -o bmc-lite -g bmc-lite -m 0600 /tmp/bmc-key.pem /opt/bmc-lite/control/key.pem
sudo install -o root -g bmc-lite -m 0640 /tmp/bmc-cert.pem /opt/bmc-lite/control/cert.pem
rm /tmp/bmc-key.pem
```

把 `cert.pem` 复制到调用客户端，用 `--cacert` 验证证书链与 URL 主机名/IP，
**不要**使用 `curl -k`（它会跳过验证，等于把 TLS 的防护全部关掉）。

这里实现的是"服务器证书 + Bearer 令牌"，**没有实现客户端证书认证（mTLS）**。
证书与令牌都在启动时读取一次，轮换之后需要重启服务。

### 4. 配置 systemd 覆盖

```sh
sudo systemctl edit bmc-lite
```

填写以下覆盖配置。首次测试保留模拟动作，先不加 `--enable-actions`：

```ini
[Service]
ExecStart=
ExecStart=/opt/bmc-lite/bmc-lite --config /opt/bmc-lite/config/hardware.conf --rules /opt/bmc-lite/config/rules.conf --sel /var/log/bmc-lite/sel.db --log /var/log/bmc-lite/faults.jsonl --http-port 8000 --control-port 8443 --control-bind 0.0.0.0 --control-token-file /opt/bmc-lite/control/token --control-tls-cert /opt/bmc-lite/control/cert.pem --control-tls-key /opt/bmc-lite/control/key.pem
ReadOnlyPaths=/opt/bmc-lite/control
```

`ExecStart=` 那行先清空再重设是 systemd 覆盖的固定写法。
`ReadOnlyPaths` 让服务账户能读令牌与证书，但不能改写它们。

```sh
sudo systemctl daemon-reload
sudo systemctl restart bmc-lite
sudo systemctl status bmc-lite --no-pager
sudo journalctl -u bmc-lite -n 50 --no-pager
ss -ltn | grep -E ':8000|:8443'
curl http://127.0.0.1:8000/healthz
```

只读服务仍绑定回环。若确实需要远程只读 HTTP，再加
`--http-bind 0.0.0.0 --http-allow-remote`。

同时启用只读与控制时注意：只读/控制/心跳三种角色**各建一个监听线程**，
控制面最多 8 个并发连接。

### 权限与文件清单

| 对象 | 权限 | 属主 | 说明 |
|---|---|---|---|
| `/opt/bmc-lite/control`（目录） | `0750` | `bmc-lite:bmc-lite` | 只有服务账户与 root 能进入 |
| `token` | `0640` | `bmc-lite:bmc-lite` | 必须恰好 0640，普通文件 |
| `key.pem` | `0600` | `bmc-lite:bmc-lite` | 私钥只留在服务器 |
| `cert.pem` | `0640` | `root:bmc-lite` | 公开部分，可复制给客户端 |

启动失败的常见原因：

| 现象 | 原因 |
|---|---|
| stderr 出现 `control unavailable:` | 令牌文件不是 0640、属主不对、或是符号链接 |
| 同上，报文含 `at least 32 printable non-space characters` | 令牌太短，或含空格/不可打印字符 |
| 同上，报文含 `non-loopback control requires TLS` | 绑了非回环地址但没给证书与私钥 |
| 同上，报文含 `control requires port and token file together` | 只给端口，或只给令牌文件 |
| 日志 `listener unavailable: Address already in use` | 8443 被占用 |

## 四、使用

### 客户端准备

在客户端准备一个权限为 `0600` 的 curl 配置文件，避免令牌出现在命令行里：

```text
header = "Authorization: Bearer 替换为令牌文件内容"
cacert = "/客户端路径/cert.pem"
```

```sh
chmod 0600 control.curl.conf
```

### 三个端点

```sh
curl --config control.curl.conf https://192.168.124.128:8443/v1/config/generation
curl --config control.curl.conf -H 'Content-Type: application/json' \
  --data '{"sensor":"cpu","action":"inspect_device"}' \
  https://192.168.124.128:8443/v1/actions/inspect
curl --config control.curl.conf -H 'Content-Type: application/json' \
  --data '{"sensor":"cpu","action":"increase_fan"}' \
  https://192.168.124.128:8443/v1/actions/fan
```

要点：

- `sensor` 必须是当前配置中存在的 ID；风扇动作还要求该传感器配了 `action_path`。
- 请求体只接受 `sensor`/`action` 两个字符串字段，
  不接受路径、额外字段、重复键或字符串转义。
- 动作路径始终来自配置快照，客户端无法指定。
- **202 只表示已排队，不表示硬件操作已完成。**
- 重复的风扇请求进入同一个恢复引擎，冷却期内不会重复写硬件。
- 默认动作是模拟（只记日志）。真实 PWM 写入需要
  `--enable-actions`，并给服务账户目标节点的写权限。
  风扇动作写入配置指定的 PWM 节点，值为 255。

### 状态码

| 状态码 | 含义 | 客户端该怎么做 |
|---|---|---|
| 200 | 查询成功（`/v1/config/generation`） | 读取响应体里的 `generation` |
| 202 | 已排队，执行结果稍后见审计 | 用 `request_id` 关联后续审计 |
| 400 | 请求体、传感器或动作不合法 | 修正请求，别重试 |
| 401 | 认证失败 | 检查令牌；连续失败会升级为 429 |
| 429 | 该来源 IP 失败次数超限 | 等待约 5 秒再试一次；换源端口无效 |
| 503 | 恢复队列已满，或审计无法持久化 | 稍后重试；若持续出现要查磁盘与 SEL |

关于 429：失败限流是**令牌桶**，桶容量 5、每秒补充 0.2 个令牌。
即连续 5 次失败后，需要约 5 秒才恢复 1 次尝试机会。
来源表满时会淘汰最旧的来源，所以新管理员不会被永久挡在表外。

### 审计记录与 `detail` 的 6 个取值

每条控制请求都会写 SEL，字段固定为
`action`、`sensor`、`outcome`、`peer`、`request_id`：

- `outcome` 取 `requested` / `accepted` / `rejected` / `unauthorized` / `rate-limited`；
- `peer` 是来源 **IP**（不含端口）；
- `request_id` 把同一请求的"验证"与"执行结果"两条记录关联起来；
- 令牌本身**不会**出现在审计里。

因为 202 只代表排队，**判断硬件动作到底成没成，必须看异步结果**。
异步结果写在带 `detail` 的审计记录里，`detail` 一共有 6 个取值：

| `detail` | 含义 | 是否算失败 |
|---|---|---|
| `completed` | 动作执行成功 | 否 |
| `failed` | 动作执行失败（重试后仍未成功） | 是 |
| `cooldown` | 同一（传感器, 动作）在冷却窗口内，本次不重复写硬件 | 是（有意跳过） |
| `already running` | 同一（传感器, 动作）上一次还在执行中 | 是（有意去重） |
| `concurrency limit` | 恢复引擎同时在跑的动作数已达上限 | 是（稍后重试可成） |
| `state capacity` | 恢复状态表已满且无法回收 | 是（需排查是否有异常多的传感器/动作组合） |

注意区分两处含义不同的 `detail`：
上面这 6 个来自恢复执行结果；而网络层的拒绝
（连接超限、解析失败、读超时、对端断开）也会写审计，
它们的 `detail` 是 `connection-limit`、`parse`、`timeout`、`disconnect`。
两者都用同一个字段名，靠 `outcome` 与上下文区分。

查看审计：

```sh
sudo grep 'control' /var/log/bmc-lite/sel.db | tail -20
sudo tail -20 /var/log/bmc-lite/faults.jsonl
```

### 热重载配置

```sh
sudo systemctl kill --kill-whom=main --signal=HUP bmc-lite
curl --config control.curl.conf https://192.168.124.128:8443/v1/config/generation
```

只有传感器与规则配置**全部**验证成功才更新代次与控制快照；
失败的重载保留旧配置。已排队的任务持有请求时的配置值副本，
不保存传感器对象地址，因此重载不会让在途任务读到悬空引用。

## 五、优缺点与适用性

### 优点

- **默认零暴露**：不配置就没有监听套接字，默认部署的攻击面与不用控制面时完全一致。
- **失败即停机**：启动期配置错误、运行期监听失效、审计无法持久化，全都以非零状态退出，
  配合 `Restart=on-failure` 能快速暴露问题而不是带病运行。
- **动作与自动恢复同路**：控制请求经 `Worker` 进入 `RecoveryPolicyEngine`，
  自动继承冷却、去重、并发上限与取值校验，不存在"远程路径更宽松"的情况。
- **审计不可绕过**：先持久化审计再执行动作，且审计里有 `request_id` 可关联验证与执行结果。
- **操作方式对自动化友好**：Bearer 令牌 + 两个 JSON 字段 + `generation` 轮询，
  用 curl 或任意 HTTP 客户端都能驱动。

### 边界与代价

| 边界 | 说明 |
|---|---|
| **未实现 mTLS** | 只做服务器证书 + Bearer 令牌，不要求客户端出示证书。持有令牌即可通过认证 |
| 出站 TLS 只在实例心跳实现 | 控制面是入站；**实例心跳的出站方向已实现 TLS**。上行遥测是明文 TCP |
| 轮换需要重启 | 令牌与证书在启动时读取一次。轮换后必须重启服务，没有在线重载凭证的能力 |
| 令牌本身没有有效期 | 代码里没有令牌过期、吊销或轮换逻辑；这些要由外部流程保证 |
| 控制面串行处理 | `handle()` 全程持锁，8 个连接是上限而不是并发能力。单次请求处理时间决定吞吐 |
| 30 秒冷却由启动代码给定 | `RecoveryPolicyEngine` 的冷却窗口固定为 30 秒，不能按传感器配置 |
| 202 不保证执行成功 | 客户端必须查询审计才能确认结果，不能把 202 当作"已改硬件" |
| SEL 落盘仍受磁盘延迟影响 | 审计用普通文件 + `fdatasync`，慢盘会直接反映为请求变慢或 503 |

### 这套设计为什么适合当前场景

BMC-Lite 的控制面服务对象是**少数几个管理员对同一台机器做低频、后果明确的动作**，
不是多租户 API。在这个前提下：

- 单令牌 + 常数时间比较 + 按 IP 限流，已经足以覆盖"令牌泄漏前的暴力猜解"这一类风险；
- 串行处理换来了"审计顺序与动作顺序严格一致"这一确定性，比吞吐更值钱；
- fail-closed 让"忘记配令牌"变成一次明显的启动失败，而不是一个静默开放的写接口。

如果需求变成"多用户、按角色分权、需要在线吊销凭证"，
那么该上的是完整的身份体系（mTLS + 短期凭证 + 外部 CA），
而不是在现有单令牌方案上继续加开关。
