# 写入路径基准

## 本次 Linux 验收补充

Ubuntu 24.04 / GCC 13 开发虚拟机，最新代码，50000 条。脚本修正 strace -c 的列解析，并只跟踪 write/fdatasync。原脚本错误报告 writes=0；下面数字来自真实调用，不是根据批次推算。

| 场景 | write 次数 | fdatasync 次数 | 被 strace 跟踪的耗时 |
|---|---:|---:|---:|
| Logger 逐条 | 50001 | 0 | 34.87 s |
| Logger 批量 4 KiB | 1277 | 0 | 18.21 s |
| Logger 批量 64 KiB | 82 | 0 | 2.98 s |
| Logger 每条同步 | 50001 | 50000 | 88.09 s |
| SEL 批量 | 1158 | 1157 | 2.34 s |
| SEL 每条重要记录 | 50001 | 50000 | 81.53 s |

write 包含基准程序自身的一次结果输出。strace 会显著改变运行时间，表中时间不能和未跟踪的历史容器数字直接比较。

同一最新二进制不使用 strace，50000 条，默认批次：

| 存储位置 | Logger（无同步） | SEL（批次同步） |
|---|---:|---:|
| 虚拟机 /tmp 文件系统 | 235.18 ms | 1503.31 ms |
| /dev/shm tmpfs | 250.34 ms | 95.36 ms |

SEL 与 Logger 的差距从磁盘上的约 6.4×，变为 tmpfs 上约 0.38×。结合每批 fdatasync 的计数，主要差异是存储同步延迟；过去的约 18× 不是固定算法开销，不能跨机器照搬。保留重要证据的同步策略，不为了基准数字关掉持久化。

以下为早期基准记录，环境和计数口径与上表不同。

日志（`Logger`）与 SEL（`SelStore`）都改成了"常驻描述符 + 批量合并写入"。这里记录量化结果与结论，
以及一个重要的反直觉发现：**批量的收益是系统调用次数，不是这类快速存储上的吞吐。**

## 怎么跑

```sh
bash tools/bench-writes.sh 100000
```

脚本会构建 `bench-writes` 目标，逐场景运行，并在系统装了 `strace` 时用 `strace -c` 统计
`write` / `fdatasync` 的实际调用次数。没有 `strace` 时会退化为只报告吞吐，并明确标注。

也可以在测试里看到同一组对照（`bmc_tests --gtest_filter='*'` 中的 `[Bench]` 段落）：

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build --parallel 2
./build/bmc_tests --gtest_filter='Sel.*:Logger.*'
```

## 结果（50000 条记录，容器内 ext4/overlayfs，Release -O2）

| 场景 | 耗时 | 每条 | 说明 |
|---|---|---|---|
| 对照（只拼字符串，无 I/O） | 46 ms | 0.9 µs | 字符串与容器开销的下限 |
| `Logger` 逐条写入（batch=1，等价改造前） | 515 ms | 10.3 µs | 每条一次 `write` |
| `Logger` 批量（batch=4096） | 385 ms | 7.7 µs | **吞吐 1.34×**，`write` 次数约 50000 → 约 714 |
| `Logger` 批量（batch=65536） | 871 ms | 17.4 µs | 批次过大反而更慢（内存搬运主导） |
| `SelStore` 批量（默认 4096） | 853 ms | 17.1 µs | 与日志同量级 |
| `SelStore` 关键记录（每条 `write+fdatasync`） | 3217 ms | 64.3 µs | **比批量慢 3.8×** |

## 结论

1. **批量合并把系统调用的数量降了一个多数量级**：50000 条记录从 50000 次 `write` 降到约 714 次。
   这是确定性的收益，与机器无关，可用 `strace` 复核。
2. **吞吐只提升约 1.34×**，因为这里的写入落到页缓存，`write` 本身已经很快；
   实测每次一批大 `write` 与多次小 `write` 的差距有限。不要指望批量能把吞吐提高数倍。
3. **真正的代价在 fsync，不在 write**：SEL 对状态迁移/恢复这类关键证据每条都 `write+fdatasync`，
   实测比批量慢 3.8×。这个取舍是有意的——故障证据必须落盘；普通采样记录则不付这个代价。
4. **批次阈值不是越大越好**：阈值调到 64 KiB 时吞吐反而下降（缓冲区增长与内存搬运成为主导）。
   默认 4096 字节是一个合理的折中。

## 一个方法学教训

第一版基准把 `SelStore` 放在堆上（`new SelStore(...)`）并通过指针调用 `append`，
结果测出 SEL 比日志慢约 30 倍。改用栈对象后该差异消失——**指针间接会阻止 `append` 被内联**，
指针版本测到的是未内联的调用开销，而不是被测量代码的真实成本。
基准工具因此改为在栈上构造被测量对象。

另外，远程编译服务会对相同源码返回缓存的执行结果（可通过在源码里放一个随机常量验证），
所以本文件中的数字取自本地 `ctest`/`bmc_tests` 的运行，而不是远程结果。
