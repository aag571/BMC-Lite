# 写入路径性能基准

**这份文档回答什么**：日志（Logger）与事件档案（SEL）的写入路径值不值得优化；
「批量合并写入」到底省下了什么、代价在哪里；以及这些基准数字该怎么读、不能怎么读。

**适合谁读**：需要调整 `batch_bytes`、`sync` 这类写入策略的人，以及第一次打开
`tools/bench-writes.sh`、`tools/bench_writes.cpp` 的开发者。`strace`、系统调用、
`fdatasync` 等术语在第一次出现时都会解释。

**本文的事实来源**：`tools/bench-writes.sh`、`tools/bench_writes.cpp`、
`src/logger.cpp`、`src/sel.cpp`、`include/bmc/core.hpp`。表格中的数字取自既有实测
记录，本文只重排版并补充解释，**不改动任何数值**。

## 一、为什么需要基准

**一句话**：日志和事件档案在故障时是证据，所以写入路径关心的首先是「证据有没有
完整落盘」，其次才是「写得快不快」；而衡量它的可靠指标是系统调用次数。

### 1.1 两条写入路径

| 组件 | 写什么 | 默认策略 |
|---|---|---|
| `Logger` | 滚动日志文件 | 批量合并；默认不 `fsync` |
| `SelStore` | SEL 事件档案 | 批量合并；关键记录立即落盘 |

SEL 是 System Event Log（系统事件日志）的缩写，在本项目里专门记录传感器状态迁移
与恢复动作这类「故障证据」。为什么这两条路径要单独做基准：故障现场最有价值的
东西就是「故障发生前后的记录是否完整」，如果写入策略为了跑分把关键记录丢掉，
事后诊断就失去了依据。

### 1.2 为什么系统调用次数比吞吐更值得优化

一次 `write`（把数据交给内核）或 `fdatasync`（要求内核把数据真正写进存储）
都是一次**系统调用**：程序要从用户态陷入内核态，内核再做参数检查、文件描述符
查表、缓冲区处理。这部分成本与「写多少数据」关系不大，而与「调用多少次」成正比。

| 指标 | 特点 | 是否适合作为结论 |
|---|---|---|
| 吞吐（条/秒）、墙钟时间 | 受机器负载、页缓存、磁盘型号影响，换台机器就变 | 参考 |
| 系统调用次数 | 由代码逻辑决定（批次阈值、同步策略），可用工具数出来 | 结论 |

`bench_writes.cpp` 的文件头注释也说明了同样的取舍：重点关注 `write` / `fdatasync`
的次数，而不是易受机器负载影响的墙钟时间。**批量合并的意义主要是把调用次数降下来**，
这一点与机器无关，可以在任何环境复核。

### 1.3 三个术语

- **页缓存**：内核用来缓存文件内容的内存。`write` 成功通常只表示数据进了页缓存，
  并不表示已经落到存储介质上。
- **`fdatasync` / `fsync`**：把数据（`fsync` 还包括元数据）真正刷到存储介质。
  它是「证据是否安全」的关键，也是写入路径里最慢的一步。
- **`strace`**：Linux 上跟踪进程系统调用的工具，`-c` 表示只输出汇总统计
  （每个系统调用被调用多少次）。

## 二、设计思路

**一句话**：用 `strace` 数真实发生过的系统调用，而不是用公式推算；同时让六个场景
两两对照，把「批次大小」「是否同步」这两个变量的影响分开看。

### 2.1 怎么测才可信

| 做法 | 为什么 |
|---|---|
| 用 `strace -c` 数真实调用 | 计数来自内核记录，不是推算；估算会漏掉 `flush`、轮转与自身输出 |
| 只跟踪 `write` / `fdatasync` | 其它系统调用与写入路径无关，只会稀释结果 |
| `-f` 跟踪子进程 | 避免漏掉进程创建的线程/子进程里的写入 |
| 解析汇总表的第 4 列 | 脚本按行末字段匹配 `write` / `fdatasync`，匹配不到用 `0` 兜底 |
| 没有 `strace` 时退化为只测吞吐 | 并在同一列位置标注 `(no strace)`，避免与 syscall 计数混淆 |

早期版本的脚本曾错误报告 `writes=0`：原因是汇总表的列解析写错了。修正后数字来自
真实调用。这说明「计数口径本身也要被验证」——一个永远返回 0 的计数器比没有计数器
更危险。

### 2.2 六个场景分别对照什么

`tools/bench-writes.sh` 固定跑六个场景：

| 场景 | 参数 | 对照的问题 |
|---|---|---|
| `logger-per-record` | `--mode logger --batch 1` | 改造前的逐条写入基线 |
| `logger-batch-4k` | `--mode logger --batch 4096` | 默认批次阈值的效果 |
| `logger-batch-64k` | `--mode logger --batch 65536` | 批次是不是越大越好 |
| `logger-sync-per-rec` | `--mode logger --batch 4096 --sync` | 给每条记录加同步的代价 |
| `sel-batched` | `--mode sel` | SEL 默认批量 |
| `sel-important` | `--mode sel --important` | 关键证据每条立即落盘的代价 |

对照关系是刻意设计的：`per-record` 对 `batch-4k` 回答「批量值不值」，
`batch-4k` 对 `batch-64k` 回答「批次多大合适」，`batch-4k` 对 `sync-per-rec`
回答「同步才是真正的代价吗」。

### 2.3 被测量对象为什么必须在栈上构造

`bench_writes.cpp` 里被测量的对象是栈对象，而不是 `new` 出来的：

```cpp
bmc::SelStore sel(path, 1000000);   // 栈对象，不是 new SelStore(...)
```

原因与 C++ 的**内联**有关：编译器只有在看得见具体类型时，才可能把 `append` 这类
小函数的函数体直接嵌进调用处；通过指针调用时，编译器无法确定实际类型（也可能是
另一个翻译单元里的实现），通常就不内联。于是一个「用指针调用」的基准测到的是
**未内联的调用开销**，而不是被测量代码的真实成本。

早期版本的基准把 `SelStore` 放在堆上并通过指针调用 `append`，结果测出 SEL 比日志
慢约 30 倍；改用栈对象后这个差异消失。这条对比记录来自早期文档，**当前代码已经是
栈对象，无法再从现有代码复现当时的指针版本**，因此它只能作为方法学教训来读。

### 2.4 计数与口径上的已知偏差

- `write` 次数**包含基准程序输出结果的那一次** `write`，所以逐条写入场景是 50001
  而不是 50000。
- `Logger` 的 `--sync` 与 `SelStore` 的「每条重要记录」都走 `fdatasync`
  （`src/logger.cpp`、`src/sel.cpp`），因此这两个场景的 `fdatasync` 计数是 50000。
- `strace` 会显著改变运行时间（每次系统调用都要停下来记录），所以**被跟踪的耗时**
  不能和未跟踪的数字直接比较。

## 三、具体实现

**一句话**：一条脚本命令跑完全部六个场景，数据用 `key=value` 输出，便于脚本汇总。

### 3.1 怎么跑

```sh
bash tools/bench-writes.sh 50000
```

脚本行为（`tools/bench-writes.sh`）：默认记录数 100000；`BUILD_DIR` 可覆盖构建目录
（默认 `build-bench`）；自行以 `Release`、`BUILD_TESTING=OFF` 配置并只构建
`bench-writes` 目标；每个场景用独立子目录，退出时整体删除临时目录。

也可以直接跑二进制，便于用 `--rounds` 观察抖动：

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 2 --target bench-writes
./build/bench-writes --mode both --records 50000 --batch 4096 --dir var/bench
```

参数一览（`bench_writes.cpp`）：

| 参数 | 默认值 | 作用 |
|---|---|---|
| `--mode` | `both` | `logger` / `sel` / `both` |
| `--dir` | `var/bench` | 数据目录 |
| `--records` | `100000` | 记录条数 |
| `--batch` | `4096` | Logger 的批次字节阈值 |
| `--sync` | 关 | Logger 每条记录后 `fdatasync` |
| `--important` | 关 | SEL 每条记录按关键证据处理：`write + fdatasync` |
| `--rounds` | `1` | 重复轮数，用于判断差异是否稳定 |

每条记录由 `payload()` 生成：`entry-<序号>` 加 40 个 `x`，约 52 字节
（代码注释写作「约 60 字节」，量级一致）。每个场景输出一行可解析的键值对，
脚本把它压成一行显示。

批量语义本身另有单元测试，但**不是性能数字**：`-DBUILD_TESTING=ON` 构建出的
`bmc_tests` 里，`Sel.*` 与 `Logger.*` 用例验证「达到批次阈值才落盘」「每条记录同步」
等行为。基准场景只存在于独立的 `bench-writes` 目标中，`bmc_tests` 里**没有**
`[Bench]` 段落。

### 3.2 表 A：`strace` 统计的真实系统调用（50000 条）

环境：Ubuntu 24.04 / GCC 13 开发虚拟机，最新代码。脚本修正了 `strace -c` 的列解析，
并且只跟踪 `write` / `fdatasync`。

| 场景 | write 次数 | fdatasync 次数 | 被 strace 跟踪的耗时 |
|---|---:|---:|---:|
| Logger 逐条 | 50001 | 0 | 34.87 s |
| Logger 批量 4 KiB | 1277 | 0 | 18.21 s |
| Logger 批量 64 KiB | 82 | 0 | 2.98 s |
| Logger 每条同步 | 50001 | 50000 | 88.09 s |
| SEL 批量 | 1158 | 1157 | 2.34 s |
| SEL 每条重要记录 | 50001 | 50000 | 81.53 s |

`write` 包含基准程序自身的一次结果输出。这张表的价值在左边两列——它们是算法决定的
确定性数字；右边的时间列只说明「在被跟踪的情况下」发生了什么。

### 3.3 表 B：同一二进制不挂 `strace`（50000 条，默认批次）

| 存储位置 | Logger（无同步） | SEL（批次同步） |
|---|---:|---:|
| 虚拟机 `/tmp` 文件系统 | 235.18 ms | 1503.31 ms |
| `/dev/shm` tmpfs | 250.34 ms | 95.36 ms |

SEL 与 Logger 的差距从磁盘上的约 6.4× 变为 tmpfs 上的约 0.38×（即反超）。
既有记录把主要差异归因于存储同步延迟：SEL 每批都要 `fdatasync`，在真实磁盘上
这个等待很贵，在 tmpfs 上几乎免费。过去的约 18× 差距不是固定算法开销，
**不能跨机器照搬**。保留重要证据的同步策略，不为了基准数字关掉持久化。

### 3.4 表 C：早期基准记录（50000 条，容器内 ext4/overlayfs，Release -O2）

| 场景 | 耗时 | 每条 | 说明 |
|---|---:|---:|---|
| 对照（只拼字符串，无 I/O） | 46 ms | 0.9 µs | 字符串与容器开销的下限 |
| Logger 逐条（batch=1） | 515 ms | 10.3 µs | 每条一次 `write` |
| Logger 批量（batch=4096） | 385 ms | 7.7 µs | **吞吐 1.34×**，`write` 约 50000 → 约 714 |
| Logger 批量（batch=65536） | 871 ms | 17.4 µs | 批次过大反而更慢（内存搬运主导） |
| SEL 批量（默认 4096） | 853 ms | 17.1 µs | 与日志同量级 |
| SEL 关键记录（每条 `write+fdatasync`） | 3217 ms | 64.3 µs | **比批量慢 3.8×** |

### 3.5 怎么读这三张表

三张表的环境与计数口径不同，只能各自内部比较，不能混用：

| 表 | 能回答 | 不能回答 |
|---|---|---|
| A | 每种策略的真实系统调用次数 | 真实吞吐（被 `strace` 放大了） |
| B | 存储位置（磁盘/tmpfs）对墙钟的影响 | 系统调用次数 |
| C | 批次阈值对吞吐的影响 | 跨机器复现（容器 + overlayfs） |

一个容易看错的地方：表 A 里 64 KiB 批次的跟踪耗时最短（2.98 s），看起来与「批次
越大越慢」矛盾。原因是**这两句话回答的是不同问题**——表 A 的耗时被系统调用次数
主导（82 次 vs 1277 次），而「64 KiB 更慢」来自表 C 里不挂 `strace` 时的内存搬运
开销。读基准时先确认「这个数字是在什么条件下测的」，再看结论。

## 四、结论与取舍

**一句话**：批量合并把系统调用数量降了一个数量级，但它救不了同步的成本；
真正的取舍发生在「要不要为每条证据等一次落盘」。

1. **批量合并把系统调用数量降了一个多数量级**：50000 条记录从 50000 次 `write`
   降到数百至一千余次（早期记录约 714 次；表 A 的 4 KiB 批次为 1277 次）。
   这是确定性的收益，与机器无关，可用 `strace` 复核。
2. **吞吐只提升约 1.34×**（515 ms → 385 ms）：因为写入落到页缓存，`write` 本身
   已经很快；一次大 `write` 与多次小 `write` 的差距有限。不要指望批量能把吞吐
   提高数倍。
3. **真正的代价在同步，不在 `write`**：SEL 对状态迁移/恢复这类关键证据每条都
   `write + fdatasync`，实测比批量慢 3.8×。这个取舍是有意的——故障证据必须落盘，
   普通采样记录则不付这个代价。
4. **批次阈值不是越大越好**：阈值调到 64 KiB 时吞吐反而下降（871 ms vs 385 ms，
   缓冲区增长与内存搬运成为主导）。默认 4096 字节是一个合理的折中。
5. **跨存储位置的比较要在同一存储上做**：SEL 与 Logger 的差距在磁盘上约 6.4×，
   在 tmpfs 上约 0.38×。这说明差异主要来自同步延迟而不是算法开销。

## 五、优缺点与适用性

**一句话**：这套方法的优点是结论可复核，局限是它测的是「系统调用的形状」，
不是「真实硬件上的性能」。

### 5.1 优点

1. **可复核**：系统调用次数可以用 `strace` 在任何环境重新数一遍，不依赖绝对时间。
2. **口径明确**：只跟踪 `write` / `fdatasync`，脚本自建临时目录并自动清理，
   没有 `strace` 时明确标注退化。
3. **变量分离**：六个场景把「批次大小」「是否同步」拆开对照，避免把两个因素
   混成一个结论。
4. **拒绝自欺**：明确写出 `write` 计数含程序自身的输出、`strace` 会改变耗时，
   以及指针间接会污染测量，这些都会影响读者对数字的解读。

### 5.2 局限与边界

| 局限 | 说明 |
|---|---|
| `strace` 显著改变耗时 | 每次系统调用都要记录，被跟踪的时间不能当作真实吞吐 |
| 不能跨机器照搬 | 磁盘型号、文件系统、虚拟化层都会改变数字 |
| 虚拟机数字不代表真实硬盘 | `/tmp` 与 `tmpfs` 都可能被宿主缓存；真实掉电行为无法在 VM 中验证 |
| 单次运行没有统计显著性 | 共享环境的抖动可能很大，需要 `--rounds` 多跑几轮 |
| 只覆盖写入路径 | 读取、轮转、SEL 压缩等路径不在同一套基准里 |
| 记录长度固定 | `payload()` 生成的记录长度固定，真实日志长度分布不同 |

### 5.3 这些数字来自哪次运行

诚实说明如下，读者引用数字前请先确认环境：

- **表 A** 来自 Ubuntu 24.04 / GCC 13 开发虚拟机、50000 条记录、最新代码、
  修正列解析后的 `bash tools/bench-writes.sh 50000` 运行。
- **表 B** 来自「同一最新二进制不挂 `strace`」的运行，50000 条、默认批次，
  分别落在虚拟机 `/tmp` 文件系统与 `/dev/shm` tmpfs 上。既有记录**没有留存**
  每次运行对应的具体存储位置与挂载参数。
- **表 C** 来自更早的一次运行：容器内 ext4/overlayfs、`Release -O2`、50000 条，
  环境和计数口径都与表 A 不同，因此不能与表 A 并列比较。
- **需要读者注意的一处不一致**：表 A 里 SEL 批量（2.34 s）比 Logger 批量 4 KiB
  （18.21 s）快，而表 B 里同一二进制在 `/tmp` 上 SEL（1503.31 ms）比 Logger
  （235.18 ms）慢。既有记录把差异归因于存储同步延迟，但没有留存每次运行的完整
  条件，因此本文**不给出更强的解释**，也不据此修改任何写入策略。
- **环境不同数字会变**：以上所有时间都只在对应环境下有意义；只有 `write` /
  `fdatasync` 的**次数**是可跨环境复核的量。
