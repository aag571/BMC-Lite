# Uplink telemetry installation and use

One-line summary: this document answers "how do I ship this host's hardware
events to an external collector for central analysis without ever slowing
sampling down?". It is written for operators integrating the daemon with a
monitoring platform and for developers changing `src/uplink.cpp`.

Five terms first:

- **Uplink telemetry**: the read-only stream of events this daemon sends out.
- **Collector**: the external receiver, usually your log platform or a small
  script.
- **JSONL**: one complete JSON object per line, terminated by a newline. It is
  not an array and it cannot span lines.
- **Bounded queue**: a waiting queue with a hard capacity; what happens when it
  is full is explicit. Here the oldest entry is dropped.
- **Exponential backoff**: after a failure the wait doubles each time, which
  prevents a reconnect storm.

## 1. Why it is needed

Sampling on a single host has limited value. Critical temperatures, service
degradation and recovery actions only become useful once they are collected in
one place for trending, cross-host comparison and central alerting. Without an
uplink you must log into each machine and read local logs and SEL, so
diagnosis is as slow as the inspection cycle.

But uplink has one **primary constraint: it must not affect sampling**. The
first duty of this process is to read sensors, evaluate thresholds and run
hardware recovery actions; telemetry is an add-on. A slow collector, a hung
collector or no collector at all must never stall sampling, drop ticks or
delay an action. Most design decisions in this document follow directly from
that constraint.

## 2. Design

**Core goal**: assume the collector may become unavailable at any moment. Queue
events, deliver as many as possible, and keep the sampling path completely
decoupled from that work.

The key trade-offs:

- **`enqueue` only queues; it performs no network I/O**: `enqueue` runs on the
  EventBus dispatch thread and does exactly three things - limit length, encode,
  push into the queue. Connecting, sending and reconnecting are driven by the
  uplink thread. As long as enqueue never blocks, an arbitrarily slow collector
  cannot affect sampling.
- **When the queue is full the oldest event is dropped instead of blocking the
  producer**: capacity is fixed (1..4096, default 256). On overflow the front
  entry, which is the oldest, is popped before the new one is pushed. Telemetry
  is a "current state" channel, so the newest state is worth more than history.
  Blocking the producer would let the collector set the sampling pace and break
  the primary constraint.
- **A half-sent frame is dropped on disconnect**: a new TCP stream cannot resume
  in the middle of a JSON line. Continuing would leave the collector with a
  truncated line followed by the start of the next one, which is unparseable.
  On disconnect the in-flight frame is therefore discarded, and collectors
  should discard any unterminated fragment before EOF.
- **Exponential reconnect backoff**: it starts at 250 ms, doubles up to a 30
  second ceiling, and resets only after a complete message was delivered to the
  socket. A collector restart or a network outage therefore causes no
  once-per-second reconnect storm, yet recovery stays fast.

Alternatives that were considered and rejected:

| Alternative | Why it was rejected |
|---|---|
| Send synchronously inside the EventBus callback | Blocks the sampling path outright |
| Unbounded queue | Unbounded memory; a long outage can exhaust the process |
| Block or spin when the queue is full | Again lets the collector set the sampling pace |
| Disk queue with replay | Adds persistence and disk I/O; disk-full is a new failure |
| Resume a half-sent frame | Breaks JSONL line integrity, so collectors cannot parse it |

Local evidence is kept by SEL, so uplink does not need a second offline queue.

## 3. Implementation

### 3.1 Options and value ranges

| Option | Meaning | Range |
|---|---|---|
| `--uplink-address` | Collector IPv4 address | IPv4 literal, no DNS |
| `--uplink-port` | Collector TCP port | 1..65535 |
| `--uplink-capacity` | Waiting queue capacity | 1..4096, default 256 |

Address and port must be given together; supplying only one fails during option
parsing. A non-literal address, an out-of-range port or an out-of-range
capacity makes startup fail rather than degrade silently. The feature is off by
default: without an address no thread and no connection are created.

### 3.2 JSONL fields

```json
{"type": "sensor_state", "source": "cpu", "message": "critical", "sequence": 12, "time_ms": 1728000000000, "value": 95}
```

| Field | Meaning |
|---|---|
| `type` | Event type, see below |
| `source` | Originating subsystem, e.g. `cpu`, `control`, `peer` |
| `message` | Human-readable event description |
| `sequence` | Process-local EventBus sequence, restarts with the process |
| `time_ms` | Unix millisecond timestamp taken when the line was encoded |
| `value` | Numeric payload; `null` when absent or not finite |

The four event types:

| `type` | When it is produced |
|---|---|
| `sensor_state` | A sensor state crosses a threshold (entering or leaving critical) |
| `configuration` | A hot reload was accepted or rejected |
| `service` | Service lifecycle events such as startup and shutdown |
| `recovery` | Scheduling and outcome of recovery actions |

Only state transitions and business events are sent, not every raw sample, so
this is not a complete data-recording channel. Newlines and quotes inside
strings are JSON-escaped, so a record always occupies exactly one line;
collectors must frame by newline and must not treat one `recv` as one message.

### 3.3 Per-record limits and memory bounds

| Limit | Value | Behaviour when exceeded |
|---|---|---|
| Raw `source` + `message` | 4 KiB combined | Rejected and counted in `dropped` |
| Encoded single line | 8 KiB | Rejected instead of truncated |
| Waiting queue | `--uplink-capacity` entries | Oldest entry dropped and counted |
| In-flight message | At most 1 | Dropped and counted when the link breaks |

Buffer memory per instance is therefore bounded by approximately
`(capacity + 1) x 8 KiB`, plus a small object overhead.

### 3.4 Connection management and reconnect

- Connect, send and disconnect detection are all nonblocking: `EAGAIN` only
  means no progress this round.
- Connect and first send share one 5 second absolute deadline; sending each
  message also has a 5 second deadline, so a slow peer cannot occupy a frame
  forever.
- When the queue is empty the thread still uses `MSG_PEEK` to detect a peer
  FIN/RST, so a closed collector is noticed and reconnected without waiting for
  the next event.
- Reconnect backoff starts at 250 ms, doubles, and is capped at 30 seconds; it
  resets only after a complete message was sent.
- The network thread runs on a 20 ms cycle and sends at most 16 fragments per
  round, so its network work per round is bounded.

### 3.5 Delivery semantics (read this section before relying on the data)

| Item | Fact |
|---|---|
| Acknowledgement | None; the collector sends nothing back |
| Durable queue | None; only the bounded in-memory queue |
| Replay after disconnect | None; the in-flight frame is dropped |
| Meaning of `sent` | The complete message was handed to the **local socket** |
| Does it mean the collector stored it? | No, and not that the collector received it |
| Protocol direction | One-way; collector data counts as out-of-protocol and forces a reconnect |

In other words, this is best-effort telemetry. Gaps in `sequence` are expected
and can come from queue overflow, oversized events or a dropped frame after a
disconnect. Collectors should read a gap as "data was lost", not as an error.

At shutdown, unsent telemetry is counted in `dropped`; the daemon never waits
for an offline collector.

### 3.6 Metrics

When uplink and read-only HTTP are both enabled, `/metrics` adds:

| Metric | Meaning |
|---|---|
| `bmc_uplink_queued` | Waiting frames, excluding one in-flight frame |
| `bmc_uplink_dropped_total` | Overflow, oversized, failed/timed-out and shutdown drops |
| `bmc_uplink_sent_total` | Complete frames handed to the local socket |
| `bmc_uplink_bytes_total` | Bytes sent, including partial failed frames |
| `bmc_uplink_connect_attempts_total` | Connection attempts |
| `bmc_uplink_connected` | Last observed connection state, 1/0 |

### 3.7 Demonstration collector and startup

On a demonstration collector:

```sh
sudo apt-get install -y netcat-openbsd
nc -lk 9000 | tee telemetry.jsonl
```

On the daemon host (replace 127.0.0.1 with the collector IPv4 for separate
hosts):

```sh
./build-release/bmc-lite --config config/mock.conf --rules config/rules.conf \
  --sel var/sel.db --log var/faults.jsonl --http-port 8000 \
  --uplink-address 127.0.0.1 --uplink-port 9000 --uplink-capacity 256
curl http://127.0.0.1:8000/healthz
curl http://127.0.0.1:8000/metrics | grep bmc_uplink
```

### 3.8 systemd deployment

Append the following to the existing `ExecStart` line, then restart the
service:

```text
--uplink-address COLLECTOR_IP --uplink-port 9000 --uplink-capacity 256
```

```sh
sudo systemctl daemon-reload
sudo systemctl restart bmc-lite
sudo journalctl -u bmc-lite -n 50 --no-pager
```

Source and release installation follow README.en.md; this feature adds no
library dependencies. The existing TLS build option applies to control HTTPS
only, so uplink is plaintext TCP today and belongs on a trusted network or
inside a tunnel.

### 3.9 Shutdown order

Shutdown stops inbound requests, stops Worker, drains the EventBus, and only
then stops the uplink thread. The reason for that order is that all
asynchronous writes finish before statistics are read and buffers are flushed,
so local fault evidence in SEL survives an offline collector. Unsent telemetry
is counted in `dropped` and never delays exit.

### 3.10 Self-test

```sh
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build -R 'Uplink|uplink_runtime' --output-on-failure
```

The C++ `FakeSocketIo` tests cover partial sends with `EAGAIN`, queue bounds
after 50,000 enqueues, connect and send deadlines, exponential backoff, idle
disconnects, and one valid JSON line per event type. The real TCP integration
test covers a missing collector, a collector that stops reading, reconnection,
JSONL framing and continued sampling progress.

## 4. Strengths, costs and applicability

**Strengths**

- Zero impact on sampling: with a missing or stalled collector the `samples`
  counter in `/healthz` keeps growing and queue depth stays bounded.
- Bounded, predictable memory: both queue capacity and per-record size are hard
  limits.
- Automatic reconnect: a restarted collector needs no manual intervention, and
  backoff prevents a reconnect storm.
- No extra dependencies: installation is identical to the main program.

**Costs and limits**

- **Plaintext TCP**: the TLS option covers control HTTPS only, so cross-host
  deployment belongs on a trusted network or inside a tunnel (VPN, SSH tunnel,
  WireGuard and similar).
- **No ACK, no disk queue, no replay**: unsuitable for auditing, billing or
  compliance retention; use SEL and a central log system for those.
- **IPv4 literals only**: DNS is not supported, which avoids a startup
  dependency on name resolution and keeps the destination identity fixed.
- **One collector only**, with no fan-out and no failover.
- **Overflow drops the oldest entry**, so bursts lose middle events and
  `sequence` gaps are normal.
- **Frames can be lost**, so collectors must detect loss from incomplete lines
  and from `sequence` gaps.
- Only transitions and business events are sent; there is no full raw sample
  history.

**Why this fits the project**

The target platform is a single-machine hardware monitoring daemon, often
without a log agent installed. One dedicated thread, one bounded queue and one
plaintext TCP connection are enough for central analysis, while the risk of
affecting sampling is structurally zero. Heavier reliability (disk queues,
ACKs, replay) belongs to a dedicated collection or logging system, not to the
hardware protection path.
