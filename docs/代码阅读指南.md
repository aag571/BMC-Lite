# 代码阅读指南

这份文档给"要读源码的人"一张地图，回答的是**"`src/` 有 27 个源文件、`include/bmc/` 有 15 个头文件，
从哪读起"**。它不讲怎么部署、也不当 API 手册，只讲阅读顺序、每个文件的职责，以及两个最常见的困惑。

适合谁读：第一次接触本项目的开发者、要改动某个子系统的人、需要评估改动影响面的评审者。

## 一、建议阅读顺序

下面的五阶段顺序本身就是**知识依赖的顺序**：先概念、再纯逻辑、再硬件、再编排、最后基础设施。
每一阶段都可以独立停下来读懂，不必先理解后面的内容。

### 阶段 1：先建立领域概念 —— `include/bmc/core.hpp`

`core.hpp` 是本项目的**公共声明入口**：设备与状态机、配置与标定、事件总线、故障规则、SEL 与日志、
恢复策略、Worker 的声明几乎都在这里。先读它，是因为后面每个 `.cpp` 都在回答同一个问题——
"`core.hpp` 里那个类到底是怎么实现的"。

**为什么故意不拆分**：把它拆成十几个头文件看起来更整齐，但会立刻引入大量互相包含
（`Engine` 需要 `Config`，`FaultRuleEngine` 需要 `Event`，`Monitor` 需要几乎全部类型）。
当前选择是保留单一入口，让"某个类在哪声明"永远有唯一答案；代价是这个文件偏长。
这是一个**有意的取舍**，不是没整理。

### 阶段 2：再读纯逻辑（不碰硬件）

顺序：`src/engine.cpp` → `src/calibration.cpp` → `src/config.cpp` → `src/rules.cpp`

**目的**：先把"判断"读懂，再去看"取值"和"动作"。这四份文件不打开任何设备、不做网络 I/O，
因此最容易读懂、也最容易被单元测试单独驱动：

- `engine.cpp`：单路传感器的判级状态机——阈值判定 + **迟滞**（恢复阈值与告警阈值不同，
  避免在临界值附近来回抖动）+ **去抖**（连续 N 次命中才算数）+ 读失败累进到 `unavailable`。
- `calibration.cpp`：原始读数到工程值的换算，先 `gain`/`offset` 线性修正，再按校准点做分段线性插值。
- `config.cpp`：传感器配置文件解析与校验，把所有策略错误挡在启动阶段。
- `rules.cpp`：规则文件的解析、确认状态机，以及一轮采样后如何裁剪状态。

### 阶段 3：然后读硬件层

顺序：`src/readers.cpp` → `src/chips.cpp`

**目的**：理解"一个读数值是从哪来的"。这里会第一次遇到 **`LinuxIo` 注入层**
（`include/bmc/linux_io.hpp`）：把 `open`/`ioctl`/`read`/`write`/`close` 收敛成一个可替换接口，
生产环境用 `PosixLinuxIo` 直通真实系统调用，测试用 `tests/core_test.cpp` 里的 `FakeLinuxIo`
脚本化返回值。有了它，I2C 寄存器解码、能力位拒绝、PWM 写入失败这些分支不必插真实硬件就能测。

- `readers.cpp`：`mock` / `sysfs` / 原始 `i2c` / `gpio` 四种读取后端，以及设备注册。
- `chips.cpp`：I2C/SMBus 总线封装与专用芯片驱动（`lm75`/`lm75b`、`adm1275`、`emc2103`、
  `ina219`/`ina226`）。寄存器换算依据见 [芯片驱动与标定](芯片驱动与标定.md)。

### 阶段 4：然后读编排

顺序：`src/monitor.cpp` → `src/main.cpp`

**目的**：把前面所有零件拼成一条流水线，并看清"业务编排"与"进程生命周期"是分开的。

- `monitor.cpp`：一轮采样的业务顺序——取值 → 状态迁移 → 日志/SEL/总线 → 规则判定 → 提交恢复 →
  降级上报。它**不认识** epoll、timerfd 或信号，依赖全部由 `main.cpp` 注入；`Monitor` 本身也
  不持有传感器，唯一自身状态是降级上报的节流游标。
- `main.cpp`：进程唯一负责生命周期的地方——信号掩码与 `signalfd`、`epoll` 主循环、SIGHUP 热重载，
  以及按固定顺序停机刷盘（顺序原因见第三节）。

### 阶段 5：最后读基础设施与网络

顺序：`src/worker.cpp`、`src/recovery.cpp`、`src/event_bus.cpp`、`src/logger.cpp`、`src/sel.cpp`、
`src/socket_io.cpp`、`src/http.cpp`、`src/network.cpp`、`src/control.cpp`、`src/uplink.cpp`、
`src/peer.cpp`

**目的**：这些是"被业务使用"的部件，放在最后读不会打断主线的理解。
其中 `logger.cpp` 与 `sel.cpp` 涉及落盘策略与降级，细节见 [运行时可靠性说明](运行时可靠性说明.md)；
TCP/TLS 部分见 [网络设计说明](网络设计说明.md)。

## 三、两个初学者常见困惑

### 1. 为什么同时有"采样快照"和"状态事件"两种数据？

规则确认需要**每一个采样周期**的状态，否则"连续 3 次 critical"这类规则永远无法触发：
如果只在状态迁移时产生事件，那么一直停在 critical 的传感器就不会再产生事件，
计数也就停在 1，`confirmations > 1` 的规则永远不会激活。

所以 `Monitor::poll` 每一轮都会构造一个事件：

- 有迁移时用迁移事件（`before`/`after` 不同）；
- 没有迁移时造一个"当前状态"事件（`before == after`）。

两者的下游用途不同：

| 数据 | 下游用途 |
|---|---|
| 每次采样的状态快照 | 喂给 `FaultRuleEngine::evaluate`，累计确认计数 |
| 真正的状态迁移事件 | 写日志、写 SEL（关键记录）、发总线事件、打印 stdout |

**采样快照本身不写 SEL**：只有状态迁移，以及由它触发的规则激活/清除决策（这两类都是
"关键记录"），才会往故障历史里追加记录；否则每个采样周期都会塞进一条内容相同的记录。
"快照用于判断、迁移用于记录"是这里唯一需要记住的分工。

### 2. 异步生命周期：为什么 Worker 必须先排空、总线随后、日志与 SEL 最后？

`main.cpp` 的停机顺序是固定的，顺序由**依赖方向**决定，不能随意交换：

1. **先停网络**（只读、心跳、控制面）。网络线程还在向 Worker 提交任务；
   先停 Worker 会让这些提交直接变成 `rejected`。
2. **再停 Worker**：执行完队列中已受理的任务。恢复动作的回调会写日志、SEL 和总线，
   所以此时日志、SEL、总线必须都还活着。
3. **然后发布 `stopping`、停事件总线与上行通道**：总线排空后，所有异步写入都已结束，
   上行队列里的在途消息也在此刻结算为 `dropped`。
4. **最后统计并刷盘 SEL 与日志**，再在析构里关闭常驻描述符。
   日志与 SEL 在 `run()` 中声明得最早，因此析构得最晚——即使异常退出，
   总线仍在排空时，它的处理函数按引用持有的这两个对象不会被提前销毁。

另外两个容易踩的点：

- 恢复请求只**复制**设备路径与 ID，不保存 `Sensor` 地址。因此热加载可以销毁旧 `Sensor`，
  而不会破坏已经提交的请求（`Action` 接口只接受值类型请求也是同一原因）。
- 规则热重载是"先整体校验、再改状态"。校验失败时旧传感器与旧规则原样保留；
  校验通过后才 `merge`，避免每次重载都把已激活规则复位并重复触发一次恢复动作。

## 四、可替换接口一览

本项目没有引入依赖注入框架，只用**接口 + 引用/指针注入**。下面列出每个接口的生产实现、
测试替身，以及"能替换"带来的实际收益：

- **`Action`**（恢复动作）
  - 生产实现：`PwmAction`（写 PWM 节点）；`LogOnlyAction` 供无硬件环境使用。
  - 测试替身：`FakeLinuxIo` + `PwmAction`。
  - 可验证：动作选择与 PWM 写失败路径。
- **`EventLogger`**（监控逻辑看到的日志接口）
  - 生产实现：`Logger`（JSON 行文件）。
  - 测试替身：`HealthLogger`（`tests/runtime_management_test.cpp`）。
  - 可验证：降级上报分支，并断言告警不反写日志。
- **`Reader` / `Device`**（测量量的取值来源）
  - 生产实现：`readers.cpp` 里 mock/sysfs/i2c/gpio 四种后端与设备适配器。
  - 测试替身：`mock` 后端与 `FakeLinuxIo`。
  - 可验证：读取、寄存器解码、失败与能力位拒绝。
- **`LinuxIo`**（Linux 系统调用）
  - 生产实现：`PosixLinuxIo`，进程级默认实例是 `system_io()`。
  - 测试替身：`FakeLinuxIo`（`tests/core_test.cpp`）。
  - 可验证：I2C 地址/寄存器校验、SMBus word 解码、GPIO 线值、PWM 写入。
- **`SocketIo`**（socket 系统调用）
  - 生产实现：`PosixSocketIo`，进程级默认实例是 `system_socket_io()`。
  - 测试替身：`FakeSocketIo`（`tests/core_test.cpp`）。
  - 可验证：连接状态机、部分写、`EAGAIN`、超时，无需真实端口。

`FakeLinuxIo` 的一个重要细节：它返回自己打开的真实占位描述符，并对线值 `ioctl` 做脚本化应答，
因此可以覆盖 active-low 请求、读取失败、`CLOEXEC` 和析构时关闭。
但**电气行为仍然必须在真实设备上验证**，假接口只能证明"实现与假设一致"。
`epoll`/`timerfd`/`signalfd` 的进程编排由 Linux 集成测试验证。

## 五、当前拆分边界

- 保留 `core.hpp` 作为兼容的公共声明入口，避免一次引入大量互相包含的头文件。
- `Reader` 的具体实现仍集中在 `readers.cpp`；没有为每种设备创建单独文件。
- `Monitor` 是无状态业务协调器，依赖由调用方提供；应用运行时（`main.cpp`）负责持有传感器和基础服务。
- 没有引入依赖注入框架、没有为网络层引入通用 HTTP 框架（只实现协议严格子集）。
- `main.cpp` 是唯一管理进程生命周期的地方，其余文件只提供可被单测单独驱动的状态机。
