# 专用芯片驱动与标定

**这份文档回答什么**：挂在 I2C 总线上的温度、风扇、电压、电流芯片，寄存器里那串
数字怎么变成 ℃ / RPM / V / A；以及可选的配置字段「标定」怎么用、为什么这样设计。

**适合谁读**：要编写传感器配置 `hardware.conf` 的集成人员，以及第一次打开
`src/chips.cpp`、`src/calibration.cpp` 的开发者。读之前只需要知道「I2C 总线上每个
从设备有地址、内部有寄存器号」这一层概念；其余术语在第一次出现时都会解释。

**本文的事实来源**：`src/chips.cpp`、`src/calibration.cpp`、`src/config.cpp`、
`src/readers.cpp`、`tests/core_test.cpp`。代码里标注「未核实」的常量，本文一律
保留该标注，绝不改写成确定结论；完整清单见 4.4 节。

## 一、为什么需要它

**一句话**：内核只帮你把 I2C 事务做完，不帮你解释寄存器里的位是什么意思。

### 1.1 同一个 16 位整数，在不同芯片上含义完全不同

Linux 访问 I2C 芯片的入口是 `/dev/i2c-N` 加 `ioctl`（一种「向设备发命令」的系统
调用）。项目原有的 `i2c` 后端（`RawI2cReader`）做得很直接：发一次 SMBus
（一种两线制芯片通信协议）的字读，把返回的 16 位整数乘 `scale` 当作工程值。
这只有在「该寄存器本身就是一个线性标量」时才成立，而真实芯片并不是这样：

| 芯片与寄存器 | 寄存器里是什么 | 直接当数值用会怎样 |
|---|---|---|
| LM75B 温度 `0x00` | 11 位二补码，低 5 位是小数位 | 值偏大 256 倍（少了 `>> 5` 与 ×0.125） |
| EMC2103 温度 `0x00` | 16 位二补码，1 ℃ 对应 256 | 值偏大 256 倍 |
| EMC2103 转速 `0x4E/0x4F` | 13 位左对齐计数，需两个字节拼装 | 得到的是计数，不是 RPM |
| INA219 母线 `0x02` | 13 位数据在 bit[15:3]，低 3 位是状态 | 值偏大 8 倍，还把状态位算进电压 |
| ADM1275 电压 `0x88` | 12 位无符号码，高位是保留位 | 保留位污染数值 |
| INA219 电流 `0x04` | 需要先写校准寄存器才有意义 | 未校准前恒为 0 |

举一个能直接算的例子：EMC2103 内部温度寄存器读回 `0x1F40`。按芯片语义
（16 位二补码 ÷ 256）是 31.25 ℃；若当成无符号整数直接上报，就会上报 8000。
再如 EMC2103 的停转哨兵值 `0x1FE0`（= 8160），若当转速代入公式会算出
3932160 × 2 ÷ 8160 ≈ 964 RPM 的假转速——风扇明明停了，系统却看到正常转速。

### 1.2 为什么不能靠通用 SMBus 读

SMBus 字读（`read_word`）只保证一件事：由内核按总线协议把从设备返回的两个字节
拼成一个 16 位整数，并还原字节序。它不知道这 16 位是温度、是计数、还是有符号码。
换句话说，**协议层是通用的，寄存器语义是每颗芯片独有的**。只要出现下面任意一种
情况，通用后端就不够用：

1. 需要移位（INA219 母线电压、LM75B 温度、EMC2103 转速）；
2. 需要二补码解释（温度、INA 分流电压与电流）；
3. 一个测量量跨两个寄存器（EMC2103 转速与温度的高低字节）；
4. 某些取值是故障或哨兵码而不是数值（EMC2103 的 `0x8000`、`0x1FE0`）；
5. 换算依赖运行时状态（INA 的校准值、ADM1275 的量程与分流电阻）。

### 1.3 没有专用驱动会怎样

| 后果 | 具体表现 |
|---|---|
| 工程值错误 | 温度差 256 倍、电压差 8 倍，阈值判定全部失效 |
| 故障被伪装成正常读数 | 停转哨兵算出约 964 RPM；二极管故障报成 −128 ℃ |
| 错误无法定位 | 通用后端只会给出一个「看起来合理」的数字，排查时无从下手 |
| 安全动作被误导 | 风扇/温度判据失真，会影响降速、告警等上层行为 |

所以本项目的做法是：**把寄存器语义写成代码**，并让配置显式声明「这是哪颗芯片」。

## 二、设计思路

**一句话**：一个封装负责「怎么和总线说话」，一个抽象负责「这些位是什么意思」，
系统调用做成可注入的参数，好让解码逻辑在没有硬件时也能测。

### 2.1 三条核心目标

1. **语义集中**：每颗芯片的寄存器地址、位宽、换算公式只写在一个类里。
2. **可测试**：解码与换算不依赖真实 `/dev/i2c-*`，在普通 x86 机器上就能跑。
3. **错误早暴露**：配置写错的型号或测量量在装载或构造阶段报错，不退化成
   运行期静默返回空值。

### 2.2 `I2cBus` 封装了什么

`I2cBus`（声明见 `include/bmc/chip.hpp`）代表「一个 I2C 从设备」。
构造时依次做三件事，任何一步失败都抛 `std::system_error` 或 `std::runtime_error`：

| 步骤 | 系统调用 / `ioctl` | 作用 |
|---|---|---|
| 打开设备 | `open(O_RDWR \| O_CLOEXEC)` | 拿到 `/dev/i2c-N` 的文件描述符 |
| 选中从地址 | `I2C_SLAVE` | 告诉内核「后面的事务发给这个 7 位地址」 |
| 查询能力 | `I2C_FUNCS` | 要求同时支持 SMBus 字节读与字读 |

为什么要检查能力位：适配器不支持的字读不会报错，只会每轮采样静默失败；
在构造期直接拒绝，比运行期「设备一直无读数」容易定位得多。

它提供的事务方法如下。注意两种「读 16 位」的区别，这是后文反复用到的分界线：

| 方法 | 事务 | 返回值与要点 |
|---|---|---|
| `read_byte` | SMBus Read Byte Data | 单字节寄存器，失败返回 `std::nullopt` |
| `read_word` | SMBus Read Word Data | 内核已完成字节序还原，返回值即主机序数值 |
| `read_block` | SMBus I2C Block Data | 最长 32 字节；**当前没有驱动调用**，能力检查也未包含它 |
| `write_byte` | SMBus Write Byte Data | 写配置/页选择；当前驱动未调用 |
| `write_word` | SMBus Write Word Data | 写 16 位寄存器，如 INA 的校准值 |

失败语义按层次分开，这是有意设计的：

- **构造期错误抛异常**：打不开设备、选不中从地址、适配器能力不足。这些属于
  「配置选错了硬件」，进程应该在启动时就停下。
- **单次读取失败返回 `std::nullopt`**：从机无应答、总线超时这类运行期噪声，
  上层记为「无读数」，不应该让守护进程崩溃。

### 2.3 `ChipDriver` 抽象为什么这样设计

`ChipDriver` 只有三个方法：

```cpp
virtual const char* name() const;                              // 型号名，即注册表键
virtual std::vector<ChipFeature> features() const;              // 该型号提供哪些测量量
virtual std::optional<double> read(const std::string& feature); // 读一个测量量
```

| 设计选择 | 原因 |
|---|---|
| 一个驱动 = 一个型号 | 同一型号的多个测量量共享寄存器知识（INA219 的四个量共用校准值） |
| `features()` 返回「名字 + 单位」 | 既用于构造期报错，也直接对应本文各节的参数表 |
| `read` 收字符串而不是枚举 | 配置里写的就是字符串（`@temp`）；`make_chip` 逐字比较，区分大小写 |
| 驱动只持有 `I2cBus&` | `ChipReader` 里 `bus_` 先于 `driver_` 声明，析构时驱动先释放 |
| 不支持的测量量返回 `std::nullopt` | 作为兜底；正常路径在 `make_chip` 构造期就已经拒绝（见 2.5） |

### 2.4 为什么所有系统调用都经过 `LinuxIo` 注入

`LinuxIo` 是一个把 `open` / `ioctl` / `close` / `read` / `write` 等系统调用抽象成
虚函数的接口：生产环境注入 `PosixLinuxIo`（真实系统调用），测试注入
`tests/core_test.cpp` 里的 `FakeLinuxIo`（脚本化应答）。

芯片解码逻辑与外部世界的全部交互，恰好就是「几个系统调用 + 返回的字节」。
把它做成参数以后，测试可以这样说：「读 `0x4E` 返回 `0x0F`，读 `0x4F` 返回 `0x00`，
那么转速必须是 16384」，从而在没有任何 I2C 硬件的机器上验证换算式。
这是 `chips.cpp` 能进入 CI 的前提，也是本项目「硬件相关代码也要有单测」的具体落法。

代价是多一层间接调用（虚函数）。采样周期是秒级，这点开销可以忽略。

### 2.5 后端语法 `i2c:<chip>[@<feature>]` 的由来

原有的 `i2c` 后端（裸字读）必须保持不变，因此新能力用「前缀 + 冒号」的方式扩展，
而不是新增一个后端名。校验被刻意分成两层：

| 层 | 位置 | 校验内容 | 报错时机 |
|---|---|---|---|
| 配置层 | `config.cpp` | 只认 `i2c:` 前缀与 `@` 前的型号名 | 装载配置时 |
| 构造层 | `chips.cpp` | 型号是否已知、`@` 后的测量量是否属于它 | 构造读取器 |

为什么这样分层：配置层不该知道每个型号有哪些测量量（否则每加一颗芯片都要改配置
解析器）；但型号拼错是最常见的错误，值得在加载阶段就报出来。测量量拼错则由
构造期负责——两者都不会退化成「运行期一直无读数」。

解析细节（`ChipReader`）：去掉 `i2c:` 这 4 个字符，按第一个 `@` 拆分；测量量为空时
取该型号声明的第一个测量量（`features().front()`）。`path` 只接受
`device,address` 两段，多写寄存器字段会报错。

```text
# 通用字读（原有行为，未改动）：path = device,address,register
i2c_word    i2c            /dev/i2c-1,0x48,0x00  1 high 70 90 3 3 3 -
# 专用驱动：path = device,address；@ 后选择测量量，省略则取该型号第一个
cpu_temp    i2c:lm75b      /dev/i2c-1,0x48       1 high 70 90 3 3 3 -
fan_rpm     i2c:emc2103@rpm /dev/i2c-1,0x2E      1 low 500 200 20 3 3 -
vout        i2c:adm1275@vout /dev/i2c-1,0x10     1 high 12 13 0.5 3 3 -
```

支持的型号（`chip_names()`）：`lm75`、`lm75b`、`emc2103`、`adm1275`、`ina219`、
`ina226`。每个型号的测量量见第三节的表格。

### 2.6 考虑过、但没有采用的做法

| 做法 | 为什么不采用 |
|---|---|
| 每个测量量一个后端名 | 后端名会随「型号 × 测量量」膨胀，新增型号要改语法与解析器 |
| LSB 与换算系数放进配置 | 这些是芯片事实而非部署策略；抄错一个 LSB 会变成静默错误 |
| 未知测量量在运行期返回空值 | 配置错误会伪装成「设备无读数」；改为构造期抛异常 |
| 用块读一次取回多个寄存器 | 块读上限 32 字节且能力位不一定支持，寄存器地址也不保证连续 |
| 自动探测芯片型号 | 需要先知道各型号的探测寄存器语义，且同一地址可能挂不同芯片 |
| 在驱动里缓存原始码 | DIRECT 格式下同一码值在不同量程/分流电阻下含义不同 |

## 三、具体实现

**一句话**：先认识两个公共辅助函数，再逐颗芯片看寄存器与公式。

### 3.1 公共地板：字节序与二补码

芯片寄存器内部的位域多数是「高字节在前」，而 SMBus 字读由内核还原总线字节序，
两者是不同的事。于是有了两个辅助函数：

| 辅助函数 | 做的事 | 用在哪 |
|---|---|---|
| `from_register_bytes` | 按寄存器语义拼装 `(high << 8) \| low` | 两次字节读之后 |
| `to_signed(uint16_t)` | 按二补码解释成有符号整数 | 温度、INA 分流电压与电流 |

**二补码**（用最高位表示负数的编码）：16 位里最高位为 1 就表示负数，把它当作
无符号数读出来的值再减去 65536，就是它的真实数值。例如 `0xFFF8` 读成无符号是
65528，65528 − 65536 = −8，所以 `0xFFF8 >> 5 = −1`，对应 −0.125 ℃。

**算术右移**：对有符号负数右移时，最高位补的是符号位而不是 0，这叫符号扩展。
这解释了为什么代码写 `static_cast<std::int16_t>(raw) >> 5` 而不是先转 `double`
再除——先除会破坏低位的精度，先右移则天然保留了二补码的符号语义。

### 3.2 LM75 / LM75B（温度，1 个测量量）

核验状态：型号与分辨率的对应关系**未核实**（`chips.cpp:148`）。以下「本实现怎么做」
是可核实的；「某型号实物是多少位」不是。

温度寄存器 `0x00`，16 位、高字节在前、二补码。同一芯片家族的分辨率并不统一，
因此驱动用构造参数 `high_resolution` 区分两条路径，型号名随之不同：

| 型号名 | 有效位 | 右移 | LSB | 公式 | 低字节说明 |
|---|---|---|---|---|---|
| `lm75` | 9 | `>> 7` | 0.5 ℃ | `T = (int16)raw >> 7 × 0.5` | 低 7 位不参与换算 |
| `lm75b` | 11 | `>> 5` | 0.125 ℃ | `T = (int16)raw >> 5 × 0.125` | bit7..bit5 是 0.125 ℃ 位 |

测试用例给出的对照（`tests/core_test.cpp`）：

| 输入 raw | 型号 | 计算 | 结果 |
|---|---|---|---|
| `0x1F40` | `lm75b` | 8000 >> 5 = 250，× 0.125 | 31.25 ℃ |
| `0xFFF8` | `lm75b` | −8 >> 5 = −1，× 0.125 | −0.125 ℃ |
| `0xFF00` | `lm75` | −256 >> 7 = −2，× 0.5 | −1.0 ℃ |
| `0x0180` | `lm75` | 384 >> 7 = 3，× 0.5 | 1.5 ℃ |

为什么只用 `read_word` 一次完整事务，不用两次单字节读：代码注释把「LM75A 单字节读
会把数据线拉低、导致总线挂死」记为一个已知陷阱，因此读取只用一次完整事务。
该陷阱的硬件细节（触发条件、是否已在 LM75B 修复）**未核实**：仓库里只有这句注释，
没有手册章节依据。规避方式成本为零，所以保留。读取失败与分辨率无关，一律返回「无读数」。

### 3.3 EMC2103（转速 + 温度，3 个测量量）

核验状态：**整节未核实**（`chips.cpp:243`）。下面的常量、位域、故障码与内部温度
分辨率都是当前实现的假设，只能证明「代码与测试彼此一致」，不能当作硬件保证。

**转速**：`0x4E`（高字节）/ `0x4F`（低字节），13 位左对齐，低 3 位恒为 0。

```text
COUNT = (hi << 5) | (lo >> 3)
RPM   = 3932160 × m / COUNT        m 本实现取 2
```

| 项 | 取值 | 状态 |
|---|---|---|
| 常量 `3932160` | `kTachConstant` | 未核实：候选值，时钟/边沿推导未记录 |
| 量程乘数 `m` | `2.0` | 未核实：取默认 1000 RPM 量程的乘数 |
| 停转哨兵 | 掩码 `0x1FE0` 全 1 或 `count == 0` | 未核实：掩码对应高字节的 bit12..bit5 |
| 从地址 | 固定 `0x2E`（仅注释声明） | 未核实，且**代码不校验**配置里的地址是否等于 `0x2E` |

为什么要用掩码判断哨兵而不是等值比较：低 3 位不是数据位，若用 `count == 0x1FE0`
做等值比较，低 3 位一旦非 0 就会漏判，把「风扇停转」当成真实转速上报。
掩码判断只看有意义的高位。

为什么分两次 `read_byte`：手册未记录影子/锁存寄存器，因此两次读之间数值可能变化，
本实现**不声称原子性**（`chips.cpp:261-262`）。若换成块读可以少一次事务，
但当前能力检查未包含块读，且该改动缺少依据。

**温度**：内部 `0x00`/`0x01`，外接二极管 `0x02`/`0x03`；每通道 16 位有符号、
0.125 ℃ 分辨率：

```text
raw = (hi << 8) | lo
C   = (int16)raw / 256
```

`0x8000` 在二补码里是 −32768，除以 256 就是 −128 ℃。**这是二极管故障码，
不是温度**，本实现返回「无读数」。为什么必须这样做：若报成 −128 ℃，故障会伪装成
一个合法的低温读数，上层阈值判定随之失效——「不知道」比「一个错误的数字」安全。

| 测量量 | 单位 | 寄存器 |
|---|---|---|
| `rpm` | RPM | `0x4E` / `0x4F` |
| `temp` | C | `0x00` / `0x01`（内部） |
| `temp_external` | C | `0x02` / `0x03`（外接二极管） |

本驱动只读不写，量程沿用芯片上电默认值；外部若改过风扇配置寄存器，转速换算会整体
偏移（代码注释如此说明，具体寄存器地址未在本仓库出现）。

### 3.4 ADM1275（电压 + 电流，3 个测量量）

核验状态：**未核实**（`chips.cpp:182`、`chips.cpp:206`）。Rev.E 手册链接已记录，
但命令表、公式与量程位的具体章节/表项尚未留存。

`vin` / `vout` / `iout` 分别读 `READ_VIN 0x88`、`READ_VOUT 0x8B`、
`READ_IOUT 0x8C`。数据右对齐在 bit[11:0]，所以代码里的 `& 0x0FFF` 是**必需**的
而不是可选的美化：高位不是数据。

| 测量量 | 寄存器 | 公式 | 说明 |
|---|---|---|---|
| `vin`/`vout` | `0x88`/`0x8B` | `V = 5.208 mV × (code + 0.5)` | 用 LSB 法而非 m/b/R 系数 |
| `iout` | `0x8C` | `I = 12.4 µV × (code − 2048) / R_SENSE` | 12 位双向电流，零点在 2048 |

两个公式里各有一个容易忽略的细节：

- **`+ 0.5` 是半码偏移**：12 位码代表的是一个量化区间而不是一个点，加半码是把
  区间中心还原成实际电压，而不是取区间下沿。测试用 `0x1234` 验证：
  `0x1234 & 0x0FFF = 564`，`5.208 mV × 564.5 ≈ 2.940 V`。
- **`− 2048` 是电流零点**：这是一个双向电流通道，正负电流共用同一段码值，
  所以要先减去中点才有符号。分流电阻以毫欧配置，`1e-3` 用来换算成欧姆。

为什么 `iout` 常常返回「无读数」：分流电阻字段 `shunt_milliohms_` 默认 0，只有大于 0
才给出安培值；而 `make_chip()` 构造该驱动时并不传入分流电阻，也没有其它入口设置它。
因此**从配置构造的 `adm1275` 永远无法给出 `iout`**——这比给出一个错误的安培值好。

`power` 与 `temp` 不被提供（`read` 返回 `std::nullopt`，测试亦如此断言）。
「该型号没有对应命令、完整命令表只有 31 条」这一判断**未核实**，所以不做扩展。
电压量程由 `PMON_CONFIG` 的 `VRANGE` 位选择，本实现默认 0–20 V、LSB 取
`5.208e-3`；该 LSB 与量程位的对应关系同样**未核实**，换量程必须同步改这个常量。

### 3.5 INA219 / INA226（4 个测量量）

核验状态：**未核实**（`chips.cpp:406`）。手册编号 SBOS448G / SBOS547C 已记录，
但具体章节/表项未留存。两种芯片寄存器指针相同，LSB 与位域不同：

| 项目 | INA219 | INA226 |
|---|---|---|
| 分流电压 `0x01` | 16 位有符号，10 µV | 16 位有符号，2.5 µV |
| 母线电压 `0x02` | 13 位无符号，4 mV，数据在 bit[15:3] | 15 位无符号，1.25 mV，不移位 |
| 电流 `0x04` | 有符号，LSB = Current_LSB（由校准值反推） | 同左 |
| 功率 `0x03` | 16 位无符号，LSB = `20 × Current_LSB` | 16 位无符号，LSB = `25 × Current_LSB` |
| 校准 `0x05` | 系数 `0.04096`，**FS0 恒为 0** | 系数 `0.00512` |

**为什么必须右移 3 位**（INA219）：母线电压寄存器低 3 位是 `bit2`（未定义）、
`bit1` CNVR（转换就绪）、`bit0` OVF（溢出），数据在 `bit[15:3]`。
测试用例 `(3000 << 3) | 0x3` 验证了这一点：先右移 3 位得到 3000，再 × 4 mV
得 12.0 V；若不右移就是 96 V，偏大 8 倍。INA226 是 15 位无符号、不需要移位，
测试用 16000 × 1.25 mV 得到 20.0 V。

**为什么构造时就写校准寄存器**：INA 系列的电流与功率寄存器在写入校准值之前恒为 0，
不是「读到 0 安培」而是「这个寄存器还没工作」。因此 `InaDriver` 的构造函数就调用
`write_word(0x05, ...)`，失败直接抛异常——宁可构造失败，也不要让后续电流/功率
静默读成 0。

默认校准值与换算：

| 型号 | 默认校准值 | 校准系数 | 默认情况下的含义 |
|---|---|---|---|
| `ina219` | `4096` | `0.04096` | 电流寄存器数值等于分流电压寄存器数值 |
| `ina226` | `2048` | `0.00512` | 同上（分流 LSB 为 2.5 µV） |

功率的换算由测试覆盖：INA226 功率寄存器读到 100，则
`100 × 25 × 2.5 µV = 6.25 mW` 量级（测试断言 `100 * 25 * 2.5e-6`）。

`InaDriver` 构造函数另有「提供分流电阻与最大电流时按手册公式计算校准值」的入口
（`current_lsb = max_current / 32768`，`computed = factor / (current_lsb × R)`，
再由写下的校准值反推 `current_lsb_`）。但 `make_chip()` 总是传 `0, 0`，
**从配置构造时这条路径不可达**，永远走默认校准。两个由此而来的边界：

- 未配置分流电阻时，`current` 上报的数值在单位上并不是安培（代码注释亦说明
  「无法换算成安培/瓦，但保留默认 LSB 使 Raw 值可用」），`power` 同理。
- INA219 的 `calibration_ &= 0xFFFE`（FS0 恒为 0）发生在反推 `current_lsb_`
  之后；若计算的校准值恰为奇数，两者会相差 1。该分支当前不可达，故不影响使用，
  但属于已知不精确处。

电流寄存器在两个型号上都按二补码解释（`to_signed`）；手册层面的符号行为
（例如是否支持负分流电压）**未核实**。

### 3.6 标定：可选的第 12 个配置字段

**一句话**：标定把「芯片读出的原始值」翻译成「你信任的工程值」，由一次线性修正
加一张分段折线表组成。

配置行前 11 个字段固定为
`id backend path scale direction warning critical hysteresis debounce failure_limit action_path`，
第 12 个字段可选，省略或写 `-` 表示恒等（`gain = 1`、`offset = 0`、无折线表）。
旧配置（11 字段）不受影响。

```text
# 语法：gain[:offset][;raw=value;raw=value...]
cpu_temp i2c:lm75b /dev/i2c-1,0x48 1 high 70 90 3 3 3 - 1.5:-2;0=10;100=210
```

换算顺序是**先线性、后分段插值**，两步不可交换：

```text
corrected = raw × gain + offset          # 第一步：线性修正
result    = 在 corrected 上做分段线性插值  # 第二步：折线表
```

为什么顺序不能换：`points` 的键定义在**线性修正之后**的量纲上。测试用例
（`gain = 10`、`offset = 5`、`points = {100→1, 200→2}`）说明了这一点：
`raw = 15` 先修正为 155，再落在 100..200 段的 55% 处，得 1.55；
若先查表就会用 15 去找区间，直接落到表外。

| 规则 | 为什么 |
|---|---|
| 区间外按端点**钳制**，不外推 | 外推会把未标定区间的误差按斜率放大；钳制至少保证不产生更离谱的值 |
| `points` 的 raw 必须**严格递增** | 查表用 `std::upper_bound`；乱序或重复的点会落进错误的段 |
| `gain` 必须为正 | 查表用 `corrected`：负 gain 会让标定点在查表域里递减并取错段 |
| `gain = 0` 同样被拒 | 它把所有读数压成一个点，等于让标定表失去意义 |
| 非有限值一律拒绝 | NaN 参与比较恒为 false，会一路隐形影响判定，让故障被判成 `normal` |

为什么把「静默」单独点出来：查表取错段不会报错，只会返回一个**看起来正常**的数值。
这种错误没有任何日志痕迹，只能靠配置校验在加载期拦住，所以才把「gain 必须为正」
做成硬性规则，而不是留给使用者自觉。

三条校验发生在不同时机：`validate()` 与加载期都会检查标定点；乱序、重复与非有限值
在加载配置时即被拒绝（测试用 `1;50=1;10=2` 验证）。`apply()` 自己再拦一次非有限
输入，作为运行期的最后一道闸门。

`FakeLinuxIo` 脚本化 `ioctl` 应答，因此上述解码与换算无需真实 `/dev/i2c-*`。

| 已覆盖 | 用例要点 |

| LM75 两种分辨率与负温度 | 11 位 `0x1F40 → 31.25`、`0xFFF8 → −0.125`；9 位 `0xFF00 → −1.0` |

## 四、优缺点与适用性

**一句话**：这套方案用「少量重复代码」换来了「错误早暴露 + 可脱机测试」，
代价是仍有不少寄存器事实停留在未核实状态，且没有真实硬件验证。

### 4.1 优点

1. **语义集中且可对照**：每颗芯片的寄存器、位宽、公式都在一个类里，与本文的表格
   一一对应，评审时可以直接拿手册逐条核对。
2. **无需硬件即可测试**：系统调用经 `LinuxIo` 注入，`FakeLinuxIo` 能覆盖解码、
   位域、故障码、构造期校验等全部逻辑分支。
3. **错误早暴露**：未知型号在加载配置时报错，不支持的测量量在构造期报错，
   缺分流电阻时返回「无读数」而不是错误的安培值。
4. **失败语义分层清晰**：构造期异常 vs 单次读取 `std::nullopt`，
   调用方不用猜「这个空值代表什么」。
5. **向后兼容**：原有 `i2c` 裸字读后端与 11 字段配置行完全不受影响。

### 4.2 代价与局限

| 局限 | 说明 |
|---|---|
| 寄存器事实未全部核实 | 见 4.4；EMC2103 整节与 ADM1275/INA 的 LSB 都缺手册章节依据 |
| 无真实硬件验证 | 测试证明的是「代码与假设一致」，不是「芯片确实如此」 |
| 部分能力不可达 | `adm1275` 的 `iout`、INA 的参数化校准路径都无配置入口 |
| 单位与语义有缺口 | 未配分流电阻时 INA 的 `current` 数值并不是安培，但单位仍声明为 `A` |
| 只读不写 | 驱动不修改芯片量程/配置，外部改动会让换算整体偏移 |
| 缺少通用扩展点 | 新增型号必须同时改 `chips.cpp` 与 `chip_names()`；没有从配置注入公式的机制 |

### 4.3 为什么这个方案适配本项目

本项目是一个 Linux C++20 硬件监测与故障恢复服务（systemd 守护进程）——README 明确
说明它「不是完整 BMC 固件」。它的取值场景有三个特点：芯片型号少而固定、故障时读数
必须可信、开发与 CI 环境没有目标硬件。于是「少量硬编码 + 构造期校验 + 注入式 I/O」
正好对齐：

- 型号少而固定 → 硬编码寄存器语义的成本可接受，比引入配置化公式更安全；
- 读数必须可信 → 宁可返回「无读数」，也不返回未校准或语义不明的数值；
- 没有目标硬件 → 注入式 I/O 让解码逻辑进入 CI，把「必须上机才能发现」的错误
  压缩到真正的电气与手册层面。
