# Runtime reliability

**In one sentence**: this document answers "when the log, the SEL or an internal state table
starts failing *itself*, what keeps the daemon sampling and what makes the damage visible?".
It is written for operators on call and for developers changing `monitor.cpp`, `logger.cpp`,
`sel.cpp`, `rules.cpp` or `recovery.cpp`.

## 1. Why it exists

The most ironic way a monitoring daemon can fail is this: **the fault happens, and the path that
records faults breaks first.** Three concrete forms exist:

1. **The log cannot be written** (disk full, target `/dev/full`, read-only mount, bad quota).
   Every subsequent sample fails once. If "write failed" were fatal, the daemon would exit exactly
   when it is needed most - the temperature is still rising and nobody is on duty any more.
2. **Internal state tables grow without bound as hardware changes.** Hot-plug, re-enumeration, or
   sensor IDs that differ on every boot leave entries in the rule engine and the recovery engine
   that will never be used again, and after months of uptime memory growth kills the process.
3. **"Write failed" and "sync failed" get conflated.** Data that reached the page cache but failed
   `fdatasync` is not the same as data that was never written; merging the counters makes it
   impossible to tell "the record is gone" from "the record is not on disk yet".

Four terms used throughout this document:

- **Degradation** - keep running with reduced capability instead of exiting or retrying forever,
  and report the reduced capability.
- **Throttling** - report the same fault at a fixed minimum interval, so that a per-sample record
  does not flood the log and bury the genuinely new fault.
- **fsync / fdatasync** - `write` usually only hands bytes to the kernel page cache and loses them
  on power loss; `fdatasync` asks the kernel to put them on persistent media. It is expensive, so
  it is reserved for records that are fault evidence.
- **Feedback loop** - the alert itself travels the failing path, so the alert creates new failures
  and the new failures create new alerts.

Without this machinery the worst outcome is not a crash; it is **a log that silently drops lines,
tables that silently grow, and nobody who knows**.

## 2. Design approach

The goal is one sentence: **separate "can keep working" from "must stop".**

The single test is: would this lose **confirmed fault evidence**, or invalidate the **decision
conditions themselves**?

| Situation | Handling | Why this verdict |
|---|---|---|
| Log write failure | Keep sampling, count and report | Audit trail, not recovery data |
| SEL write failure | Keep sampling, count and report | Never go off duty over notes |
| `fdatasync` failure | Separate counter (`sync_failures`) | Data may be in page cache |
| Log/SEL buffer over cap | Drop oldest bytes and count them | Bounds memory, loss measurable |
| Invalid config or rules | Fail at start, or reject the reload | Wrong conditions, wrong actions |
| Audit not persisted | Stop listening, exit non-zero | A hardware action needs audit |

**Why a log write failure does not exit.** Exiting means "I cannot take notes, so I will not stand
watch". The log here is an audit trail; when it is damaged the right response is to keep monitoring
and make "the log can no longer be trusted" itself an observable alert. (One exception: if
*reopening* the file after rotation fails, the new segment does not exist at all and
`std::system_error` is thrown. Ordinary write failures never throw.)

**Why degradation alerts never write back to the failing log.** The alert is itself a log write.
If a log failure raised an alert, and the alert went into the same failing log, the failure counter
would push itself up in a feedback loop, turning one real fault into an unbounded number of lines.
So the log-degradation alert goes only to the SEL and the event bus, never to the broken logger.
For the same reason the SEL-degradation report appends itself as **non-critical**, so it cannot
force another `fdatasync` that fails again.

**Alternatives considered and rejected:**

- **Exit on write failure and let systemd restart us** - throws away the live sampling context,
  which is the last thing to do during a fault.
- **Retry forever until the write succeeds** - with a full disk this pins the sampling thread
  inside the write syscall.
- **Give degradation reporting its own thread or listening port** - this project deliberately adds
  no threads and no ports; degradation reuses the existing sampling loop and event bus, otherwise
  the reliability mechanism becomes a new failure surface itself.
- **Evict the oldest entry when a state table fills up** - that deletes states that are still
  cooling down or still running, causing duplicate recovery actions or lost de-duplication.
  Only genuinely reclaimable entries may be dropped.
- **Invent a new persistence format for degraded health** - reusing the existing SEL and log formats
  means `grep` and the queries in
  [Control plane deployment and usage](控制面部署与使用（英文）.md) keep working unchanged.

## 3. Implementation details

The code lives in `src/monitor.cpp` (reporting), `src/logger.cpp` and `src/sel.cpp` (persistence),
and `src/rules.cpp` / `src/recovery.cpp` (state tables).

### 3.1 Logger degradation reporting

`Monitor::report_log_degradation` reads `EventLogger::write_failures()` and `dropped_bytes()`:

| Rule | Behaviour |
|---|---|
| Trigger | Failure count **or** dropped bytes differ from the last report |
| First report | Immediate, never throttled (degradation must be visible at once) |
| Later reports | Skipped while less than 5 seconds have passed since the last one |
| Unchanged counters | Never repeated |
| Changes inside the window | Coalesced into the latest cumulative counters at the next report |
| Destination | One SEL record `source=log state=degraded` plus a `service` bus event |
| Never | Any alert written back into the failing `Logger` |

There are two check points: the end of `Monitor::poll`, and after `logger.flush()` in the main loop
(`src/main.cpp`). The baseline counters advance **only after a report actually succeeded**, so an
observation dropped by the throttle is reported on the next round.

A record produced through a file log looks like this:

```text
source=log state=degraded message="log-write-failures=10 dropped-bytes=0"
```

The SEL file itself uses quoted fields (`std::quoted`), so query it like this:

```sh
sudo grep '"log" "degraded"' /var/log/bmc-lite/sel.db | tail -10
```

`Logger` counts three things into `write_failures()`: a real write failure, a `fdatasync` failure
(when `sync=true`), and dropping unflushed content because the buffer cap was exceeded. The dropped
byte count is tracked separately in `dropped_bytes()`.

A log that keeps failing during operation **does not** stop sampling; only an unsuccessful final
flush at exit produces status 1 and the stderr line `log flush failed`
(frozen by `tests/degradation_runtime_test.py`).

### 3.2 SEL degradation reporting

`Monitor::report_sel_degradation` is simpler: it reports **once per increase of
`sel.write_failures()`** (an unchanged value is never repeated) with four independent counters:

| Field | Meaning |
|---|---|
| `sel-write-failures` | Failed writes (including failed compaction rewrites) |
| `sync-failures` | Failed `fdatasync` calls, counted separately |
| `pending` | Bytes not yet successfully flushed |
| `dropped` | Bytes discarded because the buffer cap was exceeded |

The report writes one log action line (`logger.action`), one SEL record (`state=degraded`,
**non-critical**) and one `service` bus event. It is deliberately not critical: otherwise the
"report the degradation" act would force a flush that may fail again and push the counter higher.
With these counters, "fault evidence is being lost" stops being a guess and becomes a queryable
number.

### 3.3 Lifetime of rule state

The runtime state key is `<rule id>\n<trigger state>\n<sensor id>`; putting the trigger state in the
key means a rule whose `trigger` changed cannot inherit counters or the `active` flag from the old
condition.

| Moment | Behaviour |
|---|---|
| End of `Monitor::poll` | `retain_sensors` removes state of absent devices |
| Sensors still present | `bad`/`good` counts and the `active` flag are preserved |
| Why every round | Reload-only pruning is not enough: a reused ID inherits old counts |
| SIGHUP reload | `merge` validates the new rule set, then keeps valid state |

`merge` keeps an entry only when the rule identity (`id` + trigger state) still exists **and** the
sensor still exists. Removed rules, absent sensors and rules whose `trigger` changed lose their
state: a surviving `active` flag would refer to different decision conditions, which is worse than
losing the state. Changes to `confirmations`/`action` do not reset state because the identity of the
decision is unchanged.

**Note for direct callers**: call `retain_sensors` after one complete device sampling round, passing
the whole current sensor set. Calling it with a single sensor after each `evaluate` incorrectly
erases the confirmation counts of every other sensor. These interfaces belong to the sampling
thread, never to a network thread.

### 3.4 Recovery state table: cap and reclamation

`RecoveryPolicyEngine` keys state by `sensor + '\n' + action`, so different actions on the same
sensor have independent cooldowns.

| Rule | Behaviour |
|---|---|
| Cap | 4096 entries |
| When checked | Only when a **new** key has to be created |
| Reclaimable | `!running` and cooldown expired (never-completed entries too) |
| Never evicted | States that are running, or still inside their cooldown |
| Still full after reclamation | The recovery is refused with `detail = "state capacity"` |

"I would rather skip one action than let the table grow without bound" is deliberate: a refusal is
visible (the reason travels with the result), while an overflowing table kills the process quietly
weeks later.

### 3.5 Persistence strategy for the log and the SEL

Both use a **resident descriptor plus batched writes**, turning "one syscall per record" into
"one syscall per batch".

| Object | Batch threshold | Sync policy | Unflushed buffer cap |
|---|---|---|---|
| `Logger` | 4096 bytes | No `fsync` by default | 1 MiB, drop oldest |
| `SelStore` | 4096 bytes | Critical records: `write`+`fdatasync` | 1 MiB, drop oldest |

**Why the log does not `fsync` by default**: it is an audit trail, not recovery data, so losing the
last small batch on a crash is acceptable. Passing `sync=true` to the `Logger` constructor restores
"flush and `fsync` every record". **Why the SEL distinguishes critical records**: state transitions,
rule activation/clearing, recovery results and control-plane audit lines are fault evidence, so each
is appended with `important=true` and flushed with `write`+`fdatasync` immediately; ordinary records
accumulate to the threshold.

Four further details that exist specifically to avoid losing lines:

- **Flush before rotation**: the log rotates only when "file + unflushed buffer + new record"
  really exceeds the limit, and it flushes the buffer into the segment that is about to be renamed.
  If that write fails, the file and buffer are left untouched and the write is retried at once.
  Draining unconditionally just to decide about rotation would leave the buffer permanently empty
  and disable batching entirely.
- **Targets whose size cannot be queried** (pipes, device nodes) skip the rotation decision but are
  still written, so write failures on those targets remain observable.
- **Short writes retry only the suffix**: when `write` writes part of the buffer, only the not-yet
  written suffix is kept, so a retry never emits half a record twice.
- **SEL replay at startup**: a torn trailing record without a newline is handled by the `Truncate`
  policy below, and memory is trimmed to `max_records` (4096 by default). Above the cap the file is
  rewritten through a unique temporary file, `fsync`ed, `rename`d, with the directory entry
  `fsync`ed too, and `SelStore` takes over the new descriptor (`rename` does not update an already
  open fd; without takeover the process would keep writing to the deleted inode).

| `Truncate` policy | Behaviour at startup |
|---|---|
| `tail` (default) | Truncate at the torn record; count in `truncated_bytes()` |
| `refuse` | Append only, never modify: no data is lost, but the torn line stays |
| `prepare` | In-memory mode: nothing is written or compacted (tests) |

### 3.6 Developer verification

```sh
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build -R 'RuntimeManagement|degradation_runtime' --output-on-failure
```

Coverage includes write failures on `/dev/full`, a persisted runtime warning, the 5-second
reporting window, "the alert never writes back into the log", independent dropped-byte changes,
10,000 devices appearing and disappearing, retained confirmation counts, and the real pruning wiring
inside `Monitor` (see `tests/runtime_management_test.cpp` and `tests/degradation_runtime_test.py`).

## 4. Trade-offs and applicability

**Benefits**

- **On duty even while failing**: a broken log or SEL never stops the monitoring itself.
- **Faults stay observable**: degradation becomes SEL records, bus events and queryable counters.
- **Bounded memory**: rule state converges to the current device set; the recovery table and both
  write buffers have hard caps.
- **Evidence first**: the records that must be durable (state transitions, rule decisions, recovery,
  control-plane audit) take a separate synchronous path.
- **No new failure surface**: no extra thread, port or storage format; degradation reuses existing
  channels.

**Costs and limits**

- **Log lines are lost while degraded**: above the 1 MiB buffer cap the oldest bytes are dropped and
  only counted; the content is genuinely gone.
- **Events inside the throttle window are coalesced**: several counter changes within 5 seconds are
  reported as the latest cumulative value only, so the *rate* of new failures is not observable.
- **If the SEL is unwritable too, alerts cannot be persisted**: only the log and event bus remain,
  and if both are unusable the degradation is invisible. This mechanism cannot fix that.
- **A full recovery table refuses actions**: in an extreme case one recovery is skipped rather than
  growing the table.
- **Synchronous critical records cost time**: one `fdatasync` per piece of fault evidence.
  Measurements are in [Write-path performance baseline](写入路径性能基准.md) (Chinese).
- **Exit-code semantics are coarse**: a failed final log flush shows up only as status 1 plus one
  stderr line, not as "how many records were lost".

**Why this fits this project**: BMC-Lite is a long-running, low-resource monitoring daemon that must
avoid wrong actions. It has no redundant storage and no external transaction coordinator, so
"records are never lost" is not achievable; what *is* achievable is **turning damage into an
observable, counted state while never abandoning monitoring because of a recording problem**.
Keeping this logic in the stateless `Monitor` and behind the injectable `EventLogger` / `SelStore`
means no new threads are needed and every degradation branch can be driven by a test double.
