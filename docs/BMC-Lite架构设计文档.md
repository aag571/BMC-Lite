# BMC-Lite 架构设计文档

## 一、开发原因

### 1.1 BMC 是什么，这个项目做什么

- **BMC**（Baseboard Management Controller，基板管理控制器）是服务器主板上的一颗独立芯片。
- 它的职责很单纯但很关键：**在操作系统无法正常运行的时候，监控机器的物理状态**——温度、电压、风扇转速——出现问题就记录下来。

| 行为 | 解读                                               | 代码入口 |
|---|---|---|
| 采集 | 定时去读温度、电压、风扇转速 | `Monitor::poll` |
| 判断 | 判断这个数值算正常还是危险 | `Engine::update` |
| 记录 | 把发生的事写成日志；重要事件单独存一份「事故档案」 | `Logger`、`SelStore` |
| 恢复 | 危险时尝试救一下（本项目中就是调大风扇） | `RecoveryPolicyEngine`、`Action` |

### 1.2 要解决的问题

| 真实现象 | 这套系统解决的问题 |
|---|---|
| 读数偶发尖峰（探头噪声、单次读取错误） | 风扇乱转、误告警；运维开始忽略告警（「狼来了」效应） |
| 阈值附近的数值抖动 | 状态在正常/危险之间反复横跳，风扇一顿一顿启停 |
| 探头掉线、数值读不到 | 缺失值被静默当成「正常」，监控悄悄失效却看起来一切正常 |
| 故障已经过去 | 没有证据链，事后无法判断当时到底发生了什么 |
| 手工写 PWM 恢复 | 没有冷却、去重与并发上限，可能把硬件写爆 |
| 想在线改一个阈值 | 只能重启监控，等于制造一段监控空白 |
| 磁盘满导致日志写不进去 | 若因此退出，后续发生问题将追溯困难 |

### 1.3 设计目标与边界

| 目标 | 说明 |
|---|---|
| 单一实现 | 模拟输入和真实硬件走完全同一条处理链 |
| 无硬件可运行 | 没有真实传感器（如使用 QEMU 虚拟机或纯软件环境）时用模拟序列 |
| 受控恢复 | 只允许写配置里明确指定的 PWM 文件，不执行任意 shell |
| 有界资源 | 队列、缓冲区、连接数都有上限；上限满时丢弃并计数，防止崩溃也防止无限增长 |
| 默认不可达 | 全部网络能力默认关闭，不显式开启就不监听任何端口 |
| 只读管理面优先 | 先保证能看见发生了什么 |

## 二、设计思路

### 2.1 设计主线

把整个设计主线压缩成三步：

```text
第一步 判据：什么样的信号才值得相信？  → 去抖 + 迟滞 + 垃圾值单独处理
第二步 表达：当前到底处于什么状态？    → 四态状态机，只在变化时产出事件
第三步 动作：确认危险之后怎么动手？    → 异步 + 独立策略层 + 默认演练模式
```

### 2.2 难题一：如何不被假信号骗到

#### 2.2.1 去抖（debounce）：连续确认才认账

- 配置里的 `debounce 3` 意思是：**连续 3 次读到异常，才算真的异常。**
- 如果中间夹了一次正常值，计数清零重来。可以根据实际需求调整容错值。

```text
读到 95°C → 可疑，先记下，对外状态仍是 normal
读到 96°C → 第 2 次异常
读到 95°C → 第 3 次异常，达到门槛 → 正式判为 critical
```

#### 2.2.2 迟滞（hysteresis）：留一段缓冲带，防止边界横跳

> 迟滞只需要影响**恢复**，不影响上升

- 假设 `critical = 90`。如果只按「低于 90 就恢复」判断，温度在 89.9 ↔ 90.1 之间抖动时，状态会疯狂来回切换，风扇跟着一顿一顿启停。
- 迟滞就是留一段缓冲区间：hysteresis 3 表示必须降到 87 以下才算真的恢复。

```text
升上去：90 才算 critical
降下来：87 才算恢复正常      ← 中间的 87~90 保持原状态不动
```

#### 2.2.3 读取失败与「垃圾值」必须单独处理

1. **读取失败单独计数**，达到 `failure_limit` 才进入 `unavailable`。探头偶发一次读不到，不应该立刻报「设备失联」。
2. **NaN 与无穷大被当作「读取失败」，而不是「一个数值」。** 原因是 NaN 参与任何比较都返回`false`——如果不管它，它会一路穿过所有阈值判断，最后被静默地当成「正常」。
3.  温度是「越高越危险」，风扇转速是「越低越危险」。代码用乘一个方向系数（`high ? 1 : -1`）把两种方向统一成「越大越危险」，因此判断逻辑只写一份，而不需要复制两套。

### 2.3 难题二：状态怎么表达

每个传感器独立维护一个状态，只有四个取值：

| 状态 | 含义 |
|---|---|
| `normal` | 正常 |
| `warning` | 警告，需留意 |
| `critical` | 危险，要处理 |
| `unavailable` | 读不到数 |

#### 关键点：`unavailable` ≠ `critical`

这两个是**不同性质**的问题：

- `critical` = 「数值很危险」
- `unavailable` = 「**我根本不知道现在什么情况**」

`unavailable`往往更可怕：相当于**失去了监控能力**，而所有危险都可能在无监控状态下发生。所以它必须是独立状态、能独立上报的。

#### 仅当状态真的变了才产出事件

> 时间戳不放在事件里，而是由写档案（SEL）时补上。事件本身只描述「发生了什么变化」。

```text
每次采样 → Engine::update(读数)
             ├── 状态没变 → 返回「无事件」（什么都不记）
             └── 状态变了 → 返回一个 Event（旧状态、新状态、当前值、原因、序号）
```

设计原因：

- 如果每一次采样都记录，一天产出的事件是庞大的
- 而实际有效信息都包含在状态改变的时候，状态改变，就相当于传递给我们一个信号

### 2.4 难题三：动作怎么安全地做

核心思路：**恢复动作永远不在采样线程里执行。**

```text
规则激活
  └─ Worker::submit 提交任务（异步！不阻塞采样）
       └─ RecoveryPolicyEngine::submit
            ├─ 同一(传感器,动作)正在执行？ → 拒绝 "already running"
            ├─ 并发额度满？               → 拒绝 "concurrency limit"
            ├─ 还在 30 秒冷却期内？        → 拒绝 "cooldown"
            ├─ 状态表已满且无可回收？      → 拒绝 "state capacity"
            └─ 通过 → 释放锁 → 执行 Action（最多 3 次尝试，总退避 ≤30ms）
                 ├─ LogOnlyAction：只记日志（默认，dry-run）
                 └─ PwmAction：真的往配置指定的文件写 PWM 值 255
```

**四个拒绝原因分开报的设计思路：** 调用方需要区分「这是重复提交」还是「系统忙不过来」，前者应该忽略、后者可能需要扩容。混在一起无法判断。

### 2.5 关键取舍：考虑过但放弃的方案

**网络通道划分**
- 考虑过：一个端口搞定只读、控制、上行、心跳。
- 放弃原因：一个端口无法按角色分别限流与审计；只读端点会继承写通道的凭证与暴露面。
- 选择：四种通道各自独立监听，默认初始均为关闭。

**主循环怎么等**

- 考虑过：用 `sleep()` 轮询。
- 放弃原因：睡眠期间收不到信号、退出变慢；采样周期还会被信号处理打乱。
- 选择：`timerfd` 交给 `epoll` 统一等待。

**信号怎么处理**
- 考虑过：在信号处理函数里直接干活。
- 放弃原因：信号处理函数里能干的事极少——不能加锁、不能分配内存、不能调用大多数库函数。
- 选择：`signalfd` 把信号变成「可读的数据」。

**硬件通知**
- 考虑过：给所有 hwmon（Linux 的硬件监测接口）都注册中断。
- 放弃原因：绝大多数硬件不支持可靠的中断通知，只能老实轮询。
- 选择：默认轮询，只有 GPIO 这类能独立注册中断的才用事件驱动。

**恢复动作位置**

- 考虑过：主循环里直接写 PWM。
- 放弃原因：几十毫秒的慢动作会拖垮整条采样节奏。
- 选择：交给 `Worker` 线程池异步执行。

**规则状态处理方案**

- 考虑过：热重载时清空并重建。
- 放弃原因：已激活的规则会被当作「还没激活」，于是**重复触发一次恢复动作**。
- 选择：按「规则 id + 触发状态」合并保留。

**已提交的任务**

- 考虑过：支持强制取消。
- 放弃原因：会破坏审计与一致性，且无法安全中断阻塞的系统调用。
- 选择：有界队列 + 明确拒绝，放弃取消功能。

**日志写失败**

- 考虑过：立即退出，避免记录有问题的日志导致日志紊乱。
- 放弃原因：等于「因为记不了笔记就不值班了」，而监控本身更重要。
- 选择：继续监控 + 将其降级上报成一条记录。

**SEL 尾部残缺**
- 考虑过：拒绝启动，或保留残缺不动。
- 放弃原因：一行半截会让后续所有读取解析失败，**污染整个文件**。
- 选择：默认从残缺记录起点截断并记录丢弃字节。

**头文件组织**
- 考虑过：把 `core.hpp` 拆成十几个小文件。
- 放弃原因：会引入大量互相包含与可见性管理，收益只是单文件更短。
- 选择：保留单一公共声明入口。

## 三、架构分层

### 3.1 四层结构与依赖方向

四层，依赖方向**严格单向**：上层知道（依赖）下层，下层完全不知道上层。

| 层 | 职责 |
|---|---|
| **domain**（领域） | 纯逻辑判断：将设备原始值通过纯线性缩放换算成工程值，对这些进行判级、去抖、迟滞等 |
| **hardware**（硬件） | 读取设备原始值，所有系统调用经统一接口转发 |
| **infrastructure**（基础设施） | **提供机制 + 可注入参数**：描述符、定时器、信号、日志、线程池 |
| **application**（应用） | 链接上面三层，管理进程生命周期 |

各层的代表文件：

- **domain**：`engine.cpp`、`rules.cpp`、`calibration.cpp`
- **hardware**：`readers.cpp`、`chips.cpp`
- **infrastructure**：`fd.cpp`、`logger.cpp`、`sel.cpp`、`worker.cpp`、`event_bus.cpp`
- **application**：`main.cpp`、`monitor.cpp`、`config.cpp`、`cli.cpp`

依赖关系：

```c#
application  →  infrastructure  →  hardware
     ↓                ↓
   domain  ←──────────┘        （domain 谁都不依赖）
```

**为什么这个方向很重要？** 因为 `domain` 层不依赖任何外部东西，所以它可以在没有硬件、没有文件、没有网络的机器上完整测试。项目里测试覆盖最密集的就是这一层。

依赖方向还有一个具体好处：`Monitor` 只依赖 `EventLogger` 这个接口，生产实现是 `Logger`，测试可以换成记录型实现，不必创建真实日志文件。

### 3.2 并发模型：一个主线程加三个辅助

这是全项目并发设计的核心，也是理解「为什么这个程序不会卡住」的关键。

#### 3.2.1 主循环：一个人守着一台交换机

程序主体是一个单线程事件循环。它把所有需要等待的东西**登记**给 Linux 的事件通知器、`epoll`，然后等 `epoll` 告诉它「哪个有动静了」。

```text
        ┌───────────── epoll（统一事件分发）─────────────┐
        │                                               │
   timerfd              signalfd                  GPIO（可选）
  （定时器响）        （收到信号）               （线电平跳变）
        │                    │                        │
   采样一次             SIGHUP → 重载配置          立刻额外采样一次
                        SIGTERM → 准备退出
```

- `timerfd`：定时触发采样。**不能用 `sleep()`**——睡眠期间收不到信号，退出会变慢，而且采样周期会被信号处理打乱。
- `signalfd`：把信号变成「可读的数据」。**信号处理函数里能干的事极少**（不能加锁、不能分配内存、不能调用大多数库函数）；转成普通事件后，就能在主循环里安全地处理。
- GPIO：线电平变化的中断。**默认不用**——绝大多数硬件（hwmon）不支持可靠的中断通知，只能老实轮询；只有 GPIO 这类能独立注册中断的才值得用事件驱动。

#### 3.2.2 三个辅助：只读 HTTP、控制面、实例心跳

这三项网络能力各自开独立线程 + 自己的 epoll，和主循环并行运行。
但它们受三条铁律约束：

**铁律一：绝不直接碰传感器对象，只能读「加锁的快照」。**

- 热加载会整个换掉传感器对象。
- 如果网络线程抓着一个旧对象的引用，那就是野指针——程序会随机崩溃，而且极难复现。
- 所以网络线程能看到的只有两样东西：SEL 的快照、以及配置的快照，两样都是加锁拷贝出来的。

**铁律二：网络线程里绝不能直接写硬件。**

- 控制面收到「调大风扇」的请求时，必须把它扔进 Worker 任务队列，走和自动恢复完全同一条恢复引擎。
- 这样冷却、去重、并发限制、审计这些保护自动全部生效。
- 如果图省事绕过它直接写 PWM，那所有保护就都失效了——这是架构上最不能妥协的一条。

**铁律三：默认全部关闭。**

-  不给出对应开关，连监听端口都不创建。

#### 3.2.3 为什么不用「一个端口搞定所有事」

四种网络需求（只读管理、控制面、上行遥测、实例心跳）的信任级别完全不同：

| 通道 | 方向 | 信任前提 | 要认证吗 | 出问题的后果 |
|---|---|---|---|---|
| 只读管理 | 入站 | 低 | 不需要 | 只影响可观测性 |
| **控制面** | 入站 | **高** | **必须** | **可造成物理动作** |
| 上行遥测 | 出站 | 中 | 采集器侧 | 不得影响采样 |
| 实例心跳 | 双向 | 高（对等） | 双向 | 可导致脑裂 |

- 合并成一个端口的代价是具体的：**一个端口无法按角色分别限流和审计**。
- 只读端点会继承写通道的凭证与暴露面；慢采集器会波及控制面重试；
- 实例间协议会变成「任何对等体都能改风扇」的后门。所以宁可多几个端口。
- 端口划分与信任模型的完整论证见 [网络设计说明](网络设计说明.md)。

### 3.3 安全设计：默认什么都不开启

> 默认全关，且 fail-closed

| 能力 | 默认 | 怎么开启 |
|---|---|---|
| 写 PWM（真的调风扇） | **不写**，只记日志（dry-run） | `--enable-actions` |
| HTTP 只读接口 | 不监听 | `--http-port` |
| 控制面（能触发动作） | 不监听 | 端口 **和** 令牌文件，两个都必须给 |
| 实例心跳 | 不监听 | 四个参数必须齐全 |

- **「fail-closed」的意思是：**配置不全就拒绝启动
- 比如控制面只给了端口没给令牌文件——程序直接报错退出，
- 不会开一个「不用密码的控制端口」。这种习惯在安全领域叫「失败时选择关闭而非打开」。
- **默认全关一个实际好处**：不开启这些功能时，程序的攻击面和完全不做网络功能时一模一样。因为我就不在网络上，不到本地就攻击不到我

### 3.4 配置与热加载

#### 3.4.1 配置分成两类文件

| 文件 | 内容 | 改动频率 |
|---|---|---|
| `hardware.conf` | 有哪些传感器、后端、阈值、动作目标 | 换硬件时改 |
| `rules.conf` | 什么状态触发什么动作 | 调策略时改 |

#### 3.4.2 热加载：不重启就换配置

运维现实是「不能为了改一个阈值就重启监控」。所以支持发一个信号（`SIGHUP`）让程序重新读配置。但这件事有几个必须做对的地方：

**第一，先全部校验完，再动任何状态。**

```text
收到 SIGHUP
  ├─ 解析新传感器配置 + 解析新规则
  ├─ 两者全部校验通过？
  │    ├─ 否 → 记一条 "reload rejected; keeping generation N"，保持旧配置不动
  │    └─ 是 → 发布 "validated generation N+1" → 替换 → 刷新缓存 → 完成
```

如果边解析边替换，中途失败就会留下「传感器换了一半、规则还是原来的」这种四不像状态，比拒绝重载还要糟糕。

**第二，规则状态要「合并」而不是「清空」。**

- 这是最容易忽略、但用户最能感知的细节。
- 假设某规则已经激活（风扇正在高速运转），此时你只改了一个**无关**的阈值并重载——如果规则状态被清空，程序会认为「这条规则还没激活」，然后**再触发一次恢复动作**。
- 所以重载时按「规则 id + 触发状态」判断哪些状态可以保留：

| 情况 | 保留状态？ |
|---|---|
| 规则 id 和触发状态都没变 | ✅ 保留确认计数与激活标志 |
| 规则的触发状态被改了（比如 critical 改成 warning） | ❌ 丢弃（旧的激活标志对应的是不同条件） |
| 规则被删除 | ❌ 丢弃 |
| 传感器消失了 | ❌ 丢弃 |

**第三，配置代次（generation）。** 

- 每次成功重载，代次加一。
- 这个数字会通过网络接口暴露，让自动化工具能确认「我改的配置真的生效了」。
- 实例心跳之间也交换这个数字，用来互相判断对方是不是还活着、配置是否一致。

### 3.5 验证

由于我这里没有真实硬件设备，想要验证只能通过QEMU模拟服务器和测试用例来验证，因此这样考虑：

#### 3.5.1 把所有「外部世界」抽成可替换的接口

程序里所有与外部打交道的动作——打开文件、读设备、发网络包——**都不直接调用系统调用**，而是通过两个接口：

| 接口 | 覆盖什么 | 生产实现 | 测试实现 |
|---|---|---|---|
| `LinuxIo` | 文件/设备的 `open`/`ioctl`/`read`/`write` | 真的调系统调用 | 脚本化返回值 |
| `SocketIo` | 网络的 `socket`/`accept`/`recv`/`send` | 真的调系统调用 | 脚本化返回值 |

#### 3.5.2 用 Python 写一份参考实现，逐字对拍

只读 HTTP 接口的输出（Redfish 形状的资源文档、Prometheus 指标文本）有一个特殊要求：

- **格式必须严格固定**，因为监控系统会按固定格式解析。

项目的做法是：用 Python 写一份独立的参考实现（`tools/bmc_manage.py`），让生成器把它的输出固化成 C++ 测试里的「标准答案」（`tests/service_vectors.hpp`），然后断言 C++ 实现**逐字节相同**。

这样虽然麻烦，但是：

- 因为如果只写 C++ 测试并自己填期望值，那测试只是「重复了一遍我的假设」，无法发现「我以为对但其实和真实约定不符」。
- 有一份独立实现做对照，才真的能发现差异。

> 这个机制也确实发挥作用了：它曾暴露出 C++ 侧把 `1e16` 写成
> `10000000000000000`，而 Python 输出 `1e+16`。

#### 3.5.3 三层测试，覆盖不同层次

| 层次 | 手段 | 能验证什么 | 无法验证 |
|---|---|---|---|
| 单元测试 | C++ + 假接口 | 判断逻辑、寄存器解码、状态机、持久化加固 | 真实进程行为 |
| 进程测试 | Python 启动真实程序 | epoll 循环、信号、热加载、真实 socket/TLS | 真实硬件电气行为 |
| 动态检查 | ASan/UBSan/TSan/Valgrind | 内存错误、未定义行为、数据竞争 | 逻辑正确性 |

#### 3.5.4 边界声明

测试全部通过**不等于**可以在真实硬件上直接使用：

- 真实 I2C/GPIO 的电气行为必须在目标板子上验证——虚拟机测不出来。
- 部分芯片寄存器常量标注为「未核实」（未拿到对应数据手册的确定章节），这些在文档和代码注释里都明确标注，不以确定语气呈现。
- 高可用相关的选主/fencing 没有实现，因为自己实现失败模式比不做更危险。
