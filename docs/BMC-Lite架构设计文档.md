## 一、开发原因

### 1.1 BMC 是什么，这个项目做什么

**BMC**（Baseboard Management Controller，基板管理控制器）是服务器主板上的一颗独立芯片。
它的职责很单纯但很关键：**在操作系统无法正常运行的时候，监控机器的物理状态**——温度、电压、风扇转速——出现问题就记录下来。

| 行为 | 解读                                               | 代码入口 |
|---|---|---|
| 采集 | 定时去读温度、电压、风扇转速 | `Monitor::poll` |
| 判断 | 判断这个数值算正常还是危险 | `Engine::update` |
| 记录 | 把发生的事写成日志；重要事件单独存一份「事故档案」 | `Logger`、`SelStore` |
| 恢复 | 危险时尝试救一下（本项目中就是调大风扇） | `RecoveryPolicyEngine`、`Action` |

### 1.2 要解决的问题

| 真实现象 | 这套系统解决的问题 |
|---|---|
| 读数偶发尖峰（探头噪声、单次读取错误） | 风扇乱转、误告警；运维开始忽略告警（「狼来了」效应） |
| 阈值附近的数值抖动 | 状态在正常/危险之间反复横跳，风扇一顿一顿启停 |
| 探头掉线、数值读不到 | 缺失值被静默当成「正常」，监控悄悄失效却看起来一切正常 |
| 故障已经过去 | 没有证据链，事后无法判断当时到底发生了什么 |
| 手工写 PWM 恢复 | 没有冷却、去重与并发上限，可能把硬件写爆 |
| 想在线改一个阈值 | 只能重启监控，等于制造一段监控空白 |
| 磁盘满导致日志写不进去 | 若因此退出，最需要它的时候它反而不在了 |

这个项目绝大部分复杂度，都在解决「如何不被假信号骗到」以及「出错时怎么还能留下证据」。

### 1.3 设计目标与边界

| 目标 | 说明 |
|---|---|
| 单一实现 | 模拟输入和真实硬件**走完全同一条处理链**，不存在「测试用一套、生产用一套」 |
| 无硬件可运行 | 没有真实传感器（如使用 QEMU 虚拟机或纯软件环境）时用模拟序列，整条链路照样跑通 |
| 受控恢复 | 只允许写配置里明确指定的 PWM 文件，不执行任意 shell |
| 有界资源 | 队列、缓冲区、连接数都有上限；上限满时丢弃并计数，不崩溃也不无限增长 |
| 默认不可达 | 全部网络能力默认关闭，不显式开启就不监听任何端口 |
| 只读管理面优先 | 先保证能看见发生了什么，再考虑远程控制；**不要求远程 TCP 也能完整运行** |

这些是**目标**，不是对现状的夸奖。实现到什么程度、哪些没做，
写在第四节 4.4 和 [验证与测试报告](验证与测试报告.md)。

## 二、设计思路

### 2.1 设计主线

把整个设计主线压缩成三步：

```text
第一步 判据：什么样的信号才值得相信？  → 去抖 + 迟滞 + 垃圾值单独处理
第二步 表达：当前到底处于什么状态？    → 四态状态机，只在变化时产出事件
第三步 动作：确认危险之后怎么动手？    → 异步 + 独立策略层 + 默认演练模式
```

### 2.2 难题一：如何不被假信号骗到

#### 2.2.1 去抖（debounce）：连续确认才认账

配置里的 `debounce 3` 意思是：**连续 3 次读到异常，才算真的异常。**

```text
读到 95°C → 可疑，先记下，对外状态仍是 normal
读到 96°C → 第 2 次异常
读到 95°C → 第 3 次异常，达到门槛 → 正式判为 critical
```

如果中间夹了一次正常值，计数**清零重来**。可以根据实际需求调整容错值。

#### 2.2.2 迟滞（hysteresis）：留一段缓冲带，防止边界横跳

假设 `critical = 90`。如果只按「低于 90 就恢复」判断，温度在 89.9 ↔ 90.1 之间抖动时，状态会疯狂来回切换，风扇跟着一顿一顿启停。

**迟滞就是留一段缓冲区间**：`hysteresis 3` 表示**必须降到 87 以下才算真的恢复**。

```text
升上去：90 才算 critical
降下来：87 才算恢复正常      ← 中间的 87~90 保持原状态不动
```

> 迟滞只需要影响**恢复**，不影响**升级**。

#### 2.2.3 读取失败与「垃圾值」必须单独处理

1. **读取失败单独计数**，达到 `failure_limit` 才进入 `unavailable`。探头偶发一次读不到，不应该立刻报「设备失联」。
2. **NaN 与无穷大被当作「读取失败」，而不是「一个数值」。** 原因是 NaN 参与任何比较都返回`false`——如果不管它，它会一路穿过所有阈值判断，最后被静默地当成「正常」。
3.  温度是「越高越危险」，风扇转速是「越低越危险」。代码用乘一个方向系数（`high ? 1 : -1`）把两种方向统一成「越大越糟」，因此判断逻辑只写一份，而不是复制两套。这是典型的架构取舍：**把差异压缩到参数里，而不是复制代码。**

### 2.3 难题二：状态怎么表达

每个传感器独立维护一个状态，只有四个取值：

| 状态 | 含义 |
|---|---|
| `normal` | 正常 |
| `warning` | 警告，需留意 |
| `critical` | 危险，要处理 |
| `unavailable` | **读不到数** |

#### 关键点：`unavailable` ≠ `critical`

这两个是**不同性质**的问题：

- `critical` = 「数值很危险」
- `unavailable` = 「**我根本不知道现在什么情况**」

`unavailable`往往更可怕：探头坏了，你就**失去了监控能力**，而所有危险都可能在无监控状态下发生。所以它必须是独立状态、能独立上报的。

#### 仅当状态真的变了才产出事件

```text
每次采样 → Engine::update(读数)
             ├── 状态没变 → 返回「无事件」（什么都不记）
             └── 状态变了 → 返回一个 Event（旧状态、新状态、当前值、原因、序号）
```

设计原因：

- 如果每一次采样都记录，一天产出的事件是庞大的
- 而实际有效信息都包含在状态改变的时候，状态改变，就相当于传递给我们一个信号

> 时间戳不放在事件里，而是由写档案（SEL）时补上。事件本身只描述「发生了什么变化」。

### 2.4 难题三：动作怎么安全地做

核心思路：**恢复动作永远不在采样线程里执行。**

```text
规则激活
  └─ Worker::submit 提交任务（异步！不阻塞采样）
       └─ RecoveryPolicyEngine::submit
            ├─ 同一(传感器,动作)正在执行？ → 拒绝 "already running"
            ├─ 并发额度满？               → 拒绝 "concurrency limit"
            ├─ 还在 30 秒冷却期内？        → 拒绝 "cooldown"
            ├─ 状态表已满且无可回收？      → 拒绝 "state capacity"
            └─ 通过 → 释放锁 → 执行 Action（最多 3 次尝试，总退避 ≤30ms）
                 ├─ LogOnlyAction：只记日志（默认，dry-run）
                 └─ PwmAction：真的往配置指定的文件写 PWM 值 255
```

**四个拒绝原因分开报的设计思路：** 调用方需要区分「这是重复提交」和「系统忙不过来」，前者应该忽略、后者可能需要扩容。混在一起就无法判断。

### 2.5 关键取舍：考虑过但放弃的方案

**网络通道划分**
- 考虑过：一个端口搞定只读、控制、上行、心跳。
- 放弃原因：一个端口无法按角色分别限流与审计；只读端点会继承写通道的凭证与暴露面。
- 选择：四种通道各自独立监听，默认初始均为关闭。

**主循环怎么等**

- 考虑过：用 `sleep()` 轮询。
- 放弃原因：睡眠期间收不到信号、退出变慢；采样周期还会被信号处理打乱。
- 选择：`timerfd` 交给 `epoll` 统一等待。

**信号怎么处理**
- 考虑过：在信号处理函数里直接干活。
- 放弃原因：信号处理函数里能干的事极少——不能加锁、不能分配内存、不能调用大多数库函数。
- 选择：`signalfd` 把信号变成「可读的数据」。

**硬件通知**
- 考虑过：给所有 hwmon（Linux 的硬件监测接口）都注册中断。
- 放弃原因：绝大多数硬件不支持可靠的中断通知，只能老实轮询。
- 选择：默认轮询，只有 GPIO 这类能独立注册中断的才用事件驱动。

**恢复动作位置**

- 考虑过：主循环里直接写 PWM。
- 放弃原因：几十毫秒的慢动作会拖垮整条采样节奏。
- 选择：交给 `Worker` 线程池异步执行。

**规则状态处理方案**

- 考虑过：热重载时清空并重建。
- 放弃原因：已激活的规则会被当作「还没激活」，于是**重复触发一次恢复动作**。
- 选择：按「规则 id + 触发状态」合并保留。

**已提交的任务**

- 考虑过：支持强制取消。
- 放弃原因：会破坏审计与一致性，且无法安全中断阻塞的系统调用。
- 选择：有界队列 + 明确拒绝，放弃取消功能。

**日志写失败**

- 考虑过：立即退出，避免记录有问题的日志导致日志紊乱。
- 放弃原因：等于「因为记不了笔记就不值班了」，而监控本身更重要。
- 选择：继续监控 + 将其降级上报成一条记录。

**SEL 尾部残缺**
- 考虑过：拒绝启动，或保留残缺不动。
- 放弃原因：一行半截会让后续所有读取解析失败，**污染整个文件**。
- 选择：默认从残缺记录起点截断并记录丢弃字节。

**头文件组织**
- 考虑过：把 `core.hpp` 拆成十几个小文件。
- 放弃原因：会引入大量互相包含与可见性管理，收益只是单文件更短。
- 选择：保留单一公共声明入口。

**高可用**

- 考虑过：自己做选主与 fencing（隔离故障节点）。
- 放弃原因：脑裂防护需要法定人数、外部仲裁与状态对账；做错的后果是「两个实例同时控风扇」。
- 选择：明确不做，写进 4.4 的边界。

### 2.6 完整走一遍：一次温度事件的生命周期

用项目自带的 `config/mock.conf` 配置推演。`cpu_temp` 的配置是：

```text
cpu_temp mock 45,75,76,77,95,96,97,88,87,86,60,59,58,err,err,err,45,45,45 1 high 70 90 3 3 3 -
```

含义：模拟后端、按逗号循环读数、`high`（越大越危险）、warning=70、critical=90、
迟滞=3、连续确认=3 次、失败上限=3 次、`-` 表示不写 PWM。

| 巡房次数 | 读数 | 累计失败 | 判定过程 | 状态 | 写档案 | 触发规则 |
|---:|---:|---:|---|---|:---:|---|
| 1 | 45 | 0 | 正常 | normal | — | 否 |
| 2–4 | 75,76,77 | 0 | ≥70 连续 3 次 | → **warning** | ✅ | 否（规则只针对 critical） |
| … | 95,96,97 | 0 | ≥90 连续 3 次 | → **critical** | ✅ | ✅ 激活 `cpu-critical` |
| … | 88,87,86 | 0 | 在 87~90 迟滞带内 | **仍 critical**（不掉） | — | 已激活，不重复触发 |
| … | 60,59,58 | 0 | < 87，连续 2 次 | → **normal** | ✅ | ✅ 清除 `cpu-critical` |
| … | err×3 | 3 | 失败达上限 | → **unavailable** | ✅ | ✅ 激活 `any-unavailable` |
| … | 45×3 | 0 | 恢复正常 | → **normal** | ✅ | ✅ 清除 |

## 三、架构分层 具体怎么搭起来的

### 3.1 四层结构与依赖方向

四层，依赖方向**严格单向**：上层知道下层，下层完全不知道上层。

| 层 | 一句话职责 | 关键约束 |
|---|---|---|
| **domain**（领域） | 纯逻辑判断：算几级、要不要触发规则 | **不接触文件、不接触设备、不接触网络** |
| **hardware**（硬件） | 真的去读设备 | 所有系统调用经统一接口转发 |
| **infrastructure**（基础设施） | 拧螺丝：描述符、定时器、信号、日志、线程池 | 通用、与业务无关 |
| **application**（应用） | 把上面三层拼起来，管进程生命周期 | 只有它知道整个程序怎么启动和停止 |

各层的代表文件：

- **domain**：`engine.cpp`、`rules.cpp`、`calibration.cpp`
- **hardware**：`readers.cpp`、`chips.cpp`
- **infrastructure**：`fd.cpp`、`logger.cpp`、`sel.cpp`、`worker.cpp`、`event_bus.cpp`
- **application**：`main.cpp`、`monitor.cpp`、`config.cpp`、`cli.cpp`

**为什么这个方向很重要？** 因为 `domain` 层不依赖任何外部东西，所以它可以在没有硬件、
没有文件、没有网络的机器上完整测试。项目里测试覆盖最密集的就是这一层。

依赖方向还有一个具体好处：`Monitor` 只依赖 `EventLogger` 这个接口，
生产实现是 `Logger`，测试可以换成记录型实现，不必创建真实日志文件。

### 3.2 一次采样在四层之间怎么流动

```text
配置文本（hardware.conf / rules.conf）
   │ application：config.cpp 解析并校验 → Config / FaultRule
   ▼
main.cpp：为每路传感器构造 MonitorSensor = Config + Device + Engine
   │
   │ timerfd 到期（epoll 通知）
   ▼
Monitor::poll
   ├─ hardware：Device::read_value → Reader::read → LinuxIo
   │    后端五选一：mock / sysfs / i2c / gpio / i2c:<chip>[@<feature>]
   ├─ domain：Engine::update(读数) → 状态迁移，或「无变化」
   ├─ infrastructure：Logger 落盘、SelStore 追加、EventBus 入队
   ├─ domain：FaultRuleEngine::evaluate(事件) → RuleDecision 列表
   └─ infrastructure：Worker::submit → RecoveryPolicyEngine::submit → Action
```

读这张图只要盯两件事：**箭头只往下**（domain 从不反向调用网络或设备），
以及**所有落盘都发生在 infrastructure 层**（domain 层只产出「该记什么」）。

### 3.3 一个刻意的例外：`core.hpp`

`include/bmc/core.hpp` 一个头文件里塞了 20 多个类型（当前 408 行）。按教科书标准这是
「上帝头文件」、应该按类型拆开成十几个小文件。**但这里是故意不拆的**，理由记录在
`docs/代码阅读指南.md`：

> 保留 core.hpp 作为兼容的公共声明入口，避免一次引入大量互相包含的头文件。

这是一个**有意识的取舍**：牺牲「单文件整洁」，换取「不用处理一堆头文件互相 include 的
麻烦」。代价是 `core.hpp` 偏长，读的时候建议配合目录结构定位。

### 3.4 并发模型：一个主线程加三个「外人」

这是全项目并发设计的核心，也是理解「为什么这个程序不会卡住」的关键。

#### 3.4.1 主循环：一个人守着一台交换机

程序主体是一个单线程事件循环。它把所有需要等待的东西**登记**给 Linux 的事件通知器
`epoll`，然后等 `epoll` 告诉它「哪个有动静了」。

```text
        ┌───────────── epoll（统一事件分发）─────────────┐
        │                                               │
   timerfd              signalfd                  GPIO（可选）
  （定时器响）        （收到信号）               （线电平跳变）
        │                    │                        │
   采样一次             SIGHUP → 重载配置          立刻额外采样一次
                        SIGTERM → 准备退出
```

三个登记项，每个都有「为什么这样选」（完整对照见 2.5 的取舍清单）：

- `timerfd`：定时触发采样。**不能用 `sleep()`**——睡眠期间收不到信号，退出会变慢，
  而且采样周期会被信号处理打乱。
- `signalfd`：把信号变成「可读的数据」。**信号处理函数里能干的事极少**
  （不能加锁、不能分配内存、不能调用大多数库函数）；转成普通事件后，
  就能在主循环里安全地处理。
- GPIO：线电平变化的中断。**默认不用**——绝大多数硬件（hwmon）不支持可靠的中断通知，
  只能老实轮询；只有 GPIO 这类能独立注册中断的才值得用事件驱动。

**主循环只做采样和状态判断，绝不干重活。** 这是硬约束：调风扇这种慢操作
（可能要几十毫秒）如果放在主循环里，整条采样节奏就被拖住了——一个坏掉的风扇
能让监控停摆。

主循环还有一个容易被忽略的细节：每轮 `epoll_wait` 之前先检查网络监听线程是否失败，
以及 `worker_failed` 标志；1 秒超时只是兜底唤醒，正常情况下由 `timerfd` 或
`signalfd` 驱动。

#### 3.4.2 三个「外人」：只读 HTTP、控制面、实例心跳

这三项网络能力各自开**独立线程 + 自己的 `epoll`**，和主循环并行运行。
但它们受三条铁律约束：

**铁律一：绝不直接碰传感器对象，只能读「加锁的快照」。**

为什么这么严？因为**热加载会整个换掉传感器对象**。如果网络线程抓着一个旧对象的引用，
那就是野指针——程序会随机崩溃，而且极难复现。所以网络线程能看到的只有两样东西：
SEL 的快照、以及配置的快照，两样都是加锁拷贝出来的。

**铁律二：网络线程里绝不能直接写硬件。**

控制面收到「调大风扇」的请求时，必须把它扔进 `Worker` 任务队列，走和自动恢复
**完全同一条**恢复引擎。这样冷却、去重、并发限制、审计这些保护**自动全部生效**。
如果图省事绕过它直接写 PWM，那所有保护就都失效了——这是架构上最不能妥协的一条。

**铁律三：默认全部关闭。** 不给出对应开关，**连监听端口都不创建**。

#### 3.4.3 为什么不用「一个端口搞定所有事」

四种网络需求（只读管理、控制面、上行遥测、实例心跳）的信任级别完全不同：

| 通道 | 方向 | 信任前提 | 要认证吗 | 出问题的后果 |
|---|---|---|---|---|
| 只读管理 | 入站 | 低 | 不需要 | 只影响可观测性 |
| **控制面** | 入站 | **高** | **必须** | **可造成物理动作** |
| 上行遥测 | 出站 | 中 | 采集器侧 | 不得影响采样 |
| 实例心跳 | 双向 | 高（对等） | 双向 | 可导致脑裂 |

合并成一个端口的代价是具体的：**一个端口无法按角色分别限流和审计**。
只读端点会继承写通道的凭证与暴露面；慢采集器会波及控制面重试；
实例间协议会变成「任何对等体都能改风扇」的后门。所以宁可多几个端口。
端口划分与信任模型的完整论证见 [网络设计说明](网络设计说明.md)。

### 3.5 安全设计：默认什么都不能干

#### 3.5.1 默认全关，且 fail-closed

| 能力 | 默认 | 怎么开启 |
|---|---|---|
| 写 PWM（真的调风扇） | **不写**，只记日志（dry-run） | `--enable-actions` |
| HTTP 只读接口 | 不监听 | `--http-port` |
| 控制面（能触发动作） | 不监听 | 端口 **和** 令牌文件，两个都必须给 |
| 实例心跳 | 不监听 | 四个参数必须齐全 |

**「fail-closed」的意思是：配置不全就拒绝启动，而不是降级成「裸奔但绑本地」。**
比如控制面只给了端口没给令牌文件——程序直接报错退出，
**不会开一个「不用密码的控制端口」**。这种习惯在安全领域叫「失败时选择关闭而非打开」。

默认全关还有一个实际好处：**不开启这些功能时，程序的攻击面和完全不做网络功能时一模一样。**

#### 3.5.2 只允许写「配置里指定的那一个文件」

「不执行任意 shell」和「不允许控制请求指定文件路径」是配套的两条。

控制请求只能传**传感器名字**和**动作名**，真正的文件路径来自服务器自己的配置。
否则只要能构造一个请求让它写 `/etc/passwd`，整个系统就完蛋了。
代码里额外加 `O_NOFOLLOW`（拒绝跟随符号链接）只是**最后一道防线**，
防止有人用软链接把路径偷偷拐到别处。

#### 3.5.3 令牌（密码）的处理细节

控制面用一个文件里的长随机字符串做认证。为什么不用命令行参数传？
**因为命令行参数会出现在 `ps` 输出和系统日志里**，等于公开密码。

文件本身也有硬性要求：

| 要求 | 原因 |
|---|---|
| 必须是普通文件、不能是符号链接 | 防止被指向别处 |
| 权限必须**严格**是 `0640` | 太宽（别人能读）不行；`0644`/`0666` 直接拒绝启动 |
| 属主必须是运行这个服务的账户 | 防止别人替换 |
| 长度 32~512 字符 | 太短不安全；太长放不进 HTTP 头部 |
| 比对时用**常数时间**算法 | 见下 |

**「常数时间比较」是什么、为什么要它？** 普通字符串比较是「发现第一个不同字符就返回」，
所以比较耗时**隐含地泄漏了正确密码的前缀信息**——攻击者可以通过测量响应时间
一个字符一个字符地猜出密码。常数时间比较从头扫到尾、不看内容差异提前返回，
从而不泄漏这类信息。

#### 3.5.4 恢复动作的自我保护

| 机制 | 取值 | 为什么 |
|---|---|---|
| 冷却窗口 | 30 秒 | 风扇转速不会瞬间响应，每秒发一次会把硬件写爆，还掩盖真实情况 |
| 同一传感器去重 | 是 | 同一个动作不该重复提交 |
| 重试上限 | 3 次 | 避免一个坏设备把线程池占死 |
| 总退避预算 | ≤30 毫秒 | 即使失败要重试，也不能长期占用工作线程 |
| 队列满 | **记录拒绝事件** | 不静默丢弃——「没能处理」本身是需要知道的信息 |
| 状态表上限 | 4096 条 | 防止状态无限增长；执行中或冷却中的状态绝不淘汰 |

#### 3.5.5 明确不做危险操作

**远程重启、关机、硬件 reset** 是 BMC 的标准功能，但也是**最危险的**——一条错误指令
就能让服务器下线。本项目主动不做这类动作，把风险从设计上排除，而不是靠「小心使用」。

### 3.6 可靠性：宁可降级，不可消失

这一节体现的是工程成熟度。核心原则：**区分「能继续工作」和「必须停下来」。**

| 场景 | 行为 | 为什么 |
|---|---|---|
| 某次采样读失败 | **不退出**，累计失败次数 | 探头偶发故障不该让整个监控死掉 |
| 读失败达上限 | 进入 `unavailable` 并报告 | 单独的状态，不伪装成正常 |
| 配置文件写错 | **阻止启动** | 带着错配置跑，比不跑更危险——你会以为它在监控，其实没有 |
| 日志写入失败 | **只计数 + 上报降级，不退出** | 见 3.6.1 |
| 档案（SEL）写入失败 | 同上，另把失败计数写进档案 | 见 3.6.1 |
| 收到 SIGTERM | 有序停止：先排空已接受的任务，再退出 | 不能丢掉已经开始处理的活 |
| 退出时缓冲区仍未落盘 | 返回非零码 + 在错误输出说明原因 | 让 systemd 知道这次不正常 |

#### 3.6.1 为什么日志写失败不退出

日志是**证据**，但监控本身更重要。如果因为磁盘满就退出，等于「因为记不了笔记所以
不值班了」——这显然更糟。所以设计成：继续监控，但把「我的日志正在丢」这件事
**上报成一条降级记录**。

这里有个很容易做错的细节：**降级告警不能写回那个已经失败的日志**。
否则会形成反馈循环：写失败 → 产生一条告警 → 告警也写失败 → 又产生一条告警……
所以降级信息走的是 SEL 和事件总线，不走日志本身。

降级上报还有节流：日志降级最多每 5 秒报一次，SEL 降级只在失败计数增长时报一次。
否则持续失败会变成「每个采样周期刷一条降级记录」的新问题。

#### 3.6.2 两份记录，用途不同

| | 日志（Logger） | 档案（SEL） |
|---|---|---|
| 内容 | 所有事件的流水账 | 只记状态变化与恢复动作 |
| 用途 | 排查问题 | **故障证据** |
| 落盘策略 | 批量合并写（每 4096 字节一次），默认不强制同步 | 立即 `write` + `fdatasync` |
| 崩溃时可能丢 | 最后一批（可接受） | 不丢（必须留存） |
| 满了怎么办 | 按大小轮转，保留若干份 | 只保留最近 4096 条，超出时重写文件压缩 |
| 文件格式 | 每行一条 JSON | 每行一条文本记录，字段带引号 |

**为什么要分开？** 因为两者的「证据价值」不同。日志是过程记录，丢几条无所谓；
档案是「故障发生过」的凭据，可能用于追责或分析根因，必须落盘。

#### 3.6.3 崩溃后的自我修复

档案文件如果因为断电在**最后一条记录写到一半**时中断，重启后会发现「尾部有残缺」。
默认行为是**从残缺记录的起点截断**，然后继续追加，并记录「丢弃了多少字节」。

为什么默认截断而不是保留？因为残缺的行留在文件中间会让后续所有读取解析失败——
**一行半截会毒化整个文件**。当然这个行为是可选策略（`Truncate::refuse` 可以改成
「只追加不回退」，宁可无法解析也不丢字节）。

### 3.7 配置与热加载

#### 3.7.1 配置分成两类文件

| 文件 | 内容 | 改动频率 |
|---|---|---|
| `hardware.conf` | 有哪些传感器、后端、阈值、动作目标 | 换硬件才改 |
| `rules.conf` | 什么状态触发什么动作 | 调策略时改 |

分开的理由：调整告警策略不该冒着写错传感器路径的风险。

#### 3.7.2 热加载：不重启就换配置

运维现实是「不能为了改一个阈值就重启监控」。所以支持发一个信号（`SIGHUP`）让程序
重新读配置。但这件事有几个必须做对的地方：

**第一，先全部校验完，再动任何状态。**

```text
收到 SIGHUP
  ├─ 解析新传感器配置 + 解析新规则
  ├─ 两者全部校验通过？
  │    ├─ 否 → 记一条 "reload rejected; keeping generation N"，保持旧配置不动
  │    └─ 是 → 发布 "validated generation N+1" → 替换 → 刷新缓存 → 完成
```

如果边解析边替换，中途失败就会留下「传感器换了一半、规则还是旧的」这种四不像状态，
比拒绝重载糟糕得多。

**第二，规则状态要「合并」而不是「清空」。**

这是最容易忽略、但用户最能感知的细节。假设某规则已经激活（风扇正在高速运转），
此时你只改了一个**无关**的阈值并重载——如果规则状态被清空，程序会认为
「这条规则还没激活」，然后**再触发一次恢复动作**。

所以重载时按「规则 id + 触发状态」判断哪些状态可以保留：

| 情况 | 保留状态？ |
|---|---|
| 规则 id 和触发状态都没变 | ✅ 保留确认计数与激活标志 |
| 规则的触发状态被改了（比如 critical 改成 warning） | ❌ 丢弃（旧的激活标志对应的是不同条件） |
| 规则被删除 | ❌ 丢弃 |
| 传感器消失了 | ❌ 丢弃 |

**第三，配置代次（generation）。** 每次成功重载，代次加一。
这个数字会通过网络接口暴露，让自动化工具能确认「我改的配置真的生效了」。
实例心跳之间也交换这个数字，用来互相判断对方是不是还活着、配置是否一致。

### 3.8 如何做到可以在没有硬件的情况下验证

这是本设计里回报最高的部分：把外部世界抽成可替换接口之后，硬件解码、
协议解析、状态机这些最容易写错又最难测的逻辑，都能在普通机器上完整验证。

#### 3.8.1 把所有「外部世界」抽成可替换的接口

程序里所有与外部打交道的动作——打开文件、读设备、发网络包——**都不直接调用系统调用**，
而是通过两个薄接口：

| 接口 | 覆盖什么 | 生产实现 | 测试实现 |
|---|---|---|---|
| `LinuxIo` | 文件/设备的 `open`/`ioctl`/`read`/`write` | 真的调系统调用 | 脚本化返回值 |
| `SocketIo` | 网络的 `socket`/`accept`/`recv`/`send` | 真的调系统调用 | 脚本化返回值 |

**为什么这个抽象值得做？** 因为 I2C 芯片的寄存器解码、GPIO 的线值读取、TCP 的分包重组
这些逻辑**很容易写错，但很难测**——总不能为了写单测去插一块真的温度传感器。

有了这层抽象，测试可以构造「芯片返回了 0xFFF8」这样的场景，然后断言
「解析出来是 −0.125°C」。**芯片寄存器解码、地址校验、能力位拒绝、PWM 写入失败路径
这些以往最难测的逻辑，因此都能在普通机器上完整测试**，不需要插一块真的传感器。

代价是每次调用都多一层间接，但相比「无法测试」，这个代价微不足道。

#### 3.8.2 用 Python 写一份参考实现，逐字对拍

只读 HTTP 接口的输出（Redfish 形状的资源文档、Prometheus 指标文本）有一个特殊要求：
**格式必须严格固定**，因为监控系统会按固定格式解析。

项目的做法是：用 Python 写一份独立的参考实现（`tools/bmc_manage.py`），
让生成器把它的输出固化成 C++ 测试里的「标准答案」（`tests/service_vectors.hpp`），
然后断言 C++ 实现**逐字节相同**。

**为什么要这么麻烦？** 因为如果只写 C++ 测试并自己填期望值，那测试只是
「重复了一遍我的假设」，无法发现「我以为对但其实和真实约定不符」。
有一份独立实现做对照，才真的能发现差异。

> 这个机制也确实发挥作用了：它曾暴露出 C++ 侧把 `1e16` 写成
> `10000000000000000`，而 Python 输出 `1e+16`。

#### 3.8.3 三层测试，覆盖不同层次

| 层次 | 手段 | 能验证什么 | 不能验证什么 |
|---|---|---|---|
| 单元测试 | C++ + 假接口 | 判断逻辑、寄存器解码、状态机、持久化加固 | 真实进程行为 |
| 进程测试 | Python 启动真实程序 | epoll 循环、信号、热加载、真实 socket/TLS | 真实硬件电气行为 |
| 动态检查 | ASan/UBSan/TSan/Valgrind | 内存错误、未定义行为、数据竞争 | 逻辑正确性 |

**这三层不可互相替代。** 单元测试再全，也测不出「收到 SIGTERM 时线程没排空」；
进程测试再真实，也跑不出真实温度传感器的电气特性。

#### 3.8.4 诚实的边界声明

测试全部通过**不等于**可以在真实硬件上直接使用：

- 真实 I2C/GPIO 的**电气行为**必须在目标板子上验证——虚拟机测不出来。
- 部分芯片寄存器常量标注为「**未核实**」（未拿到对应数据手册的确定章节），
  这些在文档和代码注释里都明确标注，**不以确定语气呈现**。
- 高可用相关的选主/fencing 没有实现，因为自己实现失败模式比不做更危险。

**把边界写清楚，比假装没有边界更专业。**

## 四、优缺点与适配性 这套设计的评价

**本节要讲什么**：前面讲了「为什么这么想」与「怎么搭的」，这里给出评价——
好在哪、代价是什么、以及为什么它恰好适合这个项目。

### 4.1 优点

| 优点 | 具体体现 | 对使用者的实际意义 |
|---|---|---|
| 判断逻辑可离线测试 | `domain` 层零外部依赖，硬件与网络都注入 | 改阈值算法不必上真机，回归速度快 |
| 默认不可达 | 所有网络能力默认关闭；控制面必须端口 + 令牌成对给出 | 不配置就完全没有新的攻击面 |
| 故障时降级而非消失 | 读失败累计、日志与档案失败只计数并上报 | 最需要它的时候它还在跑 |
| 行为可解释 | 状态只有四档、只在变化时产出事件、拒绝原因分开报 | 日志量可控，能直接定位原因 |
| 配置即契约 | 阈值、方向、窗口、标定、动作路径全在文本里 | 代码里没有机型常量，换硬件不改代码 |
| 单一处理链 | mock 与真实硬件走同一条链 | 不存在「演练通过、生产走另一套」的漂移 |
| 资源有界 | 队列、缓冲区、连接数、状态表都有上限且有明确溢出行为 | 不会因为输入异常而无限增长 |
| 恢复动作统一入口 | 自动恢复与控制面手动动作走同一个引擎 | 冷却、去重、并发、审计自动全覆盖 |

### 4.2 代价与缺点

诚实地列出这套设计付出了什么。**每一条都是真实存在的成本，
不是「潜在的小问题」。**

| 代价 | 具体表现 | 为什么仍然接受 |
|---|---|---|
| 多一层间接 | 每次设备访问都经 `LinuxIo`，读代码要跳一层 | 换来最难测的逻辑可测 |
| `core.hpp` 偏大 | 408 行、20 多个类型集中在一个文件 | 换来不用处理头文件互相包含 |
| 实现文件偏集中 | 所有后端挤在 `readers.cpp`（381 行） | 后端共享大量路径解析与错误分支 |
| 默认更保守 | 不显式开 `--enable-actions` 不会调风扇 | 容易以为「没生效」，但比误写硬件好 |
| 网络能力各自独立 | 端口、参数、线程都变多，运维面变宽 | 换来按角色限流与审计 |
| 没有真正的高可用 | 单进程；日志与档案都假定单一写者 | 见 4.4，自己实现选主比不做更危险 |
| 档案没有校验和 | 只能修尾部残缺，中间位翻转检测不到 | 换来简单且可人读的文本格式 |
| 测试通过 ≠ 可上真机 | I2C/GPIO 电气行为、部分寄存器常量未核实 | 如实标注，验证责任交给实机测试 |

### 4.3 为什么它恰好适配这个项目

这一节把「项目约束 → 设计选择」对应起来。**很多设计不是审美偏好，
而是被约束逼出来的。**

| 项目约束 | 对应的设计选择 | 如果不这样做会怎样 |
|---|---|---|
| 单机守护进程，无集群 | 单进程 + 进程内 `EventBus`，无消息队列 | 引入中间件就多了部署依赖与故障点 |
| 不能要求预装中间件 | 只用 libstdc++ 与 pthread；仅 TLS 需要 OpenSSL | 现场机器装不了东西就起不来 |
| 经常在无硬件的机器上跑 | `LinuxIo`/`SocketIo` 注入 + `mock` 后端 | 无法在 CI 与虚拟机里验证逻辑 |
| 运行账户权限低 | 默认全关、动作白名单、只写配置指定的文件 | 一次误配置就可能造成物理影响 |
| 长年无人值守 | 有界资源 + 降级而非退出 + 尾部自修复 | 一个磁盘满或一行残缺就让服务永久起不来 |
| 需要事后追溯 | 日志与 SEL 分离，关键记录立即 `fdatasync` | 断电后没有证据，原因查不清 |
| 要求改配置不重启 | `SIGHUP` 原子重载 + 状态合并 + 代次 | 每次调阈值都制造一段监控空白 |
| 小团队、无框架预算 | 不引入依赖注入框架，接口集中在少数文件 | 框架本身成为需要学习和维护的对象 |

> 结论：这套架构的适配性来自**明确的自我限制**——它不试图成为通用监控平台，
> 而是把「单机、无依赖、可无硬件运行、默认安全」这四个约束做到位。

### 4.4 边界与明确不做的事

| 不做 | 原因 |
|---|---|
| 完整 Redfish / RMCP+ / IPMI | 只实现了 Redfish 形状的只读子集 |
| 选主、fencing、故障切换 | 脑裂防护需要法定人数、外部仲裁与状态对账；自己做错的后果比不做更危险 |
| 固件 A/B 升级 | 不在范围内 |
| SSE / WebSocket 推送 | 只做请求-响应 |
| 远程重启 / 关机 / reset | 最危险的功能，主动排除 |
| 强制取消已提交的任务 | 会破坏审计与一致性；改为「有界队列 + 明确拒绝」 |
| SEL 的 CRC 与断电事务 | 只做尾部残缺修复，中间位翻转无法检测 |
| 多写者协调 | 日志与档案都假定单一写者（本进程） |
| 任意 shell 命令执行 | 恢复动作是白名单枚举，不是通用执行器 |

## 五、术语表

| 术语 | 通俗解释 |
|---|---|
| **BMC** | 服务器上独立管理硬件的芯片；本项目是它的核心逻辑的软件实现 |
| **采样 / tick** | 一次「巡房」：读一遍所有传感器 |
| **去抖 debounce** | 连续 N 次异常才算异常，防偶发误报 |
| **迟滞 hysteresis** | 恢复时要求比触发时更「远离」阈值，防边界抖动 |
| **阈值 threshold** | 判断正常/警告/危险的警戒线 |
| **SEL** | System Event Log，系统事件档案；只记状态变化与恢复动作 |
| **PWM** | 控制风扇转速的信号；写入 0~255 的数值 |
| **dry-run** | 演练模式：只记录「本来会做什么」，不真的动手 |
| **fail-closed** | 配置不完整就拒绝启动，绝不降级成「不安全但能用」 |
| **epoll** | Linux 的事件通知机制；一个线程可以同时等很多东西 |
| **fd / 文件描述符** | Linux 里「打开的东西」的编号（文件、socket、设备都算） |
| **RAII** | C++ 惯用法：资源在对象析构时自动释放，不靠手写清理 |
| **注入 / 可注入接口** | 把「怎么访问外部世界」做成参数，测试时换成假的 |
| **对拍** | 两份独立实现比输出，用来发现单方无法发现的错误 |
| **令牌 token** | 相当于密码的长随机字符串 |
| **常数时间比较** | 比较耗时不随内容变化，避免通过时间差猜密码 |
| **工作队列 / Worker** | 后台线程池；耗时的活扔进去，不阻塞主循环 |
| **有界队列** | 有容量上限的队列；满了有明确行为（丢弃并计数） |
| **代次 generation** | 配置版本号，每次成功热加载加一 |
| **冷却窗口 cooldown** | 同一动作在这段时间内不重复执行 |
| **domain / hardware 层** | 领域层只做纯判断；硬件层负责真正读设备 |
| **快照 snapshot** | 加锁复制出来的一份数据副本，拿到它就不怕热加载换对象 |
