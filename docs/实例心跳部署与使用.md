# 实例心跳部署与使用

一句话定位：本文回答"多实例部署时，怎么知道对端实例还活着、两台机器加载
的配置是不是同一版"。适合首次部署对等心跳的运维人员，以及需要改动
`src/peer.cpp` 的二次开发者。

先解释四个术语：

- **心跳**：两个实例按固定间隔互发一个很小的 HTTP 请求并收回响应，用来
  证明"对面还活着"。它是存活信号，不是业务数据通道。
- **代次 generation**：配置版本号，从 1 开始，每成功热重载一次就加 1。
  两边代次相同，说明看到的是同一版配置。
- **陈旧 stale**：超过 `stale_ms` 没有收到任何有效心跳，就判定对端陈旧。
- **对等通道**：本文的心跳通道，使用独立端口与独立令牌，默认关闭。

## 一、为什么需要它

硬件监测守护进程通常只从本机视角看世界：它知道自己读了哪些传感器、改过
哪些风扇。一旦把同一套服务部署成两个实例，就会冒出两个新问题：

1. 对端实例还活着吗？进程被杀、网线被拔、对端机器断电，本机都看不出来。
2. 两台机器加载的是同一版配置吗？只在一台上热重载，两台就会按不同阈值
   动作，故障证据也对不上。

没有心跳时，这两个问题只能靠人登录每台机器查日志，故障发现的延迟等于人的
巡检周期。更糟的是"看起来正常"的假象：本机指标一切正常，坏掉的对半却被
完全忽略。

多实例的常见做法是"选主 + fencing"：选出一个主节点，其余节点被隔离
（fencing 指强制切断故障节点的电源或网络，防止它继续写共享资源）。本项目
**只做心跳与代次交换，不做选主、不做 fencing**，原因是这类逻辑的失败模式
比不做更危险：误判一次就可能把仍然健康的节点踢出服务。本项目保护的是同一
台机器上的硬件，宁可保留两个都在跑的实例，也不要一个会杀错人的仲裁者。

## 二、设计思路

**核心目标**：只回答"对端是否活着"和"对端代次是多少"，并且从结构上保证
这条通道永远不会触发硬件动作。

关键取舍如下。

- **独立端口与独立令牌**：心跳用 `--peer-listen-port` 单独监听，令牌来自
  单独的 `--peer-token-file`。控制面是唯一能触发硬件动作的入口，如果两者
  共用端口或令牌，等于把"改风扇转速"的权限复制给了存活探测通道。
- **结构上不持有 Worker、Action 和设备**：`PeerHeartbeat` 只保存地址、令牌、
  代次与时间戳。没有 Action 引用，就不存在"心跳触发硬件动作"的代码路径；
  这是用类型排除可能，而不是靠口头约定。
- **出站强制校验证书链与主机名**：构造 `PeerHeartbeat` 时，非回环对端必须
  同时提供 CA 与服务器名，缺一即抛异常。代码里没有"跳过验证"开关：如果
  允许不验证，攻击者就能伪造心跳，让本机误以为对端健康。
- **一次交换一条连接**：出站请求带 `Connection: close`，收到合法响应后立即
  断开，不留复用状态。存活判断因此基于"刚刚完成了一次真实往返"，而不是
  "旧连接还没报错"。

方案对比：下面这些做法都考虑过，也都有明确的放弃理由。

| 方案 | 为什么放弃 |
|---|---|
| 与控制面共用端口和令牌 | 心跳凭证会等价于硬件动作权限 |
| 心跳携带配置并自动应用 | 一台实例被攻陷即可改写另一台的硬件策略 |
| 在心跳里做选主与 fencing | 误判会踢掉健康节点，代价高于不做 |
| 长连接加定期 ping | 半开连接会被误判为存活，还需额外超时逻辑 |

## 三、具体实现

### 3.1 参数与约束

| 参数 | 含义 | 约束与默认值 |
|---|---|---|
| `--peer-address` | 对端 IPv4 地址 | 必填；只接受 IPv4 字面量 |
| `--peer-port` | 对端端口 | 必填，1..65535 |
| `--peer-listen-port` | 本机监听端口 | 必填，1..65535 |
| `--peer-bind` | 本机监听地址 | 默认 `127.0.0.1`，只要 IPv4 字面量 |
| `--peer-token-file` | 双方共享的心跳令牌 | 必填 |
| `--peer-interval-ms` | 心跳间隔 | ≥10，默认 1000 |
| `--peer-stale-ms` | 判定陈旧的超时 | 必须严格大于 interval，默认 5000 |
| `--peer-ca` | 校验对端证书的 CA | 与 server-name 成对；非回环出站必填 |
| `--peer-server-name` | 对端证书中的主机名 | 同上 |
| `--peer-tls-cert` | 本机监听证书 | 与 `--peer-tls-key` 成对；非回环监听必填 |
| `--peer-tls-key` | 本机监听私钥 | 同上 |

只要出现任意一个 `--peer-*` 选项，`--peer-address`、`--peer-port`、
`--peer-listen-port`、`--peer-token-file` 四项就必须齐全，否则命令行解析
直接失败（退出码 2）。

令牌文件由 `load_control_token()` 校验：必须是当前有效用户拥有的普通文件、
权限恰好 0640、打开时带 `O_NOFOLLOW`（拒绝符号链接）、内容是 32..512 个
可打印非空格字符，允许一个结尾换行。建议生成 64 位十六进制随机令牌。

### 3.2 协议

| 项目 | 内容 |
|---|---|
| 方法 | `GET` |
| 路径 | `/v1/heartbeat` |
| 请求头 | `Authorization: Bearer <token>` |
| 请求头 | `X-BMC-Generation: <十进制非 0 整数>` |
| 请求体 | 必须为空 |
| 成功响应 | `200 OK`，`text/plain`，正文是本机当前代次加一个换行 |

代次必须是完整消费的十进制数：空串、负号、尾随字符、`0` 都判非法。

### 3.3 状态码顺序：令牌先于路径

**先校验令牌，再校验路径**：`Authorization` 缺失或令牌不匹配时一律返回
`401 Unauthorized`；同一来源 IP 连续失败触发限流后返回
`429 Too Many Requests`；只有令牌正确、但方法、路径、请求体或
`X-BMC-Generation` 不合法时，才返回 `400 Bad Request`。

顺序这样定，是因为两类错误的责任方不同：401/429 说明"你不是可信对端"，
400 说明"你是可信对端，但请求写错了"。把路径检查放在令牌之前，未认证的
扫描者就能靠状态码差异探出本机支持哪些路径。

限流是令牌桶：容量 5、每秒补充 0.2 个令牌，也就是突发 5 次失败后大约每
5 秒才放行一次；限流键是来源 IP（不含端口），换源端口无法绕过。凭证正确
但请求不合法不会消耗认证令牌桶，也不会污染计数。

### 3.4 状态机、时限与上限

- 出站线程以 10 ms 周期驱动状态机，一次交换依次是：连接、TLS 握手、
  发请求、收响应、断开。
- 整个交换共享一个**绝对期限** `min(5 秒, stale_ms)`：零碎的可写事件不能
  延长它。重试间隔为 `interval_ms`，到点才发起下一次心跳。
- 收发都非阻塞：`EAGAIN` 只表示本轮没有进展，下一轮继续，不阻塞进程。
- 每个实例同时只有一条在途出站交换，不积压任务。
- 入站并发连接上限为 8，超出直接关闭并计入网络指标。
- 出站响应累积超过 8 KiB 视为异常响应，断开并计一次失败。
- `stop()` 最多等一个 10 ms 周期，关机不会因为心跳线程卡住。

### 3.5 陈旧与恢复各只上报一次

`stale` 是**锁存**状态：`now - last_seen >= stale_ms` 只在跨越阈值的那一次
上报 `peer stale generation=N`，之后不再重复刷屏。恢复同理，只有从陈旧
回到新鲜的那一次才上报 `peer recovered generation=N`。

`last_seen` 在对象构造时初始化为当前时刻，因此**启动即开始计时**：即使一次
有效心跳都没收到过，也会在 `stale_ms` 之后报陈旧。有效的入站请求与经过
验证的出站响应都会刷新存活时间。

上报通过事件总线发出（类型 `service`，来源 `peer`），因此会同时出现在 SEL、
动作日志和上行遥测里。

### 3.6 指标

启用只读 HTTP 后，`/metrics` 追加下列内容：

| 指标 | 含义 |
|---|---|
| `bmc_peer_stale` | 是否已判定对端陈旧，1/0 |
| `bmc_peer_generation` | 最近一次观测到的对端代次，未观测到为 0 |
| `bmc_peer_heartbeats_total` | 有效心跳数（入站合法请求 + 验证通过的响应） |
| `bmc_peer_failures_total` | 出站交换失败次数 |
| `bmc_requests_total{role="peer",...}` | 心跳监听按方法与状态码统计的请求数 |
| `bmc_request_bytes_total{role="peer",...}` | 心跳监听的收发字节数 |

`bmc_peer_generation` 只是观察值：对端代次**不会**被自动复制到本机配置。

### 3.7 本机两实例配置示例

在仓库根目录生成令牌；两个进程必须使用相同令牌。令牌必须属于运行账户，
权限严格 0640，是普通文件且不是符号链接。

```sh
mkdir -p var/peer-demo
openssl rand -hex 32 > var/peer-demo/token
chmod 0640 var/peer-demo/token
# 终端 A：
./build/bmc-lite --config config/mock.conf --rules config/rules.conf \
  --log var/peer-demo/a.log --sel var/peer-demo/a.sel --http-port 8001 \
  --peer-address 127.0.0.1 --peer-port 9002 --peer-listen-port 9001 \
  --peer-token-file var/peer-demo/token --peer-interval-ms 1000 --peer-stale-ms 5000
# 终端 B：
./build/bmc-lite --config config/mock.conf --rules config/rules.conf \
  --log var/peer-demo/b.log --sel var/peer-demo/b.sel --http-port 8002 \
  --peer-address 127.0.0.1 --peer-port 9001 --peer-listen-port 9002 \
  --peer-token-file var/peer-demo/token --peer-interval-ms 1000 --peer-stale-ms 5000
# 终端 C：
curl -s http://127.0.0.1:8001/metrics | grep bmc_peer
```

终止 B，超过 5 秒后 A 的 `bmc_peer_stale` 为 1，SEL、日志与事件总线记录
`peer stale`；重新启动 B 后记录 `peer recovered`。对 B 发 SIGHUP 后，A 的
`bmc_peer_generation` 更新。计时从启动开始，没有任何有效心跳也会超时；
重复失联不会反复刷屏。

### 3.8 跨虚拟机 TLS 部署

先按 README 安装两个实例，再按 [控制面部署与使用](控制面部署与使用.md)
的证书步骤，分别为各自 IP 生成带 SAN 的证书。心跳使用自己的令牌文件，
例如 `/opt/bmc-lite/control/peer-token`，同一内容以服务账户所有、0640
分别安装。不要把它用作控制令牌。

将 A 的公开证书复制到 B 作为 `peer-ca.pem`，B 的公开证书复制到 A；私钥
留在各自服务器。内部 CA 环境使用 CA 文件替代自签证书。所有文件放在
systemd 可读的 `/opt/bmc-lite/control`，私钥 0600，令牌 0640。两端均用
TLS 构建。

在 A 的 systemd `ExecStart` 追加（对端 B 为 192.168.124.128）：

```text
--peer-bind 0.0.0.0 --peer-listen-port 9443 --peer-address 192.168.124.128 \
  --peer-port 9443 --peer-token-file /opt/bmc-lite/control/peer-token \
  --peer-ca /opt/bmc-lite/control/peer-ca.pem \
  --peer-server-name 192.168.124.128 \
  --peer-tls-cert /opt/bmc-lite/control/cert.pem \
  --peer-tls-key /opt/bmc-lite/control/key.pem
```

B 反向填写 A 的实际 IP，`peer-server-name` 必须对应 A 证书 SAN（DNS 名也
可以）。保留完整的 config/rules/sel/log 参数；需要指标时保留
`--http-port 8000`。override 添加 `ReadOnlyPaths=/opt/bmc-lite/control`，
执行 daemon-reload/restart，管理网防火墙允许双方的 9443。证书与令牌轮换
都要重启。

非回环出站必须提供 CA 与服务器名，非回环监听必须提供证书与私钥；CA、
主机名或令牌错误时对端状态不会被刷新，没有跳过验证的开关。

### 3.9 启动失败与自测

心跳构造或监听启动失败时，程序撤销心跳监听、记录 `listener unavailable`，
然后抛出异常，最终进程退出码为 1（systemd 的 `Restart=on-failure` 因此
生效）。采样不受影响，因为失败发生在启动阶段，主循环尚未开始。

```sh
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build -R 'PeerHeartbeat|peer_runtime' --output-on-failure
```

C++ 用例覆盖鉴权与代次、陈旧与恢复各自只上报一次、部分写与 `EAGAIN`
续传、pending connect 的绝对期限与重试间隔，以及明文远程和不完整 TLS 被
拒绝；`peer_runtime` 用两个真实进程验证双向心跳、热重载后的代次传播、
陈旧与恢复，并确认心跳流量不会写入 PWM。

## 四、优缺点与适用性

**优点**

- 对端存活与配置代次都可观测，并沉淀到 SEL、日志与上行遥测。
- 结构上不可能触发硬件动作：误把心跳端口当控制端口用只会得到 400。
- 独立端口与独立令牌，凭证泄露或故障都被限制在对等通道内。
- 默认关闭：不配置就完全不监听、不起线程。

**代价与局限（边界）**

- **不做选主、不做 fencing、不做故障切换**：两个实例都会继续按自己的规则
  独立动作，冲突由人解决。
- **代次只观察、不自动应用**：发现两边代次不同，需要人工对齐配置或各自
  重载，本模块不会把对端配置复制过来。
- 只支持 IPv4 字面量，不支持 DNS 名。
- 每个间隔新建一条 TCP 连接（默认 1 秒一次），连接与 TLS 握手开销高于
  长连接方案。
- 真实网络抖动会造成误报陈旧，`stale_ms` 必须按网络实况调整。
- 心跳只证明对端的心跳线程活着，不证明对端的采样仍在推进。
- 使用单调时钟 `steady_clock`，不受墙钟跳变影响，但也不代表真实日期时间。

**为什么这套设计适合当前部署场景**

本项目的多实例只是冗余观测，不是高可用集群：硬件保护动作由本机规则引擎
决定，不需要跨机仲裁。把范围收窄到"存活 + 代次"，就能在几乎零风险的
前提下换来部署可见性；需要自动切换的场景应交给外部编排系统，而不是让
守护进程自己猜。
