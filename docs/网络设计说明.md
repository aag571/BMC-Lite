# 网络设计说明

本文回答一个问题：**BMC-Lite 的网络为什么拆成四条通道、每条通道的边界在哪里**。
它适合两类读者：准备部署这些端口的人（先看第三、四节），以及准备改动网络代码的人
（先看第二、五节）。本文只讲设计依据，具体命令与部署步骤见文末的延伸阅读。

## 一、为什么需要它

BMC-Lite 是一个硬件监测守护进程：它周期采样温度、风扇转速等传感器，按规则判定状态，
必要时写 PWM 节点调整风扇。没有网络层时，这个进程只能通过日志和 SEL（System Event Log，
系统事件日志；本项目的故障证据文件）被观察，也只能被本地手工干预。

于是出现两个真实缺口：

1. **看不见**：运维需要远程读取"这块板子现在什么状态"，不想登录每台机器翻日志文件。
2. **改不动**：温度持续偏高时，需要远程触发一次风扇提升，而不是等人跑到机房里敲命令。

缺口补起来就会引入风险。最省事的做法是把所有功能挂到同一个端口上，但这等于让
**一个只读的 HTTP 探针、一个能写硬件的控制接口、一份对外转发的遥测、
一个实例间的对等协议共享同一套凭证和同一个失败域**。本项目的核心取向是
"宁可少一个功能，也不让安全边界变模糊"，所以选择按信任模型拆分通道。

### 四种通道的信任模型与失败后果

"信任模型"在这里指：我们假设这条通道对面的东西有多可信、要不要证明身份、
以及它出问题时最坏会造成什么。

| 通道 | 方向 | 信任前提 | 认证方式 | 失败后果 |
|---|---|---|---|---|
| 只读管理 | 入站 | 低（网络内任何人） | 无 | 只影响可观测性，不改变硬件 |
| 控制面 | 入站 | 高（必须是管理员） | Bearer 令牌，必需 | **可能造成物理动作**（风扇转速） |
| 上行遥测 | 出站 | 中（采集器由本侧指定） | 采集器侧自行决定 | 不得影响采样节奏 |
| 实例心跳 | 双向 | 高（对等实例） | Bearer 令牌，必需 | 可导致状态误判（本项目不做选主） |

四行的差别不是程度问题，而是**性质不同**：

- 只读通道泄密的最坏结果是"别人知道了你的温度"；
- 控制通道被冒用的最坏结果是"别人让风扇转到了你没想到的速度"，
  这是一个会改变物理世界状态的动作，也可能掩盖真实的过热问题；
- 上行通道是出站连接，它的风险方向相反：不是别人进来，而是**采集器把本进程拖慢**；
- 心跳通道连接的是另一个同类实例，它一旦被当成控制入口，
  就等于给了对等体一个"能改风扇"的后门。

### 合并成一个端口的具体代价

"只开一个端口"不是抽象的坏味道，它有四条可核实的后果：

1. **凭证继承**：只读端点会和写端点共用同一个监听与同一条鉴权路径，
   要么给只读也加令牌（运维成本上升、探针变复杂），要么让写端点也变成无认证（不可接受）。
2. **失败域耦合**：一个慢的只读客户端占住连接额度时，管理员的控制请求会被一起拒绝。
   拆分后只读满 64 个连接才拒绝，控制面另有 8 个名额，互不牵连。
3. **协议后门**：心跳为了自动往返必须携带令牌，如果与写入路径同端口同路径空间，
   对等体就成了一个隐式的控制入口。
4. **无法分别审计与限流**：本项目的限流是按来源 IP 的令牌桶，
   审计是写 SEL 记录。若只读与管理共用一个入口，
   来自同一 IP 的只读探测会消耗管理通道的失败额度，日志里也分不清是哪种意图。

结论：拆成四条通道，其中三条是入站监听（只读、控制、心跳），
一条是出站连接（上行遥测）。四条**默认全部关闭**。

## 二、设计思路

### 核心目标

1. **默认关闭**：不给出对应开关，就不创建任何监听套接字。默认部署的攻击面为 0。
2. **fail-closed（配置不全就拒绝启动，而不是降级成不安全但能用）**：
   控制面缺令牌、非回环绑定缺 TLS，都让进程直接起不来，而不是"裸奔但绑回环"。
3. **采样节奏优先**：任何网络行为——慢客户端、大响应、慢采集器——
   都不允许推迟采样。硬件过热不会等你的 HTTP 请求。
4. **可测试**：所有连接状态机都要能在没有真实端口的情况下单测。

### 关键取舍：并发模型用独立线程，而不是并入主 epoll

术语说明：**epoll 是 Linux 的事件通知机制**，进程把一批文件描述符注册进去，
内核在有事件时告诉你哪些就绪了。主循环把采样定时器（`timerfd`）、信号（`signalfd`）
和可选 GPIO 都注册在**主 epoll** 里。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 并入主 epoll | 零额外线程、状态天然有序 | 网络代码与采样循环共享线程，慢客户端会推迟采样 |
| **独立线程 + 自己的 epoll**（已选） | 采样节奏与网络互相隔离 | 需要把状态变更安全地投递给主循环 |
| 每连接一个线程 | 代码直观 | 连接数直接换算成线程数，64 个只读连接就是 64 个线程栈 |
| 独立进程 | 隔离最彻底 | 需要跨进程共享 SEL 与配置，复杂度与运维成本远超收益 |

选择独立线程后，必须补上三条约束，否则"隔离"会变成"绕开安全机制"：

1. **网络线程只读**：它只调用已加锁的 `SelStore::query()`、事件总线订阅得到的快照，
   以及配置快照。它不接触 `MonitorSensor`、`Engine`、`FaultRuleEngine`。
2. **所有写操作经 `Worker::submit`**：由工作线程执行，走的是与自动恢复完全相同的一条路径，
   因此自动继承 `RecoveryPolicyEngine` 的冷却、去重、并发上限，
   以及 `PwmAction` 的取值校验。
3. **禁止网络线程直接调用 `write_pwm`**。这是本设计最重要的一条约束：
   一旦绕过，冷却、去重、审计全部失效，控制面就退化成"任何持令牌者可以任意写设备节点"。

### 关键取舍：`SocketIo` 抽象为什么值得做

`SocketIo` 是一层薄薄的系统调用接口：真实实现 `PosixSocketIo` 直接转发 `socket()`、
`accept()`、`recv()`、`send()` 等；测试实现返回脚本化的结果。
项目的 `LinuxIo`（`include/bmc/linux_io.hpp`）已经证明了这个模式的价值，网络照做。

理由是具体的：如果没有它，验证清单上的每一条（超长头部被拒、慢客户端被断开、
并发上限生效、认证失败被限流）都只能靠"起一个真端口再手工构造畸形请求"来验证。
有了它，`FakeSocketIo`（`tests/core_test.cpp`）能驱动解析与限流，
`ScriptSocket`（`tests/network_test.cpp`）能驱动连接状态机，
`FakeUplinkSocket`（`tests/uplink_test.cpp`）与 `PeerSocket`（`tests/peer_test.cpp`）
分别驱动两条出站状态机。这些替身刻意分散在各测试文件里、不共享，
因为每个替身只模拟自己需要的那几种返回值：

- `accept` 返回预设连接或错误；
- `recv` 返回分片、超长、半包；
- `send` 返回部分写入或 `EAGAIN`（暂时写不动，稍后重试）；
- `getsockopt` 返回错误。

### 关键取舍：HTTP 子集为什么刻意做小

本项目零第三方运行时依赖。与其引入一个 HTTP 框架，不如只实现自己需要的那一小块，
并把"不支持"写清楚。这个子集支持：

- 方法：`GET`（只读端口、控制端口）、`POST`（仅控制端口）；
- 头部：`Host`、`Content-Length`、`Content-Type`、`Authorization`、`Connection`；
- 版本：`HTTP/1.1` 与 `HTTP/1.0`；
- 响应：**永远**带 `Content-Length` 与 `Cache-Control: no-store`，
  并固定 `Connection: close`。

明确**不支持**，并在收到时按 501（语法合法但不支持）或 400（语法非法）拒绝：

| 不支持的东西 | 为什么拒绝而不是"尽量兼容" |
|---|---|
| `Transfer-Encoding: chunked` | 分块编码让请求体长度不再由单一整数决定，是请求走私的常见来源 |
| keep-alive 复用与流水线 | 复用要在一条连接上维护"下一个请求"的状态；一次一请求后状态机最小 |
| `Expect: 100-continue` | 需要先回一个中间响应，会引入额外的时序与超时分支 |
| `Upgrade`（WebSocket 等） | 本项目只做请求-响应，不做推送 |
| `PUT`/`DELETE`/`PATCH` | 控制动作只有两个端点，用 `POST` 表达，不开放通用动词 |
| HTTP/2 | 二进制分帧、多路复用，与"最小状态机"的目标相反 |
| 重复的单值头部 | 重复 `Content-Length` 或 `Authorization` 是请求走私的经典手法，直接判 400 |

取舍的代价要说清楚：正因为不支持 keep-alive，只读端点在批量抓取指标时
会为每次请求新建一条 TCP 连接。对于本项目的使用方式（探针每 15 秒拉一次，
或人工查看）完全可以接受；如果将来要做高频抓取，这是第一个需要重新评估的决定。

### 考虑过但放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 一个端口承载全部通道 | 见第一节：凭证继承、失败域耦合、协议后门、无法分别限流 |
| 网络线程直接写 PWM | 会绕过冷却、去重与 `RecoveryPolicyEngine` 的并发上限 |
| HTTP 框架 | 与零依赖取向冲突，且框架自带的 keep-alive、分块、路由会扩大攻击面 |

其中三项值得单独说明，因为它们看起来"更省事"，实际代价最大。

**mTLS（双向 TLS，客户端也要出示证书）：当前未实现。**
控制面只做服务器证书 + Bearer 令牌。理由是单令牌已覆盖当前场景，
而客户端证书的分发、吊销与时钟同步在小型部署里是纯负担。
这是一个有意的边界，不是遗漏；需要它时应当整体升级身份体系，而不是加一个开关。

**自己实现选主：不做。** 脑裂防护需要法定人数、
fencing（阻止旧主继续写硬件）与状态对账。在没有共享存储或外部仲裁者的前提下自己实现，
失败模式是"两个实例同时控风扇"，比不做更危险。

**把 TLS 设为强制依赖：不做。** 只读回环部署不需要 OpenSSL，
因此 TLS 是可选的构建开关（默认关闭）。未编译 TLS 时，任何需要 TLS 的配置
都会**明确报错**，不会静默降级成明文。

## 三、具体实现

### 端口与开关（全部默认关闭）

"默认关闭"在实现上的含义很直接：所有端口选项默认值为 0，
`ReadOnlyServer::start()` 见到 `port_ == 0` 就立刻返回成功且不创建套接字。

| 通道 | 监听 | 开关 | 默认绑定 | 认证 |
|---|---|---|---|---|
| 只读管理 | 入站 | `--http-port` | `127.0.0.1` | 无 |
| 控制面 | 入站 | `--control-port` + `--control-token-file` | `127.0.0.1` | Bearer 令牌，必需 |
| 实例心跳 | 入站 | `--peer-listen-port`、`--peer-token-file` | `127.0.0.1` | Bearer 令牌，必需 |
| 上行遥测 | 出站 | `--uplink-address` + `--uplink-port` | — | 采集器侧 |
| 心跳出站 | 出站 | 同上 peer 选项 | — | 对端令牌 |

补充规则：

- 控制面的端口与令牌文件必须**成对**给出；只给一个会在启动时报
  "control requires port and token file together"，进程以状态 1 退出。
- 非回环绑定对控制面与心跳是**硬拒绝**：没有证书就报
  "non-loopback control requires TLS"（心跳为 "non-loopback peer requires TLS"），
  且在创建套接字之前就失败。
- 只读面要绑到非回环地址，必须同时给 `--http-allow-remote`，
  这是"显式确认你要暴露只读数据"的第二道开关。
- 三个入站监听**复用同一个 `ReadOnlyServer` 实现**，区别只在构造重载、
  连接上限、指标角色标签以及是否启用 TLS。

### 硬上限

超出即拒绝并计数，**不做静默截断**。截断会让"攻击者发了 9 KiB 头部"看上去像一次正常请求。

| 项目 | 上限 | 超限后的行为 |
|---|---|---|
| 请求行 | 8 KiB | 413 Payload Too Large |
| 头部总量 | 8 KiB | 413 |
| 单个头部行 | 1 KiB | 413 |
| 头部条数 | 64 条 | 413 |
| 请求体 | 1 MiB | 413 |
| 读超时 | 5 s（绝对期限） | 断开连接并计入 timeout 拒绝 |
| 写超时 | 5 s（绝对期限） | 同上 |
| 只读端口并发连接 | 64 | 立即关闭并计入 limit 拒绝 |
| 控制端口并发连接 | 8 | 同上，并额外写一条审计 |
| 心跳端口并发连接 | 8 | 同上 |
| 每条连接的在途请求 | 1 | 结构上不可能出现第二条 |

几个容易误读的细节：

- 读与写的 5 秒是**两个绝对期限，不累加**：连接建立即进入 5 秒读期限，
  读出完整请求后才重置为 5 秒写期限。因此"每隔 4 秒发一个字节"的慢速攻击
  不会无限延长连接，它会在读期限到点时被断开。
- 每轮事件就绪，单个连接最多读 16 × 4096 字节 = 64 KiB；
  一次 accept 就绪最多接受 64 个新连接。两者都是为了不让单个客户端独占事件循环。
- 事件循环的 `epoll_wait` 超时是 100 ms，只用于兜底扫描过期连接；
  停止时用 `eventfd` 立即唤醒，不必等这 100 ms。

### 端点

只读端口（与 `tools/bmc_manage.py` 的输出刻意保持同形状，便于跨实现对拍）：

| 路径 | 说明 |
|---|---|
| `GET /healthz` | 存活探针，返回 `{"alive": true, "samples": N}` |
| `GET /metrics` | Prometheus 文本；只读指标之后追加其余已启用角色的指标 |
| `GET /redfish/v1/` | Redfish 根资源 |
| `GET /redfish/v1/Managers` | 管理器集合（成员 1 个） |
| `GET /redfish/v1/Managers/BMC` | 管理器资源，指向 LogServices |
| `GET /redfish/v1/Managers/BMC/LogServices` | 日志服务集合 |
| `GET /redfish/v1/Managers/BMC/LogServices/SEL` | SEL 资源，指向 Entries |
| `GET /redfish/v1/Managers/BMC/LogServices/SEL/Entries` | 条目集合（最多 4096 条） |
| `GET /redfish/v1/Managers/BMC/LogServices/SEL/Entries/<id>` | 单条记录 |
| 其他 | 404，JSON 错误体 `ResourceNotFound` |

控制端口：

| 路径 | 说明 |
|---|---|
| `POST /v1/actions/fan` | 提升指定传感器的风扇，经 `Worker` + `RecoveryPolicyEngine` |
| `POST /v1/actions/inspect` | 记录一次检查请求（等价 `inspect_device`） |
| `GET /v1/config/generation` | 返回当前配置代次，供自动化确认热重载已生效 |

心跳端口：

| 路径 | 说明 |
|---|---|
| `GET /v1/heartbeat` | 带 `X-BMC-Generation` 头部，响应体是本端当前代次 |

控制请求体只接受 `sensor` 与 `action` 两个字符串字段，
**不允许**出现文件路径。动作路径始终取自配置快照；
允许客户端传路径等于开放任意文件写入，`O_NOFOLLOW`（打开时不跟随符号链接）
只是最后一道防线，不是第一道。

### 指标清单

指标名与既有的 `bmc_sensor_*` 保持同一命名风格。注意 `role` 标签把三类入站监听
（`read`、`control`、`peer`）分开统计：

| 指标 | 含义 |
|---|---|
| `bmc_connections_active{role}` | 当前活跃连接数 |
| `bmc_connections_rejected_total{role,reason}` | reason 为 `limit`/`timeout`/`parse` |
| `bmc_requests_total{role,method,status}` | method 只取 `GET`/`POST`/`other` |
| `bmc_request_bytes_total{role,direction}` | direction 为 `in`/`out` |
| `bmc_control_auth_failures_total` | 控制面认证失败次数 |
| `bmc_control_rate_limited_total` | 控制面因失败限流被拒次数 |
| 上行指标 | `bmc_uplink_queued` / `bmc_uplink_dropped_total` 等队列与发送计数 |
| `bmc_peer_stale` / `bmc_peer_generation` / `bmc_peer_heartbeats_total` 等 | 心跳存活与代次 |

指标标签**只用固定枚举值，不含客户端提供的路径**。原因是指标基数：
如果路径进了标签，任何脚本都能让 Prometheus 的时间序列数量爆炸。

### 关闭顺序

停止顺序是设计的一部分，不是实现细节：

```
network.stop() → peer_network->stop() → peer->stop() → control_network->stop()
→ worker.stop() → bus.stop() → uplink->stop() → sel.flush() → logger.flush()
```

三个要点：

- **网络必须早于 Worker 停止**。网络线程会向 Worker 提交任务，
  如果先停 Worker，这些提交会立刻变成 rejected；
  反之在网络停掉之后再停 Worker，已受理的任务仍会由 Worker 自己执行完。
- **总线最后一条出站遥测发生在 `bus.stop()` 之前**，因此上行线程在总线排空后才停。
- 每个 `stop()` 都是幂等的：先唤醒并 join 网络线程，**再**关闭描述符。
  顺序颠倒会出现描述符复用与并发访问。

## 四、安全设计

这一节把"网络层为什么不能被绕过"讲清楚。

**其一，非回环必须 TLS。** 控制面和心跳在绑定非回环地址时，
若没有配置证书与私钥，`start()` 在创建套接字之前就返回失败。
回环明文是允许的：本机通信不经网络，TLS 只增加复杂度。
构建时未启用 TLS 的二进制在需要 TLS 的配置下会抛出
"TLS support was disabled at build time"，**不会**静默降级成明文。

**其二，令牌先于路径校验。** 控制面的处理顺序固定为：
校验令牌 → 匹配路由 → 解析请求体。未认证的请求不应该从响应差异里
推断出"某个路由或某个传感器是否存在"。心跳同理：凭证错误一律 401，
凭证正确但路径、方法或代次不合法才是 400。

**其三，失败限流只用来源 IP，不用 IP:端口。** 网络层在 `accept` 之后
只取 `inet_ntop` 的结果作为对端标识（`peer_name()` 那种带端口的格式只用于诊断）。
如果限流键含端口，攻击者每次失败后重连换一个源端口就能重置计数，
限流形同不存在。限流本身是**令牌桶**：桶里有令牌才放行，
按时间以固定速率补充并封顶到桶容量，因此它同时限制突发量（桶容量）
与长期速率（补充速率）。控制面与心跳的桶都是容量 5、每秒补充 0.2 个，
即连续 5 次失败后要等约 5 秒才恢复一次尝试。
来源表满时淘汰最旧的一条，避免新管理员被永久挡在表外。

**其四，令牌文件而不是命令行。** 令牌从文件读取，要求是当前有效用户拥有的普通文件、
权限恰为 `0640`、内容 32~512 个可打印非空格字符。命令行明文会在 `ps` 输出和
systemd journal 里留下副本；`O_NOFOLLOW` 则拒绝把令牌文件做成指向别处的符号链接。

**其五，网络线程只读。** 这条约束把"网络能做什么"限制在"读取快照、提交任务"。
写硬件的唯一入口是 Worker 执行 `PwmAction`，而 `PwmAction` 自己带
`O_NOFOLLOW` 与取值校验（0~255）。三道防线各自独立。

**其六，审计失败即停服。** 控制面的审计回调写 SEL 并当场 `flush`；
一旦持久化失败或同步失败计数增加，就抛异常、置失败标志，
网络线程停止监听，主循环以非零状态退出。理由是：
**一个无法留下审计记录的控制面，比没有控制面更危险**。

## 五、优缺点与适用性

### 优点

- **默认零暴露**：不配置就没有套接字，默认部署的攻击面与不启用网络时完全相同。
- **失败域隔离**：采样与网络互不阻塞；只读连接额度与控制在额度互不牵连。
- **安全决策不可绕过**：三条入站通道共用同一套解析与上限代码，
  限流、认证顺序、审计闸门都在唯一路径上。
- **可测试**：`SocketIo` 抽象让绝大多数验证项在单测里完成，不需要特权或真实端口。
- **可观测**：连接、拒绝、请求、字节、认证失败、限流、上行、心跳都有指标，
  且标签基数固定。

### 代价与局限

| 代价 | 说明 |
|---|---|
| 每个入站监听一个线程 | 三条通道就是三个网络线程（外加各自的 epoll 与 eventfd）。空载成本低 |
| 无法按路径分别限流 | 粒度是"来源 IP + 通道"。同一 IP 打某个只读路径，会消耗它在该通道的全部额度 |
| 没有 keep-alive | 每条连接只处理一个请求，批量抓取时连接建立开销被放大 |
| 请求处理在控制面上串行 | `handle()` 全程持锁，请求按到达顺序处理。8 个连接是上限，不是并发能力 |
| 明文回环之外没有别的降级 | 未编译 TLS 时，远程控制这条路直接不存在，没有"临时明文"的逃生门 |
| 响应缓冲在内存里 | 响应在发送前已完整构建，SEL 条目集合最多 4096 条时会占用相应内存 |
| 不做选主 | 心跳只交换存活与代次，不提供故障切换 |

### 这套设计为什么适合当前场景

BMC-Lite 的部署形态是"一台机器上一个守护进程，管几个传感器"，
不是高并发网关。在这个规模下：

- 独立线程带来的隔离收益（采样永不被网络推迟）远大于三个线程的成本；
- 每连接一个请求的简单状态机，比支持复用的状态机更容易证明正确；
- 用固定上限 + 明确拒绝代替动态自适应，让"最坏情况"在部署前就能算出来；
- 零依赖 + 可注入的系统调用层，让这套网络代码可以在 CI 里完整验证。

反过来说，如果需求变成"每秒上千次指标抓取"或"多租户 SaaS 式管理面"，
本文的取舍就不再合适：那时该考虑成熟 HTTP 框架、连接复用，
以及按租户分层的鉴权体系。
