# 网络设计说明

## 一、为什么需要它

BMC-Lite 是一个硬件监测守护进程：

- 它周期采样温度、风扇转速等传感器，按规则判定状态，必要时写 PWM 节点调整风扇。
- 没有网络层时，这个进程只能通过日志和 SEL（System Event Log，系统事件日志；本项目的故障证据文件）被观察，也只能被本地手工干预。

于是出现两个真实缺口：

1. **远程观测**：运维需要远程读取"这块板子现在什么状态"，而不是每次登录每台机器翻日志文件。
2. **远程控制**：温度持续偏高时，需要远程触发一次风扇提升，而不是跑到机房。

但是缺口补起来就会引入风险。最省事的做法是把所有功能挂到同一个端口上，但这等于让**一个只读的 HTTP 探针、一个能写硬件的控制接口、一份对外转发的遥测、一个实例间的对等协议共享同一套凭证和同一个失败域**。本项目的核心取向是"宁可少一个功能，也不让安全边界变模糊"，所以选择按信任模型拆分通道。

### 四种通道的信任模型与失败后果

"信任模型"在这里指：我们假设这条通道对面的东西有多可信、要不要证明身份、以及它出问题时最坏会造成什么。

| 通道 | 方向 | 信任前提 | 认证方式 | 失败后果 |
|---|---|---|---|---|
| 只读管理 | 入站 | 低（网络内任何人） | 无 | 只影响可观测性，不改变硬件 |
| 控制面 | 入站 | 高（必须是管理员） | Bearer 令牌，必需 | 可能造成物理动作（风扇转速） |
| 上行遥测 | 出站 | 中（采集器由本侧指定） | 采集器侧自行决定 | 不得影响采样节奏 |
| 实例心跳 | 双向 | 高（对等实例） | Bearer 令牌，必需 | 可导致状态误判（本项目不做选主） |

四行的差别是性质不同：

- 只读通道泄密的最坏结果是"别人知道了你的温度"；
- 控制通道被冒用的最坏结果是"别人让风扇转到了你没想到的速度"，这是一个会改变物理世界状态的动作，也可能掩盖真实的过热问题；
- 上行通道是出站连接，它的风险方向相反：不是别人进来，而是**采集器把本进程拖慢**；
- 心跳通道连接的是另一个同类实例，它一旦被当成控制入口，就等于给了对等体一个"能改风扇"的后门。

### 合并成一个端口的具体代价

1. **凭证继承**：只读端点会和写端点共用同一个监听与同一条鉴权路径，要么给只读也加令牌（运维成本上升、探针变复杂），要么让写端点也变成无认证（不可接受）。
2. **失败域耦合**：一个慢的只读客户端占住连接额度时，管理员的控制请求会被一起拒绝。拆分后只读满 64 个连接才拒绝，控制面另有 8 个名额，互不牵连。
3. **协议后门**：心跳为了自动往返必须携带令牌，如果与写入路径同端口同路径空间，对等体就成了一个隐式的控制入口。
4. **无法分别审计与限流**：本项目的限流是按来源 IP 的令牌桶，审计是写 SEL 记录。若只读与管理共用一个入口，来自同一 IP 的只读探测会消耗管理通道的失败额度，日志里也分不清是哪种意图。

结论：拆成四条通道，其中三条是入站监听（只读、控制、心跳），一条是出站连接（上行遥测）。四条**默认全部关闭**。

## 二、设计思路

### 核心目标

1. **默认关闭**：不给出对应开关，就不创建任何监听套接字。默认部署的攻击面为 0。
2. **fail-closed（配置不全就拒绝启动，而不是降级成不安全但能用）**：控制面缺令牌、非回环绑定缺 TLS，都让进程直接起不来，而不是"裸奔但绑回环"。
3. **采样节奏优先**：任何网络行为——慢客户端、大响应、慢采集器 都不允许推迟采样。硬件过热不会等 HTTP 请求。
4. **可测试**：所有连接状态机都要能在没有真实端口的情况下单测。

### 关键取舍：并发模型用独立线程，而不是并入主 epoll

术语说明：**epoll 是 Linux 的事件通知机制**，进程把一批文件描述符注册进去，内核在有事件时告诉你哪些就绪了。主循环把采样定时器（`timerfd`）、信号（`signalfd`）和可选 GPIO 都注册在**主 epoll** 里。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 并入主 epoll | 零额外线程、状态天然有序 | 网络代码与采样循环共享线程，慢客户端会推迟采样 |
| 独立线程 + 自己的 epoll（已选） | 采样节奏与网络互相隔离 | 需要把状态变更安全地投递给主循环 |
| 每连接一个线程 | 代码直观 | 连接数直接换算成线程数，64 个只读连接就是 64 个线程栈 |
| 独立进程 | 隔离最彻底 | 需要跨进程共享 SEL 与配置，复杂度与运维成本远超收益 |

选择独立线程后，必须补上三条约束，否则"隔离"会变成"绕开安全机制"：

1. **网络线程只读**：它只调用已加锁的 `SelStore::query()`、事件总线订阅得到的快照，以及配置快照。它不接触 `MonitorSensor`、`Engine`、`FaultRuleEngine`。
2. **所有写操作经 `Worker::submit`**：由工作线程执行，走的是与自动恢复完全相同的一条路径，因此自动继承 `RecoveryPolicyEngine` 的冷却、去重、并发上限，以及 `PwmAction` 的取值校验。
3. **禁止网络线程直接调用 `write_pwm`**。这是本设计最重要的一条约束：一旦绕过，冷却、去重、审计全部失效，控制面就退化成"任何持令牌者可以任意写设备节点"。

### 关键取舍：`SocketIo` 抽象为什么值得做

- `SocketIo` 是一层系统调用接口：真实实现 `PosixSocketIo` 直接转发 `socket()`、`accept()`、`recv()`、`send()` 等；测试实现返回脚本化的结果。
- 项目的 `LinuxIo`（`include/bmc/linux_io.hpp`）已经证明了这个模式的价值，网络照做。

理由：

- 如果没有它，验证清单上的每一条（超长头部被拒、慢客户端被断开、并发上限生效、认证失败被限流）都只能靠"起一个真端口再手工构造畸形请求"来验证。
- 有了它，`FakeSocketIo`（`tests/core_test.cpp`）能驱动解析与限流，`ScriptSocket`（`tests/network_test.cpp`）能驱动连接状态机，`FakeUplinkSocket`（`tests/uplink_test.cpp`）与 `PeerSocket`（`tests/peer_test.cpp`）分别驱动两条出站状态机。这些替身刻意分散在各测试文件里、不共享，因为每个替身只模拟自己需要的那几种返回值：
  - `accept` 返回预设连接或错误；
  - `recv` 返回分片、超长、半包；
  - `send` 返回部分写入或 `EAGAIN`（暂时写不动，稍后重试）；
  - `getsockopt` 返回错误。

### 关键取舍：HTTP 子集为什么刻意做小

本项目零第三方运行时依赖。与其引入一个 HTTP 框架，不如只实现自己需要的那一小块，并把"不支持"写清楚。这个子集支持：

- 方法：`GET`（只读端口、控制端口）、`POST`（仅控制端口）；
- 头部：`Host`、`Content-Length`、`Content-Type`、`Authorization`、`Connection`；
- 版本：`HTTP/1.1` 与 `HTTP/1.0`；
- 响应：**永远**带 `Content-Length` 与 `Cache-Control: no-store`，
  并固定 `Connection: close`。

明确**不支持**，并在收到时按 501（语法合法但不支持）或 400（语法非法）拒绝：（这一块是参考AI的建议）

| 不支持的东西 | 为什么拒绝而不是"尽量兼容" |
|---|---|
| `Transfer-Encoding: chunked` | 分块编码让请求体长度不再由单一整数决定，是请求走私的常见来源 |
| keep-alive 复用与流水线 | 复用要在一条连接上维护"下一个请求"的状态；一次一请求后状态机最小 |
| `Expect: 100-continue` | 需要先回一个中间响应，会引入额外的时序与超时分支 |
| `Upgrade`（WebSocket 等） | 本项目只做请求-响应，不做推送 |
| `PUT`/`DELETE`/`PATCH` | 控制动作只有两个端点，用 `POST` 表达，不开放通用动词 |
| HTTP/2 | 二进制分帧、多路复用，与"最小状态机"的目标相反 |
| 重复的单值头部 | 重复 `Content-Length` 或 `Authorization` 是请求走私的经典手法，直接判 400 |

## 三、具体实现

### 端口与开关（全部默认关闭）

"默认关闭"在实现上的含义很直接：所有端口选项默认值为 0，`ReadOnlyServer::start()` 见到 `port_ == 0`就立刻返回成功且不创建套接字。

| 通道 | 监听 | 开关 | 默认绑定 | 认证 |
|---|---|---|---|---|
| 只读管理 | 入站 | `--http-port` | `127.0.0.1` | 无 |
| 控制面 | 入站 | `--control-port` + `--control-token-file` | `127.0.0.1` | Bearer 令牌，必需 |
| 实例心跳 | 入站 | `--peer-listen-port`、`--peer-token-file` | `127.0.0.1` | Bearer 令牌，必需 |
| 上行遥测 | 出站 | `--uplink-address` + `--uplink-port` | — | 采集器侧 |
| 心跳出站 | 出站 | 同上 peer 选项 | — | 对端令牌 |

补充规则：

- 控制面的端口与令牌文件必须**成对**给出；只给一个会在启动时报"control requires port and token file together"，进程以状态 1 退出。
- 非回环绑定对控制面与心跳是**硬拒绝**：没有证书就报"non-loopback control requires TLS"（心跳为 "non-loopback peer requires TLS"），且在创建套接字之前就失败。
- 只读面要绑到非回环地址，必须同时给 `--http-allow-remote`，这是"显式确认要暴露只读数据"的第二道开关。
- 三个入站监听**复用同一个 `ReadOnlyServer` 实现**，区别只在构造重载、连接上限、指标角色标签以及是否启用 TLS。

### 硬上限

超出即拒绝并计数，**不做静默截断**。截断会让"攻击者发了 9 KiB 头部"看上去像一次正常请求。

| 项目 | 上限 | 超限后的行为 |
|---|---|---|
| 请求行 | 8 KiB | 413 Payload Too Large |
| 头部总量 | 8 KiB | 413 |
| 单个头部行 | 1 KiB | 413 |
| 头部条数 | 64 条 | 413 |
| 请求体 | 1 MiB | 413 |
| 读超时 | 5 s（绝对期限） | 断开连接并计入 timeout 拒绝 |
| 写超时 | 5 s（绝对期限） | 同上 |
| 只读端口并发连接 | 64 | 立即关闭并计入 limit 拒绝 |
| 控制端口并发连接 | 8 | 同上，并额外写一条审计 |
| 心跳端口并发连接 | 8 | 同上 |
| 每条连接的在途请求 | 1 | 结构上不可能出现第二条 |

- 读与写的 5 秒是**两个绝对期限，不累加**：连接建立即进入 5 秒读期限，读出完整请求后才重置为 5 秒写期限。因此"每隔 4 秒发一个字节"的慢速攻击不会无限延长连接，它会在读期限到点时被断开。
- 每轮事件就绪，单个连接最多读 16 × 4096 字节 = 64 KiB；一次 accept 就绪最多接受 64 个新连接。两者都是为了不让单个客户端独占事件循环。
- 事件循环的 `epoll_wait` 超时是 100 ms，只用于兜底扫描过期连接；停止时用 `eventfd` 立即唤醒，不必等这 100 ms。

### 端点

只读端口（与 `tools/bmc_manage.py` 的输出刻意保持同形状，便于跨实现对拍）：

| 路径 | 说明 |
|---|---|
| `GET /healthz` | 存活探针，返回 `{"alive": true, "samples": N}` |
| `GET /metrics` | Prometheus 文本；只读指标之后追加其余已启用角色的指标 |
| `GET /redfish/v1/` | Redfish 根资源 |
| `GET /redfish/v1/Managers` | 管理器集合（成员 1 个） |
| `GET /redfish/v1/Managers/BMC` | 管理器资源，指向 LogServices |
| `GET /redfish/v1/Managers/BMC/LogServices` | 日志服务集合 |
| `GET /redfish/v1/Managers/BMC/LogServices/SEL` | SEL 资源，指向 Entries |
| `GET /redfish/v1/Managers/BMC/LogServices/SEL/Entries` | 条目集合（最多 4096 条） |
| `GET /redfish/v1/Managers/BMC/LogServices/SEL/Entries/<id>` | 单条记录 |
| 其他 | 404，JSON 错误体 `ResourceNotFound` |

控制端口：

| 路径 | 说明 |
|---|---|
| `POST /v1/actions/fan` | 提升指定传感器的风扇，经 `Worker` + `RecoveryPolicyEngine` |
| `POST /v1/actions/inspect` | 记录一次检查请求（等价 `inspect_device`） |
| `GET /v1/config/generation` | 返回当前配置代次，供自动化确认热重载已生效 |

心跳端口：

| 路径 | 说明 |
|---|---|
| `GET /v1/heartbeat` | 带 `X-BMC-Generation` 头部，响应体是本端当前代次 |

### 指标清单

指标名与既有的 `bmc_sensor_*` 保持同一命名风格。注意 `role` 标签把三类入站监听
（`read`、`control`、`peer`）分开统计：

| 指标 | 含义 |
|---|---|
| `bmc_connections_active{role}` | 当前活跃连接数 |
| `bmc_connections_rejected_total{role,reason}` | reason 为 `limit`/`timeout`/`parse` |
| `bmc_requests_total{role,method,status}` | method 只取 `GET`/`POST`/`other` |
| `bmc_request_bytes_total{role,direction}` | direction 为 `in`/`out` |
| `bmc_control_auth_failures_total` | 控制面认证失败次数 |
| `bmc_control_rate_limited_total` | 控制面因失败限流被拒次数 |
| 上行指标 | `bmc_uplink_queued` / `bmc_uplink_dropped_total` 等队列与发送计数 |
| `bmc_peer_stale` / `bmc_peer_generation` / `bmc_peer_heartbeats_total` 等 | 心跳存活与代次 |

指标标签**只用固定枚举值，不含客户端提供的路径**。原因是指标基数：

- 如果路径进了标签，任何脚本都能让 Prometheus 的时间序列数量爆炸。

### 关闭顺序

停止顺序：

```
network.stop() → peer_network->stop() → peer->stop() → control_network->stop()
→ worker.stop() → bus.stop() → uplink->stop() → sel.flush() → logger.flush()
```

- 网络必须早于 Worker 停止。网络线程会向 Worker 提交任务，如果先停 Worker，这些提交会立刻变成 rejected；反之在网络停掉之后再停 Worker，已受理的任务仍会由 Worker 自己执行完。
- 总线最后一条出站遥测发生在 `bus.stop()` 之前，因此上行线程在总线排空后才停。
- 每个 stop() 都是幂等的：先唤醒并 join 网络线程，再关闭描述符。顺序颠倒会出现描述符复用与并发访问。
