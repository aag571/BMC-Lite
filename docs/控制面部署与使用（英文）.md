# Control Plane Deployment and Usage

This document answers one question: **how do I enable BMC-Lite's control interface safely,
and how do I use it correctly?** It targets system administrators and operators -- you do not
need to read C++ code, but you need a Linux host, root access, and an appreciation of what
"who can change this board's fan speed" actually means. If you only want the reasoning behind
the network layer, see the network design note in Further reading below.

## 1. Why It Exists

BMC-Lite performs recovery actions automatically when rules fire (for example, raising fan speed
once a temperature enters warning). Automatic rules do not cover everything: during
troubleshooting, an operator often needs to **deliberately trigger one inspection or one fan
increase** to confirm that a device still responds.

Without a control plane the only option is to log into the machine and do it by hand: the target
host needs SSH, someone must remember the correct PWM node path, that person must avoid writing
too many times in a row, and the action **leaves no structured audit record**. Worse, the moment
someone writes a small "just write the PWM node" script elsewhere, the cooldown, deduplication and
concurrency limits of the automatic recovery engine are all bypassed.

So the problem the control plane solves is not "add an HTTP endpoint". It is:
**make remote write actions travel the same controlled path as local automatic recovery, and leave
traceable evidence behind.**

Concrete consequences of not having it:

- Remote intervention is impossible, so incident response is bounded by how fast a human can
  reach the machine room;
- Hand-written node writes have no cooldown protection, so repeated writes in a short window can
  mask a genuine overheating trend;
- The record of who did what lives only in memory and shell history.

### Why It Is Disabled by Default, and Why It Fails Closed

The control plane is the **only** network entry point in this process that can trigger a hardware
action, so its default state must be "off":

- The port option defaults to 0. Unless you pass `--control-port`, no listening socket is created.
- The port and the token file must be supplied **together**. Give only one and the process
  **exits with a nonzero status**, reporting "control requires port and token file together".
- A non-loopback bind requires TLS, and the check fails before any socket is created.
- An audit-persistence failure at runtime also terminates the process.

This is **fail-closed** (refuse to start when the configuration is incomplete, rather than
degrading into something insecure but usable): a control plane that looks enabled but is actually
unprotected is far more dangerous than one that plainly refuses to start. The nonzero exit status
also makes systemd's `Restart=on-failure` behave as intended.

Read-only HTTP uses a separate port, and its bind failure **does not** stop monitoring: missing
observability is acceptable, a blurred control boundary is not.

## 2. Design Rationale

### The Token Lives in a File, Never on the Command Line

`ps`, `/proc/<pid>/cmdline` and the systemd journal all record the full command line. Putting the
token into `ExecStart` publishes it permanently: any user who can run `ps` can read it.

The token is therefore read only from a file (`--control-token-file`), and that file must satisfy
four conditions. Any failure raises an exception -- it **never** degrades into "no token" or a
lenient mode:

| Condition | Reason |
|---|---|
| Owned by the effective user (`geteuid()`) | Someone else's file can be rewritten by them |
| Mode exactly `0640` | Group read is for the service account; wider lets other users read |
| A regular file, not a symlink | `O_NOFOLLOW` rejects trailing symlinks, so it cannot be moved |
| 32..512 printable non-space characters | Too short invites guessing; too long exceeds the limit |

### Why Constant-Time Comparison

An ordinary string comparison (for example `==` or `memcmp`) returns at the first differing byte.
An attacker cannot see the contents, but can time the response: try `a...`, then `b...`, and the
prefix that takes longer is probably correct. Byte by byte, the token leaks. This is a **timing
side channel**.

**Constant-time comparison** (comparison time does not change with the content, so a password
cannot be guessed from timing differences) instead scans every byte of the server-side token
regardless of content, accumulating differences into one variable that is checked once at the end.
A length mismatch only sets a flag rather than returning early, so the elapsed time depends only on
the server token's length -- and the length is not a secret.

### Why a Control Request Cannot Specify a File Path

The request body accepts exactly two string fields: `sensor` and `action`. It accepts **no path**,
no additional fields, no duplicate keys and no string escapes.

If clients could send a path, this endpoint would amount to arbitrary file write: anyone able to
present the token (or anyone who captured it once) could rewrite any writable file on the system.
The path must therefore come from the server-side configuration snapshot -- `sensor` must exist in
the current configuration, and a fan action additionally requires a non-empty `action_path` for
that sensor. The low-level write uses `O_NOFOLLOW` to reject a trailing symlink, but that is the
**last** line of defence, not a replacement for the rule that client-supplied paths are not
accepted at all.

### The Audit Gate: Persist the Audit First, Then Act

A "gate" here is the ordered checkpoint inside a sequence of steps. The control request path is:

1. Verify the token (a failure first counts against the per-source-IP rate limit);
2. Match route and action (`/v1/actions/fan` + `increase_fan`, or
   `/v1/actions/inspect` + `inspect_device`);
3. Parse the body and check that `sensor` exists in the configuration snapshot;
4. Write an audit record with `outcome=requested`;
5. Submit the task to the `Worker`, but the task must wait on a gate signal before it may run;
6. The submitting thread writes `outcome=accepted` or `outcome=rejected` based on the submit
   result, and flushes the audit;
7. Only **after** that flush succeeds is the task released; when it finishes, one more audit record
   carries the `detail` execution result.

A hardware action therefore cannot happen before its audit record exists. Conversely, if the
`accepted` audit cannot be written, the task is never released, the client receives 503, and the
SEL keeps a `requested` record without a matching `accepted` -- evidence that someone tried to move
hardware and did not succeed.

If audit writing fails **during operation** (write failure, `fdatasync` failure), the network
thread stops listening and the main process exits nonzero. The reason is blunt: a control plane
that cannot leave an audit trail is more dangerous than no control plane at all.

### Three Endpoints, Not a General API

| Endpoint | Why it exists |
|---|---|
| `POST /v1/actions/fan` | The only action that actually changes hardware |
| `POST /v1/actions/inspect` | Records an inspection, so "a human looked" is evidence |
| `GET /v1/config/generation` | Read-only; confirms that a SIGHUP reload took effect |

No generic resource CRUD, no configuration writes, no bulk actions. Every additional writable
endpoint is another boundary that must be re-assessed at deployment time.

## 3. Deployment

### 1. Build from Source

Ubuntu 24.04:

```sh
git clone git@github.com:aag571/BMC-Lite.git
cd BMC-Lite
sudo apt-get update
sudo apt-get install -y build-essential cmake libssl-dev openssl curl python3
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF -DBMC_TLS=ON
cmake --build build-release --parallel 2
sudo bash deploy/install.sh
```

`BMC_TLS` defaults to OFF. Without TLS, OpenSSL is not needed and loopback plaintext control still
works; **remote control requires TLS**. A prebuilt release archive supports HTTPS only if it was
packaged with `BMC_TLS` enabled:

```sh
sha256sum -c bmc-lite-release.tar.gz.sha256
tar -xzf bmc-lite-release.tar.gz
cd bmc-lite-release
sudo apt-get install -y libssl3t64 openssl curl
sudo bash deploy/install.sh
```

The installer checks for missing shared libraries and creates `/opt/bmc-lite/control`, but it
**never generates or replaces** credentials.

### 2. Create the Token and Set Permissions

```sh
sudo install -d -o bmc-lite -g bmc-lite -m 0750 /opt/bmc-lite/control
openssl rand -hex 32 > /tmp/bmc-control-token
sudo install -o bmc-lite -g bmc-lite -m 0640 /tmp/bmc-control-token /opt/bmc-lite/control/token
rm /tmp/bmc-control-token
```

Key points:

- The token file must be owned by the user that actually runs the process. Under the systemd unit
  that is `bmc-lite`; when running manually as your own account, set ownership to that account or
  startup fails.
- The mode must be **exactly** `0640`. The test suite covers the rejection of `0644`.
- It must be a regular file, not a symlink.
- The content is at least 32 printable non-space characters (one trailing newline is allowed).
- Never pass the token on the command line.

### 3. Generate the TLS Certificate

The test VM `192.168.124.128` can start from the self-signed certificate below. Use the certificate
as the client trust anchor and keep the private key on the server only. A managed network should use
a certificate issued by an internal CA.

```sh
openssl req -x509 -newkey rsa:2048 -nodes -days 30 \
  -keyout /tmp/bmc-key.pem -out /tmp/bmc-cert.pem \
  -subj /CN=bmc-lite -addext 'subjectAltName=IP:192.168.124.128,DNS:localhost'
sudo install -o bmc-lite -g bmc-lite -m 0600 /tmp/bmc-key.pem /opt/bmc-lite/control/key.pem
sudo install -o root -g bmc-lite -m 0640 /tmp/bmc-cert.pem /opt/bmc-lite/control/cert.pem
rm /tmp/bmc-key.pem
```

Copy `cert.pem` to the calling client and verify both chain and URL hostname/IP with `--cacert`.
Do **not** use `curl -k`, which skips verification and switches off everything TLS provided.

This is server certificate plus Bearer authentication. **Client certificate authentication (mTLS)
is not implemented.** The certificate and token are read once at startup, so rotation requires a
service restart.

### 4. Configure the systemd Override

```sh
sudo systemctl edit bmc-lite
```

Enter the override below. Keep actions simulated for a first test: do not add `--enable-actions`
yet.

```ini
[Service]
ExecStart=
ExecStart=/opt/bmc-lite/bmc-lite --config /opt/bmc-lite/config/hardware.conf --rules /opt/bmc-lite/config/rules.conf --sel /var/log/bmc-lite/sel.db --log /var/log/bmc-lite/faults.jsonl --http-port 8000 --control-port 8443 --control-bind 0.0.0.0 --control-token-file /opt/bmc-lite/control/token --control-tls-cert /opt/bmc-lite/control/cert.pem --control-tls-key /opt/bmc-lite/control/key.pem
ReadOnlyPaths=/opt/bmc-lite/control
```

Clearing `ExecStart=` before redefining it is the standard systemd override idiom.
`ReadOnlyPaths` lets the service account read the token and certificate without being able to
rewrite them.

```sh
sudo systemctl daemon-reload
sudo systemctl restart bmc-lite
sudo systemctl status bmc-lite --no-pager
sudo journalctl -u bmc-lite -n 50 --no-pager
ss -ltn | grep -E ':8000|:8443'
curl http://127.0.0.1:8000/healthz
```

Read-only HTTP stays on loopback. If remote read-only HTTP is genuinely required, add
`--http-bind 0.0.0.0 --http-allow-remote`.

When read-only and control are both enabled, note that the three roles -- read, control and
heartbeat -- **each get their own listener thread**, and the control plane accepts at most 8
concurrent connections.

### Permissions Reference

| Object | Mode | Owner | Note |
|---|---|---|---|
| `/opt/bmc-lite/control` (dir) | `0750` | `bmc-lite:bmc-lite` | Only the account can enter |
| `token` | `0640` | `bmc-lite:bmc-lite` | Exactly 0640, regular file |
| `key.pem` | `0600` | `bmc-lite:bmc-lite` | Private key never leaves the server |
| `cert.pem` | `0640` | `root:bmc-lite` | Public part, may be copied to clients |

Common startup failures:

| Symptom | Cause |
|---|---|
| stderr shows `control unavailable:` | Token is not mode 0640, wrong owner, or a symlink |
| Same, message has `at least 32 printable non-space characters` | Token too short, or has spaces |
| Same, message has `non-loopback control requires TLS` | Non-loopback bind without a certificate |
| Same, message has `control requires port and token file together` | Only a port, or only a token |
| Log shows `listener unavailable: Address already in use` | Port 8443 is taken |

## 4. Usage

### Client Setup

Create a curl configuration file with mode `0600` on the client so the token never appears in a
command line:

```text
header = "Authorization: Bearer REPLACE_WITH_TOKEN"
cacert = "/client/path/cert.pem"
```

```sh
chmod 0600 control.curl.conf
```

### The Three Endpoints

```sh
curl --config control.curl.conf https://192.168.124.128:8443/v1/config/generation
curl --config control.curl.conf -H 'Content-Type: application/json' \
  --data '{"sensor":"cpu","action":"inspect_device"}' \
  https://192.168.124.128:8443/v1/actions/inspect
curl --config control.curl.conf -H 'Content-Type: application/json' \
  --data '{"sensor":"cpu","action":"increase_fan"}' \
  https://192.168.124.128:8443/v1/actions/fan
```

Key points:

- `sensor` must exist in the current configuration; a fan action also requires that the sensor has
  an `action_path`.
- The body accepts exactly the two string fields `sensor`/`action`; paths, extra fields, duplicate
  keys and string escapes are rejected.
- Action paths always come from the configuration snapshot; clients cannot supply them.
- **202 means queued, not completed.**
- Repeated fan requests enter the same recovery engine, whose cooldown prevents duplicate hardware
  writes.
- Actions are simulated by default. Real PWM writes need `--enable-actions` plus write permission
  on the target node for the service account; the fan action writes 255 to the configured node.

### Status Codes

| Status | Meaning | What the client should do |
|---|---|---|
| 200 | Query succeeded (`/v1/config/generation`) | Read `generation` from the body |
| 202 | Queued; the result appears later in the audit | Correlate with the audit via `request_id` |
| 400 | Invalid body, sensor or action | Fix the request; do not retry as-is |
| 401 | Authentication failed | Check the token; repeated failures escalate to 429 |
| 429 | Failure limit exceeded for this source IP | Wait ~5s; changing source port does not help |
| 503 | Recovery queue full, or audit not saved | Retry later; check disk and SEL |

About 429: failure limiting is a **token bucket** with capacity 5 refilling at 0.2 tokens per
second. After 5 consecutive failures, roughly 5 seconds pass before one more attempt is allowed.
When the source table is full the oldest source is evicted, so a new administrator is never locked
out permanently.

### Audit Records and the 6 `detail` Values

Every control request writes to the SEL with the fixed fields
`action`, `sensor`, `outcome`, `peer` and `request_id`:

- `outcome` is one of `requested` / `accepted` / `rejected` / `unauthorized` / `rate-limited`;
- `peer` is the source **IP** (no port);
- `request_id` links the validation record to the execution-result record of the same request;
- The token itself **never** appears in the audit.

Because 202 only means queued, **the only way to know whether the hardware action happened is the
asynchronous result**. That result is written to an audit record carrying `detail`, which has
exactly 6 possible values:

| `detail` | Meaning | A failure? |
|---|---|---|
| `completed` | The action executed successfully | No |
| `failed` | The action failed (still failing after retries) | Yes |
| `cooldown` | Same (sensor, action) is in the cooldown window | Yes (deliberate skip) |
| `already running` | A previous request for the same pair is running | Yes (deliberate dedup) |
| `concurrency limit` | The engine runs its maximum actions | Yes (a later retry may succeed) |
| `state capacity` | The recovery state table is full | Yes (check for odd sensor/action pairs) |

Note that two different things share the field name `detail`:
the 6 values above come from the recovery result, while network-layer rejections
(connection limit, parse failure, read timeout, peer disconnect) also write audit records whose
`detail` is `connection-limit`, `parse`, `timeout` or `disconnect`.
They are told apart by `outcome` and context.

Inspect the audit:

```sh
sudo grep 'control' /var/log/bmc-lite/sel.db | tail -20
sudo tail -20 /var/log/bmc-lite/faults.jsonl
```

### Hot Reload

```sh
sudo systemctl kill --kill-whom=main --signal=HUP bmc-lite
curl --config control.curl.conf https://192.168.124.128:8443/v1/config/generation
```

Only when sensor and rule configuration **both** validate does the generation and the control
snapshot update; a failed reload keeps the old configuration. Queued tasks hold copies of the
configuration values from submission time and never store sensor object addresses, so a reload
cannot leave an in-flight task with a dangling reference.

## 5. Strengths, Limits and Fit

### Strengths

- **Zero exposure by default**: no configuration means no listening socket, so the default
  deployment's attack surface is identical to running without the control plane.
- **Fails loudly, not quietly**: configuration errors at startup, a failed listener at runtime and
  an unpersistable audit all exit nonzero, so `Restart=on-failure` surfaces problems instead of
  running degraded.
- **Actions share the automatic path**: control requests go through the `Worker` into the
  `RecoveryPolicyEngine`, inheriting cooldown, deduplication, concurrency limits and value
  validation. There is no "more permissive" remote path.
- **The audit cannot be bypassed**: the audit is persisted before the action runs, and
  `request_id` correlates validation with the execution result.
- **Automation-friendly**: Bearer token, a two-field JSON body and a `generation` endpoint are
  enough for curl or any HTTP client.

### Limits and Costs

- **mTLS is not implemented.** This is server certificate plus Bearer token only; clients are not
  asked for a certificate, so holding the token is enough to authenticate.
- **Outbound TLS is heartbeat-only.** The control plane is inbound. The instance heartbeat's
  outbound direction does implement TLS (CA and server name verified, with no skip option).
  Uplink telemetry is currently plaintext TCP.
- **Rotation needs a restart.** Token and certificate are read once at startup; there is no online
  credential reload.
- **The token has no lifetime.** There is no expiry, revocation or rotation logic in the code;
  an external process must provide it.
- **Control handling is serialized.** `handle()` holds a lock throughout, so 8 connections is a
  ceiling rather than a concurrency capability. Per-request latency sets the throughput.
- **The 30-second cooldown is fixed by the startup code**, not configurable per sensor.
- **202 does not guarantee success.** Clients must consult the audit; 202 is not "hardware has
  changed".
- **SEL persistence depends on the disk.** The audit uses a regular file plus `fdatasync`, so a
  slow disk shows up directly as slow requests or 503.

### Why This Fits This Project

The control plane serves **a few administrators performing infrequent, well-understood actions on
one machine**, not a multi-tenant API. Under that premise:

- A single token with constant-time comparison and per-IP rate limiting already covers the
  "brute-force before the token leaks" class of risk;
- Serialized handling buys determinism -- audit order matches action order -- which is worth more
  than throughput here;
- Failing closed turns "someone forgot the token" into an obvious startup failure rather than a
  silently open write interface.

If the requirement ever becomes "many users, role-based authorization, online credential
revocation", the right move is a full identity layer (mTLS plus short-lived credentials plus an
external CA), not more switches on top of the current single-token scheme.
